# ADR-0085. Compose a board, calendar or resource timeline for a record type

Proposed for the orchestrator’s Fable read. Slice 0 is design only.

A sales team wants opportunities grouped by stage. HR wants to see who is away next week. A planner wants to know whether extending a room booking by an hour would displace another booking. Each request starts in **Customize → Add view** on the record type. The author chooses the fields and operations from its released catalog. The same choices work for first-party types and types a customer creates. The workbench, CRM and dispatch boards, mechanic planner, HR calendar and rescheduling gesture in the owner’s reference survey are examples of these needs. [Platform plan §§8.5–8.6, 12.2 and 12.12](../greenfield-north-star-erp-platform-plan.md)

## Three additions to the closed Surface grammar

Propose three platform-owned archetypes for the N4 Surface family. Each compiles to a distinct, deep-linkable SurfaceDefinition with the following fixed slots, in reading order. A view appears as a tab alongside the record type’s List. Switching views preserves compatible, authorized filters and explicit company scope. A card or entry opens the existing Record. The desktop builder chooses bindings. The compact builder supports preview, diff, approval and rollback. The existing shell, single right rail, navigation budget and Ledger themes apply to all three. [UX grammar](../../.agents/skills/ux-grammar/SKILL.md) · [Ledger spec §§2–6](../design/ledger-spec.md)

| Archetype and slots | What Customize binds | What a person sees |
| --- | --- | --- |
| Board · title, savedViews, stageSelector, columns | A governed collection, stable record ID and label, one declared finite status field with ordered status IDs and Ledger roles, and eligible lifecycle transition bindings. | One named column per stage, including empty stages. Cards carry the record link and a text-and-glyph status. A stage with several possible next steps offers the operation names. |
| Calendar · title, savedViews, dateNavigator, calendarEntries | A governed collection, ID and label, and a selected date, timestamp or typed interval. An interval can bind two compatible endpoints when the source declares their boundary convention. | Day, week and month show dated entries, with all-day dates distinguished from timed events. A spanning entry identifies both real endpoints and indicates continuation across the window. Previous, Next, Today and Go to date are links or forms. Calendar is read-only. |
| Resource timeline · title, savedViews, dateNavigator, resourceRows | A governed resource collection and interval query joined by a stable, typed resource identity. The editable binding names the booking pack’s agreed interval, booking identity/revision and versioned Change interval operation for extending or shortening one edge. | A labelled time axis and one row per resource. Bars show the interval and accessible endpoint text. Intervals from another declared source can be viewed read-only. A booking offers **Change start** or **Change end** for each eligible edge. |

Admit a view only when its query can select, scope, filter, order and page the declared fields. Validate the record link, resource/owner relation and each action’s argument types against the compiled contracts. A board with a status vocabulary and no transition operations is a useful read-only board. Cards with an optional unset status have a labelled **No stage** group. A missing optional date belongs in a reachable **Unscheduled** view. An invalid interval produces a diagnostic on the authorized record. Renames use stable IDs throughout. The renderer dispatches by archetype and slot. Applications supply neither templates nor code.

UI-COMPOSE-1 owns form and Record sections, action placement, pop-ups and branding. These collection views have their own declarations. They consume the published Record link, Task and shell presentation contracts. A layout revision can move a field on the Record without changing which field the calendar reads. The executable slices extend the plan’s closed anatomy, grammar pin, registered renderer and compact conformance tests together after the design ruling. ## What a drop can request

**Board.** Bind each movable edge to its declared source state, destination state, transition ID and existing Semantic Operation version. Verify that its declared effect performs that transition on this record. A generic status-field update cannot satisfy the binding. The server offers edges applicable to the current record, state and caller. Dropping on a column opens the same Task as **Move card** and choosing that stage. If two operations reach it, require a named choice. If more arguments are needed, the Task collects them. An ineligible destination leaves the card in place. The server checks a submitted move even if the page offered it a moment ago.

**Timeline.** Bind Extend and Shorten to the booking pack’s O2 **Change interval** operation in amended ADR-0082. A person changes one edge of the agreed interval on the same resource. For a future 09:00–11:00 confirmation, dragging the start to 08:30 or the end to 12:00 prepares an extension. Dragging the start to 09:30 or the end to 10:30 prepares a shortening. The server resolves the unchanged edge from the identified booking revision and submits the full replacement interval for review. A live hold or confirmation can offer either edge. In use, offer only a change to the remaining term that the pack admits. Actual-use legs remain intact. Occupancy-only spans, clipped-off edges, the bar body and other rows have no drag target for rescheduling. The form can reach a boundary outside the visible window. An empty interval or a request that changes both edges or the resource through a resize is refused. Billing consumes its own governed evidence. A resize has no billing action. [ADR-0082](ADR-0082-booking-over-time.md) · [ADR-0083](ADR-0083-period-and-usage-billing.md)

**Execution.** A drop opens or prefills a Task. It cannot confirm or dispatch a write. The Task shows the actual operation and predicted effects, including source and destination stage, or resource, quantity and both complete intervals with offsets. Inherit the operation’s risk, inputs, required review, independent approvals and live guards. An eligible ordinary O0 Task with no review can submit directly from its explicit action. Every booking extension or shortening requires an explicit yes. Bind preparation to the exact operation, operands, record revision, authorized actor/scope, release and activation fence. Editing invalidates preparation. Execution through the Semantic Operation gateway rechecks grants, current state, revision, guards and confirmation. The booking writer checks capacity under its lock. On an exact retry use the original idempotency key and receipt under current authority.

Redraw from governed read-back after success. A concurrent booking can win after review. Then show **No longer available**, retain the proposed input for correction, refresh the permitted row and show the stored interval. Do not expose the conflicting owner through the refusal. A stale board move similarly returns the current permitted stage and asks for a fresh decision. If read-back access is withdrawn, report the permitted receipt or refusal and withhold the old details. [ADR-0071](ADR-0071-read-decisions-are-live-per-request-writes-per-call.md) · [ADR-0082, writer and query contracts](ADR-0082-booking-over-time.md)

## One document script and an equivalent form

All reads, paging, controls, preparation and confirmation are server-rendered. Propose one narrow amendment under ADR-0036 §2a for pointing at a card or an interval endpoint and releasing it on a target. Native navigation covers the full task but cannot carry a continuous pointer gesture to its drop target. Ship the complete form path first. In the existing dependency-free, CSP-hash-pinned script, track the active pointer, mark the current server-rendered target and, on a valid drop, select the corresponding value in the existing form and submit **Open move** or **Review interval**. The server supplies the offered target IDs. Render one shared axis of at most 64 drop positions with explicit instants and offsets, reused across resource rows. Precision between ticks is available in the form. While dragging, the source stays in its committed position. Escape, pointer cancellation or releasing outside an offered target clears the highlight and submits nothing. Calendar navigation uses ordinary links throughout. [ADR-0036 §§2–7](ADR-0036-minimum-client-capability.md)

Keep the script free of business state, date arithmetic, availability calculation, optimistic card/bar moves, extra fetches and client rendering. Use the normal same-origin page submit to enter the Task, with a return link to the originating view and window. The served-page gate counts the owned script and checks its CSP hash. A browser gate exercises drag and cancellation, then repeats the successful and refused actions with JavaScript disabled and a keyboard. The amendment ships only with the underlying operation, form and browser evidence.

Give each column, date and resource a heading and use native links, lists and labelled controls in visual order. **Move card** selects a destination/operation. **Change start** and **Change end** each accept the exact date, time and, when needed, offset for that endpoint. Both are reachable by Tab and Enter and by a single tap. Review, Confirm and Cancel work in both paths. Announce the result and focus the changed record’s action on return, or the view heading if it has left the page. On refusal focus the error linked to the field. Status and continuation use text and glyphs in both themes.

At 390 px the board shows one selected stage with its cards and a labelled stage switcher. The calendar shows a date-grouped agenda for the selected day, week or month. The timeline shows a resource selector and the selected resource’s chronological appointments with full endpoints. Each preserves period, paging, record links and every applicable action. Touch targets are at least 44 px and the page fits without horizontal scrolling. Compact interaction uses the forms.

## Time windows, coverage and page budget

Use half-open windows. Select a date or instant when `windowStart <= value < windowEnd`. Select an interval when `start < windowEnd && end > windowStart`, including one that began before the window. A date-only field stays a civil date. A declared inclusive civil end is converted using the next local date boundary. Resolve timed and business-date boundaries in the source’s declared business calendar and IANA zone and display the zone. Resolve the two boundaries separately through DST. For ambiguous local input require an offset and refuse nonexistent local times. Booking reads preserve the instants and offsets the pack recorded. Clipping a bar for display never changes the operation input. [ADR-0082, time and evidence](ADR-0082-booking-over-time.md)

| Read | Maximum in one response | How to reach more |
| --- | --- | --- |
| Board | 6 stages with 10 cards per stage, in declared stage order and stable record order within each stage | Page stages or select one directly. Each stage has its own card continuation. Move card can reach an offered stage on another page. |
| Calendar | 1 day, 7 days or one displayed month including adjacent grid days (at most 42 civil days). At most 100 distinct entries per page. | Page by effective start/date and stable record ID within that window, or select a different window. |
| Timeline | Default 7 days, maximum 31 civil days, 20 resources and 100 interval or occupancy segments total per page. | Page resources by stable key. Within that resource page continue by resource, start and interval/segment key, or narrow to one resource. Mark every row whose coverage is partial. |

Apply the stricter of these limits and the bound query’s own limits before rendering. Keep a month-spanning event as one entry with a span indicator in the agenda. Render one move control per card and load its full choice of operations only when opened. Authorize and filter in the provider, batch resource labels, records and transition eligibility, use indexed window/stage access, and probe one extra result to detect more. Validate the requested window and sizes before querying. Give each bounded provider query an explicit scan/work ceiling. If the ceiling is reached before exhaustion, return a continuation or **Narrow the search** with partial coverage. A failed or partial result cannot render as zero matches or free capacity. Counts, if shown, must identify a page count or come from an authorized aggregate.

Use opaque server-validated keyset continuations bound to principal, tenant, environment, company, release, view revision, filter, sort, group/resource page and window. Each page is a new authorized read with a read instant. Refresh starts a new traversal. If source revisions used for paging changed, restart the affected traversal with a visible message. A stale or altered cursor refuses. Never keep a database transaction open between pages.

The timeline consumes BOOKING-1’s Q2 **Bookings in a window for a resource set**. Pass the bounded, authorized resource page and half-open window. Require resource and availability access for the booking layer. Read booking details and owner links only with their separate grants. On a shared resource, occupancy includes all companies. Hidden commitments yield the pack’s coalesced anonymous busy spans, including overdue occupancy, without booking IDs, owner labels, counts, links or handles. Preserve coalescing across page boundaries. Draw editable handles only on authorized agreed intervals, even when occupied time differs from the agreement. A blank region is never proof of availability. A quantity question uses the pack’s pool remaining capacity query. Continue at the same pack snapshot or restart explicitly. Generic interval projections confer no availability claim. A missing resource-window protocol produces a named capability gap. [ADR-0082, scheduling queries](ADR-0082-booking-over-time.md#what-the-picker-assistant-and-workflows-may-read)

**Proposed acceptance budgets.** For a warm, successful full-page read of each archetype, including the shell and continuations, cap database work at 2 transactions (one read-only snapshot plus live epoch check), 40 statements, 3 authorization reads and 0 repeated identical statements. Warm operation/query/manifest parses are zero. Parse each distinct bound surface at most once. Use the SPEED-1 request meter on the actual served route at both sparse and full pages, assert visible seeded entries and next-page coverage, and pin each measured ceiling within that budget. Statement counts must stay flat as cards, days and resources fill the page. The common registered query target is p95 under 400 ms at the declared launch shape. Report timing separately on that fixture. A write, durable denial or policy-epoch retry retains its required checks and is measured separately. ## Publish, understand and roll back a view

Add three closed, schema-versioned patch members, `addBoardViewRevision`, `addCalendarViewRevision` and `addResourceTimelineViewRevision`. Each appends an immutable full view revision with a stable surface ID, owning type/list, label, predecessor and active or retired status. Reference fields, statuses, queries, resource relations and operations by stable IDs and expected typed contracts. Bind the patch to its source release and effective result digest. The visual builder and AI drafter produce the same ordered change set. Resolve new fields/types before their view. Show the chosen bindings, available moves and impact in the plain diff and preview. Compile, verify, approve the exact candidate and activate by compare-and-swap. Retirement removes the tab in that release. A pointer rollback restores the earlier tabs. Committed transitions and booking events remain in the records.

Replay reproduces the original root before applying a revision to an upgraded base. A retired status, changed interval convention, rebound resource relation, missing query selection, changed operation contract or broken predecessor gives a typed diagnostic with the affected IDs. Keep the serving release and show the owner what needs rebinding. Verify declaration, compiled slots, query/operation/assistant bindings and mandatory surface-manifest requirement in both directions. Use optional v6 declarations with no materialized defaults. With the feature omitted require byte-identical historical normalized packages, envelopes, roots and floors on first-party and actual customized tenant runners. Follow ADR-0047 for projection profile changes and return for a language ruling if existing v6 meaning must change. [ADR-0047](ADR-0047-the-compiler-semantic-profile-is-the-projection-evolution-axis.md) · [ADR-0074](ADR-0074-formula-rule-and-workflow-projection-admission.md)

Each executable capability takes the next scalar reader rung above the highest implemented on freshly fetched main **when it merges**. Board, Calendar and Resource timeline each need their own rung. Slice 0 assigns none. A release advertises the maximum its features require. Test the actual preceding serving reader’s refusal before any request, including mixed releases with layout and booking features, and refusal of an understated manifest. Regenerate artifacts and tests, run CI and re-fetch before push. If another capability landed first, renumber, regenerate and rerun. Deployments must support the highest patch parser and surface-reader floors any tenant has used, even after pointer rollback. [ADR-0079, reader admission](ADR-0079-form-and-record-composition.md)

The assistant resolves the current tab, stage or resource, window, zone, filters, coverage and eligible actions from the same pinned Surface and governed queries on each request. It can explain “Why is this card here?”, show this week’s absences, or propose extending the selected booking. It states the window and any missing coverage. Availability questions use the pack query at its read instant. It sees only permitted fields and actions, including after a scope change. A requested move resolves to the underlying operation in the existing plan, confirmation, receipt and verified-state flow. An eligible reversible action keeps its existing Undo contract. Booking resizes require the exact plan’s yes. Changing tabs cannot retarget a pending decision. Unsupported actions surface as capability gaps. ## Implementation after Fable’s read and the orchestrator’s ruling

1. **Board.** Publish a customer-created opportunity board and a work-order board through Customize. Move one card with a pointer, one with the keyboard and one with script off. Observe the stored stage and a single operation receipt. Deny a disallowed edge, a revoked grant, a stale move and an unconfirmed consequential transition. Check crowded and empty stages, the phone view, rollback, compatibility and the served-page budget.
2. **Calendar.** Publish a due-date calendar and an absence-interval calendar. Verify an interval spanning the window, an event at its exclusive end, a DST change and page 2 of a crowded month in desktop and phone layouts. Confirm the assistant names the same window and coverage. Gate historical replay, preceding-reader refusal and page budget.
3. **Resource timeline, after BOOKING-1 slice 1.** Use slice 1’s Change interval writer and the resource-set query delivered with Booking’s slice 2 scheduling protocols. Start integration after slice 1 and ship the editable timeline once both bindings are available. Exercise rooms and bookable units from separate customer-built modules. Race an extension with another commitment, confirm the refusal preserves the original booking and inspect both the winning receipt and read-back. Shorten the other edge via keyboard with script off, retry after a lost reply and verify one committed change and intact actual-use legs. Exercise a shared resource with a hidden owner, a full page with more intervals, compact navigation, replay, reader admission and page budget.
