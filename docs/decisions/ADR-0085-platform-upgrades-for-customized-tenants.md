# ADR-0085. Ship platform updates to customized companies

**In force as design, 2026-11-20, except for the policy rows, which are proposed, awaiting the owner's ruling.** Fable's verdict was ACCEPT WITH AMENDMENTS. If the owner declines the proposal, every other decision stands and every activation remains Manual. Fable’s narrow re-read accepted the design with amendments A19–A24. Slice 1 may start now. Slices that exercise CUSTOMIZE-3 and WORKFLOW-1 require their authoring, verification and approvals. The gates below are due before the first real customer.

## What a company is upgrading

A tenant may run several companies in one environment. They share an active release pointer. An upgrade moves that pointer once. Each authorized company sees the first-party base and customization revision actually serving its work. A platform rollout schedules those tenant/environment transitions independently.

UPGRADE-1 already replays immutable tenant patches onto a new first-party base and stages a candidate with the verified source as its parent. CRITFIX-B keeps the source serving on refusal. CRITFIX-C distinguishes a swap from a verified generation. CRITFIX-D can re-verify the same attempt and fence or explicitly revert a failed swap without parsing the broken candidate. The design uses those paths for every wave member. ## Workflow authority

Every workflow-bearing release is **always Manual** in the first shape, including an unchanged workflow body. The person approving activation supplies the authority ceiling for runs. Before that decision, reviewed evidence shows the number of in-flight runs the activation will suspend and the number of pending approvals it will permanently invalidate. While the new release serves, a suspended run can only be cancelled. Lifting this restriction needs a later ADR defining both successor retry and authority-ceiling inheritance. [ADR-0073, run pinning, replay and approval](ADR-0073-workflow-isolate-and-authority.md#run-pinning-replay-and-approval)

## From a replay conflict to a reviewable correction

First replay the source chain against its retained bases with its recorded parser, compiler profiles, evaluator bindings and acknowledgements. Compare each revision and release root. Then replay the ordered patch IDs in the sandbox against the target base at declared extension points. A compatible replay stages one child of the verified source. Historical reproduction failure, whole-package failure and an authored conflict are distinct outcomes. Only an attributable conflict names a particular tenant patch. [ADR-0013](ADR-0013-semantic-patch-lineage.md) · [Projection admission and replay](ADR-0074-formula-rule-and-workflow-projection-admission.md#release-lineage-and-replay)

### Slice 1 replay admission

At the read, `UPGRADE_PATCH_KINDS` in `packages/postgres-provider/src/customization-service.ts:96-105` admitted eight kinds. A chain containing `addRecordType`, `addChoice`, `addLink`, `addLineTable`, `declareLifecycle`, `addDocumentField`, `addUploadCategory` or `addLayoutRevision` refuses **every** base change with `CUSTOMIZE_BASE_MOVED`. The existing record-type refusal test pins that defect. Slice 1 replaces that expectation with successful replay for compatible bases and continued verified serving on a real conflict.

Admit **every** kind in `CUSTOMIZATION_PATCH_KINDS` to real replay before the first customer. Maintain the replay allowlist as an independent hand-written literal. Admission descends into the ordered members of each changeSet. The inventory test requires a named replay test for every admitted kind, exercising one compatible base move and one real conflict. CI must fail closed if vocabulary minus replay allowlist is nonempty, including when saveWorkflow, addPopupActionRevision or addCompanyBrandRevision enters the vocabulary. An unadmitted kind is a platform defect. Slice 1 also owns the diagnostic table, collection in one attempt, and the optional-field-on-a-re-laid-out-surface case below.

UPGRADE-2 slice 1 owns addLayoutRevision replay admission and the moved, retired and changed-binding conflicts. UI-COMPOSE-1 slice 1b owns hide, collapse, concealment and reset-to-base after slice 1 merges.

On the authoring base, verify the recorded per-edit expected digests and resultLayoutDigest exactly. On a different base, set aside target members absent from the authoring base and check each edit structurally for member presence, expected parent, destination, anchor and binding contract. Report MOVED_MEMBER, RETIRED_TARGET or INCOMPATIBLE_TYPE for a changed placement, missing reference or changed binding respectively. Place each set-aside member in base order using ADR-0079’s tenant-added-field rule unchanged (placement rule v1). It follows its base-order predecessor in that predecessor’s current section, or goes at the end of the first section if there is no placed predecessor. This defines compatible additions’ declared placement on a composed surface. Record the rule version and new effective layout digest on the candidate and the digest in its upgrade evidence. Preserve the original patch.

The drafter may propose moving the field from Shipping or relinquishing the override with slice 1b’s reset-to-base edit. Give the AI only authorized terms. Reserve against a finite drafting cost cap per refused upgrade before each call, attribute usage to its tenant, upgrade and requester, and carry the cap across retries. Exhaustion leaves manual drafting available.

Save the correction as an ordinary immutable draft. Use one generic schema-versioned replacement kind for all five customizations, keyed by **(patch ID, edit position, first base root it applies from)**. Capture the replacement's own expected contract against that new base. The refused upgrade ID records provenance only. Reproduction before the correction ignores it. Replay subsequent revisions with applicable replacements and unaffected edits in order. Preserve original attempts, patches and roots. Compile, verify and present the exact diff. Derive correction provenance from parent and replacement edges across retries and retargeting. A person must approve the exact corrected revision, including after another base, revision, evidence or fence change. The last verified release keeps serving. ## Rollout waves and the company version dashboard

The binary deploy is fleet-wide. Waves stage only release pointers. The sole target is the installed binary's first-party tip (release ID and root). CI serves a real request from **each still-supported older base under the new binary**. A later-wave, paused, held, Manual-waiting, excluded or conflicted tenant keeps drafting against its retained serving base. Replace the tip-only draft guard at `customization-service.ts:2217-2229` with resolution of that base and a source-fence check. If the serving pointer changes, re-prepare the pending attempt against the actual verified source. Test drafting and reviewing a normal revision while waiting.

Snapshot explicit tenant/environment membership and target at wave start. A tenant created mid-wave starts on the installed tip. Give each member a durable attempt identity, deduplicate by source generation and target across waves, and stage and verify under its own scope and release lock. The wave header is platform-plane in the tenant completeness manifest. Member rows are tenant-scoped under forced RLS. The cross-tenant operator view exposes only tenant/environment IDs, status and diagnostic codes. Keep subjects, labels, company names, bodies and patch content within authorized tenant reads. [Plan §7.5](../greenfield-north-star-erp-platform-plan.md) · [ADR-0019](ADR-0019-tenant-completeness-and-single-tenant-recovery.md)

A Manual member waits for human approval. Conflicts, refusal or failed verification hold advancement. Pause serializes with the final pre-swap check. Resume reconciles in-flight attempts by identity and rechecks target, authority, policy and source fence. A committed swap finishes verification or recovery. Record an attributed **exclude member / proceed** decision with actor, reason, member, target and attempt. It sets the member to excluded and preserves its serving release. Advance when each member has a verified target receipt or a recorded exclusion. Scheduling does not approve an activation. Whatever the owner rules on policy approval, confine waves to the explicit local demo or the owner's CLI on the pilot machine until the separately provisioned principal and its decision proofs exist.

When N+1 becomes the installed tip during N's wave, close unfinished unswapped attempts for N as **superseded**, retaining evidence and linking the successor attempt. Reconcile a committed swap first. Replay each member directly from its own verified source to N+1, including skipped versions, without activating N as an intermediate step. Refresh evidence, correction applicability, fencing and approval for the new target.

The company dashboard is a governed List. Resolve company ownership and current membership before returning rows or details. Show each authorized company's serving first-party base/version/root, customization revision and verified release/fence beside the target, upgrade ID, own wave position, approval mode and status. The tenant sees only its own wave position, with no fleet membership, counts or other outcomes. Statuses are **queued, paused, pending approval, refused, conflicted, verifying, verified, excluded, superseded, reverted and failed-verification**. Link to the authorized diagnostic, diff, recovery and decision history. Companies sharing a pointer show the same verified generation, including during a pending swap. Company-only grants confer no tenant-wide release authority.

## Format changes and deployment

### Forward conversion and the first-tenant switch

Ship a deterministic, versioned forward converter and a real-runner old-format replay fixture for each change that re-reads existing stored patches. A new reader rung for an optional feature with no old bytes to reinterpret needs a capability check. Keep old parsers for every retained revision and rollback target, permanently in this first shape. Reproduce historical revisions/roots first, then append a derived representation bound to input digest, converter version and output digest. Conversion is idempotent and preserves original bytes, patch IDs, order and historical roots. Any attempt using conversion is Manual. Ambiguous semantics or missing evidence refuses by name. Test forward replay, verification, activation and compatible pointer rollback without reset.

At the first-tenant ruling, mark the store and pin the ruling commit's checked-in release lineage. Two checks enforce the switch. `dev:reset` refuses a store carrying the first-tenant marker. CI rejects any rewrite or shortening of the checked-in lineage after the ruling commit. Prove both refusals. [ADR-0066](ADR-0066-pre-tenant-development-re-baselines-the-release-lineage.md) · [ADR-0074](ADR-0074-formula-rule-and-workflow-projection-admission.md)

### Binary admission and rollback window

On **process start**, in one database transaction, present the tested binary capability manifest and obtain a scoped admission record before the web process listens or any worker claims work. Both trusted request context establishment and work claims require the admission bound to that process/build. At the first-tenant ruling a migration enforces that dependency and makes the handshake-capable binary the absolute floor, including for older binaries that cannot ask for admission.

Keep a durable, append-only fleet deployment register outside tenant databases and their restore domain. It is the authority for per-tenant/environment high-water marks, including offline scopes. Serialize admission and capability use against its current generation. Before acknowledging new use, durably reserve the required capabilities in the register and record their use in the tenant transaction. An interrupted write or disagreement on restore blocks admission pending reconciliation. Scan approved retained lineage, verified rollback targets, actual release features and pinned work. Preserve historical maxima through restore, pointer rollback and policy revocation. Missing scopes or unknown capability block admission.

Compare the fleet maxima for patch parser, scalar surface-reader rung (including every lower rung) and platform migration level. Also require the exact compiler profiles and evaluator bindings needed for historical reproduction and the engine/host/SDK builds of unfinished workflow runs. Raise marks from approved lineage and pinned work. An abandoned unreadable draft refuses by name when opened. A draft alone cannot pin the fleet.

Keep new parsers and rungs disabled fleet-wide until an operator records closure of the binary rollback window. Until then, the designated rollback binary counts among all eligible serving and worker builds, whose common support bounds use. Exercise start, downgrade and restore with a genuine preceding reader, an offline store, a post-rollback high-water mark and a pre-handshake build. An incompatible process must fail before listen, context establishment or claim.

At each executable merge fetch main and allocate each new incompatible surface capability the next free scalar rung. Allocate forward migrations after the highest landed migration. Regenerate affected artifacts, schema snapshot and migration-list tests, run CI, and re-fetch before push. Renumber on collision and serialize migration merges. This proposal allocates neither number. The same gates cover calculated display fields, documents and any connector, booking or billing patch kind admitted later.
