# ADR-XXXX. Apply a versioned template when creating a record

Proposed design, amended after the independent slice-0 read on 2026-11-21. Assign the ADR number at merge.

A safety lead can already define an Inspection with a table of results. The lead also needs to write the questions for a particular equipment class. If the lead changes “Does the brake hold?” next week, a supervisor reopening Monday’s inspection must see the question the mechanic actually answered. A print shop needs the same guarantee for job instructions, and a school for the roles on a pupil’s contact form. [CUSTOMIZE-4](../execution/packets/CUSTOMIZE-4.md) · [Plan §§10.5–10.6](../greenfield-north-star-erp-platform-plan.md)

## Proposed decisions

### 1. Release the record structure. Let office workers publish the content.

In Customize, the owner enables templates for a declared place on a company-owned record, such as its results table. The binding identifies the record type, owned collection, writable fields and relations, allowed answer types, context selector and creation operation by stable ID and contract. It also says whether a template is required. The same binding serves the Record, the assistant and the operation gateway.

CUSTOMIZE-4 generates one editor line table with release-defined columns. Extend its declaration with one binding for presenting an owned collection. It names the parent relation, permitted line fields and reference pickers, editable line slot and corresponding Record child-table or section slot. On create preview, resolve the ordered groups and columns from the assigned revision. On edit and detail, resolve them from the application. Both views enumerate the pinned group keys first, then join the record’s owned rows by group key. An ungrouped grid uses one table. A role renders a labelled section even with zero rows, with its declared picker in edit and its contacts or an empty state on detail. The same mechanism orders and captions the selected columns in each group. Each input still writes its declared field or relation and each detail cell uses its governed read. Validate required-field visibility against the selection. ADR-0079 supplies placement for this collection within the existing Record anatomy. [Generated editor](../../packages/customization/src/apply.ts) · [ADR-0079](ADR-0079-form-and-record-composition.md)

An authorized author opens **Templates**, drafts an ordered set, previews it on the bound record and publishes a numbered revision. They can start with the declared columns and explicitly chosen starting values from a grid they may read. Show exactly what will become a reusable default. A field must be declared eligible for copying and for disclosure to the template’s audience. Copying a finished job wholesale risks publishing a customer’s entries to colleagues. Answer-only fields always start empty. Editing published content starts a successor draft with an expected predecessor. A competing publish must reload the winning revision. Retiring a template closes it to new applications and retains its revisions.

| What the author saves | How the record uses it |
| --- | --- |
| Ordered question or instruction, help text, answer field and permitted choices | One identifiable item, with the question and an empty typed answer or an instruction to read |
| Named role or section | A labelled group with its own membership and declared contact fields or links |
| Ordered column captions and typed field bindings, followed by starting rows | A grid with the selected columns in order and fresh editable rows |
| Member reference and suggested count | A proposed kit line on the new record. Stock movement, custody, reservation and billing each need their own authorized operation. |

Every revision has its own identity under a stable template ID. Members have stable keys independent of their label and position. Retain keys through renames and moves, allocate new keys for different meanings and never recycle removed keys. Constrain copies to declared, bounded literals, choices or scoped reference IDs. Publishing checks the entire set, including types, targets, duplicate keys, required starting fields and the declared size limits. Exclude protected fields and authoritative Tier B inputs and outputs from defaults. A template author can select among admitted types. Adding a new field type, widening access or installing a new operation requires a release. [Plan §10.6](../greenfield-north-star-erp-platform-plan.md)

**Reason.** Staff change the ten questions far more often than the shape of a result row. A release per question set would turn a weekly content edit into a schema deployment. A free-form JSON or script field would lose typed inputs, permission checks and discoverability.

### 2. Assign a published revision to one exact context.

The assignment key includes tenant, environment, owning company, record type, template binding and context value. The binding selects one declared choice or one scoped record link, for example a job class. A binding for the whole type uses one explicit whole-type key. Use the validated value on the proposed record or the stored linked record identified by the binding. The server resolves and locks that context. A caller-supplied company label or suggested template ID has no authority.

One assignment at a key points to one published revision. Show the revision and context in the creation preview. Replacing that assignment requires its expected version and takes effect for subsequent creates. Publishing a successor alone leaves the previous assignment in force. A changed assignment between preview and first save requires a fresh preview. An unassigned optional section starts empty. An existing assignment that is inaccessible, retired, incompatible or ambiguous refuses creation even for an optional section. Existing records retain their original application.

**Owner decisions for launch.** Each company has one library. A required binding accepts only the exact server-resolved assignment. If it is missing, refuse creation, identify the section to an authorized worker and let an authorized assigner repair it. Test an empty required context and an attempted worker override with a different readable revision. Both refuse. After assignment, the worker can preview again and create with the assigned revision.

**Reason.** An inspector and a scheduler starting like records in the same company must be able to explain the choice. Selecting “latest,” matching by display name or taking the first of several inherited matches could give them different questions.

### 3. Give each record its own rows and keep what each answer meant.

At first save record the parent, tenant/environment/company, applied context (selector ID and typed choice, scoped link ID or whole-type key), assignment version, template/revision IDs and immutable content digest. Pin the binding revision and its versioned field, relation, picker, presentation and lifecycle contracts, and the content schema version that decodes member keys, types, choice IDs and meanings, validation rules, authored captions, order and defaults. Retain the referenced contract bytes and decoder for the life of the application and receipt. Generate fresh IDs for owned groups and rows. Keep their source member keys and original order. The record owns its answers, actual contact links and edited counts.

The Record’s scoped application query takes the parent ID and binding ID, checks the stored owner and current record and field grants, then reads these pins and the record’s own values. The editor, detail view and receipt read-back use this query after reassignment, binding retirement or a compatible pointer rollback. Resolve each contact ID and label through its currently authorized reference read. Ordinary answer edits use the record’s revision checks and audit trail.

Source identity and the original checklist membership are server-owned. A user cannot erase a required question by deleting its seeded row through the ordinary child editor. Where the binding admits extra work rows or contacts, give additions fresh IDs and distinguish them from template defaults. Archiving a parent, role or template retains provenance. Existing records created before templates keep their ordinary data and have no application. Where reclassification is permitted, the applied context and answers stay pinned. Guarded records follow decision 6.

**Reason.** A live join to the active template would change the meaning of an old answer. A detached copy would preserve the text but lose which approved revision supplied it.

### 4. Separate permission to publish, assign, apply and answer.

Grant drafting/publishing and assigning explicitly in the library’s company. For a grid copy, retain the source row IDs, fields and values selected in the draft. At publish, re-read the source under the publisher’s current grants and check the reviewed values, each field’s copy eligibility and permission to disclose each literal or reference to the declared audience. A change requires fresh review. Reject a restricted copy even if the author can read it. Before assigning, load the context and the revision through their stored scope and require both to belong to the binding’s company (a declared choice uses its scoped assignment key). Access to both companies cannot authorize a cross-company pair.

Preview and create each require the worker’s current apply write grant, read access to the assigned revision and context, target create authority, write permission for every seeded field, child and link, and read access to every referenced target. Check the entire selection before returning defaults or writing any row. A denial can name the missing permission where authorized and must omit protected values, labels and IDs. Apply the same disclosure rules to library and revision reads. Editing an answer later needs the record’s ordinary scoped write permission.

Resolve company, binding, published status, stored owners, effective grants and active release fence on the server. Bind any reviewed decision to its exact digest and fence, including after switching away and back. Use scoped readers and narrow database writers with a fixed trusted search path. Give the runtime role no direct table grants. Audit publication, assignment, application and answer edits with actor, scope, revision and record identity as applicable. Withheld read-back reveals no prior answers or other company’s template name.

**Reason.** Anyone who can answer a question need not be able to change the questions for all colleagues. Copying the author’s privileges into a template, or treating a read grant as permission to apply, would let a default write a value the caller could never enter.

### 5. Apply once, in the transaction that creates the record.

The normal editor’s first save, direct create, imports and the operations assistant all submit one prepared request to the bound record’s create operation. Make resolution mandatory inside that operation, including on an ordinary header-only call. Replace ADR-0072’s sequential header/line first save for a bound record. The transaction writes the header, pinned applications, fresh rows with authorized initial edits, receipt and creation audit together. Enforce uniqueness on parent/binding. A failure on the last seeded row rolls back every creation fact. Later manual edits follow the ordinary document editor’s save contract. [ADR-0072](ADR-0072-tenant-document-editing-and-links.md)

Keep a stable create key from preview through retry. Uniquely index the receipt by authenticated tenant/environment/company, principal, stable create operation ID and key, across release generations, assignment versions and retirement. Its digest covers the canonical original inputs and reviewed selection, including context, assignment version, revision/content digest, binding contract and release fence. On every entry point, including after binding retirement, look for that receipt inside the transaction before dispatching by today’s binding or checking preview freshness. Compare the retried request with the stored digest. A mismatch refuses. For an exact retry, check current apply/create and scoped field, reference and record permissions against the original selection. Return the committed identity and currently readable record values, preserving intervening edits. If read-back is withheld, disclose no protected data and retain the committed receipt and key reservation. Restored grants recover the same outcome. Reapplying to an existing record refuses even with a new key.

Acquire the release fence, then the scoped request key for create, then the stable company library lock keyed by (tenant, environment, company), then assignment keys in stable order. For guarded records acquire the per-parent guard lock (decision 6) before affected record locks. Respect the existing descendant-before-ancestor record lock order. Publish, assign, retire, fresh create and archive take the same library lock even when the assignment row does not exist. Re-read stored owners, versions and liveness after waits. A retirement that wins refuses the waiting assignment. An assignment that wins may commit, but retirement then closes that revision to fresh creates. Writers relying on READ COMMITTED check that isolation level on entry. Use distinct namespaces for system-created member identities and user additions.

With no committed receipt, recheck the exact preview and its decision under those locks. Reassignment, retirement, a changed context or a changed release fence invalidates it, even on a pointer switch away and back to identical bytes. Return a fresh-preview requirement and commit zero creation facts. A worker can review a valid new preview and submit again.

**Reason.** A lost response should cost a retry, never a second checklist. A browser loop that first saves the header and later copies defaults could leave an inspection looking complete with half its questions missing.

### 6. Keep release decisions with the business that owns them.

For each question, pin its answer type, allowed choice IDs and meanings, completion requirement, N/A eligibility, failure-note rule and whether failure blocks the declared transition. On every answer write, validate each supplied value against its pinned type and choices, including N/A eligibility. A draft may retain a blank answer or a failure awaiting its note. Keep absence distinct from each selected choice. ADR-0076 covers admitted same-row and to-one validations. [ADR-0076](ADR-0076-cross-field-and-to-one-validation.md)

**Capability gap.** The CUSTOMIZE-4 transition checks the source state. ADR-0076 cannot count or validate a pinned collection of owned lines. While a guarded binding lacks that general lifecycle check, the operation gateway must refuse every transition into the guarded state, including the already-generated CUSTOMIZE-4 **Release** operation. The UI and assistant surface the gap. Test a quarantined inspection with all passing answers and an authorized worker through the normal action, assistant and direct existing transition. Each must refuse and leave the stored state Quarantined with zero successful Release events. [CUSTOMIZE-4](../execution/packets/CUSTOMIZE-4.md) · [Plan §10.4](../greenfield-north-star-erp-platform-plan.md)

**Gate for enabling Release.** Serialize Release, answer/child edits (including archive) and context changes on the same per-parent guard lock before reading or mutating the protected facts. In the transition transaction verify the applied context against the record, enumerate the full pinned membership and match its live owned rows by source key. Check all required members and answers, allowed choices, N/A, required notes and blocking failures before committing the state and audit. Guarded records retain their applied context. Refuse a context change that would reclassify one, and refuse answer or membership edits once Released.

Start each Release test in an eligible source state. Independently leave a required answer blank, omit its seeded row, supply an ineligible N/A, omit a required failure note on a nonblocking item, and record a blocking failure **with** its note. Each refuses with the state intact. Use a malformed stored fixture for cases rejected on write and test that write refusal separately. A complete allowed set including a passing required answer, an eligible N/A and a documented nonblocking failure releases once and records one Release event. Race the last answer edit against Release in both orders. Either Release judges the committed edit, or the later edit refuses on the released state. Attempt a change of equipment class before and after Release and verify the applied class and answers.

**Reason.** A printer can proceed with an unfinished work request where a failed safety check must stop release. A built-in inspection rule would impose one business’s policy on everyone. A display-only warning could allow release through a different caller.

### 7. Upgrade the binding without rewriting template history.

Persist the binding’s stable IDs and pinned contracts in an add-only, versioned Customize patch (proposed kind `addRecordTemplateBindingRevision`). Register it in ADR-0085’s replay allowlist and compare replay coverage to `CUSTOMIZATION_PATCH_KINDS` in CI. Omitting its handler must fail the check. Replay the ordered patches on the retained authoring base first, verifying the exact choices digest and original release root. On a new base check active bindings structurally, including fields, relation ownership, operations and active assignments. A label-only rename, unrelated added field and List rearrangement must compile and replay with the binding active, then again after retirement. In a separate active case change the bound Copies field from whole number to text. Require a conflict naming its field ID and the incompatible types, then serve a query from the still-verified source. [ADR-0085](ADR-0085-platform-upgrades-for-customized-tenants.md)

Retired bindings skip active-member validation and fresh assignment. Keep their versioned historical reader and the guard on every affected record. Before activation or pointer rollback, verify the target can interpret all used contracts and committed receipts and enforce the pinned lifecycle restriction on every route to Release, including when the general guard is still unavailable. Refuse a target that strands a record or receipt, or restores a source-state-only transition for it. Test with an applied I-17, an edited answer and its creation receipt. After retirement and again after a compatible rollback, open the application via the scoped Record query, retry the original request and attempt Release with the blocking failure. Expect the same applied class, meaning, edited value and record ID, one creation, and a refused Release. Try a target missing the historical reader and another exposing the unguarded transition. Both leave the verified source serving.

With the declaration absent, compare the persisted normalized definition and projection bytes, release roots and reader floors to their pre-feature values on a first-party release and a tenant-authored release. Allocate the required patch parser and reader floors (including any declaring Surface and operation capabilities) and migration numbers at executable merge. Pin the actual immediately preceding serving binary and its manifest at that merge. Through production admission, boot it on a compatible persisted release and assert the expected result of a real query. On a declaring release, require `UNSUPPORTED_RUNTIME_CAPABILITY` naming the release and missing reader/capability before any definition parse or projection decode. Exercise both cold startup and opening the moved pointer in the running compatible process. Observe the parser boundary on each refusal and verify the capable build serves the declaring release. Retain the deployment high-water mark for the newest parser and floors used by any tenant. UPGRADE-2 slice 5 owns the deployment proof. Its entry condition is a register independent of the tenant pointer that retains the highest parser and reader floors used. Exercise it after pointer rollback by attempting deployment below the retained floor. [ADR-0090](ADR-0090-check-release-capabilities-before-boot.md)

**Reason.** Rebuilding old revisions from the current layout would make an unrelated rename break publication or historical reads. Letting an older reader ignore a binding could let it create records without their mandatory questions.

### 8. Draft the binding and content in the app. Apply through ordinary creation.

Generate the Customize drafter’s binding vocabulary from the patch schema and check drafter coverage against `CUSTOMIZATION_PATCH_KINDS`. An owner describes the record, collection, context and allowed fields. Customize proposes a binding and shows the same plain diff, verification, human approval and activation as the visual path. With the binding live, an authorized template author can ask in plain English for actual members, order, choices, notes and defaults. Produce an editable company-library draft. Show the ordered content, source values, completion rules and audience before the human publishes. Assignment is a separate authorized decision naming the exact published revision and context.

Add a live in-app AI-BUILD-1 case. Ask Customize to bind inspection results to equipment class. Review the diff, approve and activate. Ask the library drafter for the brake and cab-light questions below, edit the brake wording in its preview, publish the reviewed wording and assign revision 1 to Lift. As a mechanic, ask the operations assistant to create an inspection for Lift. It must show the server-selected revision and effects, follow the create operation’s confirmation policy and use the same atomic create and governed read-back. Verify the stored wording, member keys and receipt. Repeat with a worker lacking only apply and with reassignment between preview and submission. Each attempt must leave zero creations. A fresh authorized preview must select revision 2. [ADR-0079](ADR-0079-form-and-record-composition.md)

## Three acceptance walkthroughs

These are acceptance tests for the executable slices. Create each pair through the normal editor. Reopen both records in the editor and on Record detail, then retry the first creation with its original key and inputs.

**Equipment safety.** Declare Inspection’s scoped Equipment class link and owned Results relation. Each result has a pinned question key and prompt, a nullable choice answer and a text note. Present an ordered question table with distinct blank, Pass, Fail and N/A states. A safety lead assigns **After repair** revision 1 to Lift. On I-17 a mechanic answers **Does the brake hold? → Fail** with **Slips under load**, and marks the optional cab light **N/A**. The brake is required, disallows N/A and blocks Release even with a note. Revision 2 adds **Is the guard fitted?** above the brake. Assign it, create I-18 and select **Pass** on the new question. I-17 must still show its original two questions, note and answers. I-18 must show Pass, a blank brake answer and its own row IDs. Retry returns I-17. Decision 6 covers Release.

**Print production.** Declare Job ticket’s Job class choice and owned Steps relation with Step (text), Copies (whole number) and optional Operator comment (text). From a source Booklet ticket, select only **Step / Copies** and only **Proof / 1** and **Run / 500** as starting rows. Leave the Pack row out. Proof has a job-specific Operator comment that must also be excluded. As the production lead, review the preview, publish and assign revision 1. As the coordinator, create P-41 and edit Run to **750**. In revision 2 move Copies before Step, caption it **Impressions**, put Run first with default **250** and add **Trim / 1**. Assign it and create P-42. In both editor and detail, P-41 must show **Step / Copies** with Proof 1, Run 750. P-42 must show **Impressions / Step** with 250 Run, 1 Proof, 1 Trim. Neither ticket inherits Pack or the comment. Retry returns P-41 with two rows and 750. The coordinator’s attempt to publish a revision refuses.

**School administration.** Declare Enrolment’s Intake choice and owned Contacts relation. Each contact line has a pinned role key and a scoped Person reference with a declared List picker and exact get. The registrar assigns revision 1 to Primary. The clerk sees **Guardian** and **Emergency contact** sections before selecting anyone. Use each section’s own picker to add **Jo** and **Sam**, respectively, to S-9. In revision 2 change only the Guardian caption to **Legal guardian**, retain its key and meaning, and add **Pickup delegate** with a new key in first position. Create S-10 after assignment. S-9 must still show Guardian/Jo and Emergency contact/Sam. S-10 must show Pickup delegate, Legal guardian and Emergency contact in that order, each with an empty picker in edit and a visible empty section on detail. Select one person for Pickup delegate and verify the other two sections stay empty. Retry returns S-9. A role that broadens who qualifies needs a new member key.

## Slice plan

0. **Design amendment.** The packet maps A1–A7 from the independent read to their executable tests. The owner’s two launch decisions are recorded in decision 2.
1. **Publish, assign and create atomically.** Enable a binding in Customize. Draft, preview, publish and assign revision 1. Apply the reviewed assignment in the same transaction as ordinary record creation, including the release verifier’s sample create. Exercise the create guard, seed rollback, stale previews and retries together. Prove competing publication, permissions, fail-closed replay and archived-reader admission at the declaring merge.
2. **Start and answer an inspection.** Create I-17 and I-18. Exercise the complete editor and assistant journeys, edited answers, history and the guarded-action boundary in decision 6.
3. **Use the same capability beyond questions.** Build P-41/P-42 and S-9/S-10 through tenant declarations and the same operations. Check source selection, group pickers, historical reads and contact grants. Include an instruction or proposed kit line as ordinary typed content.
