## 1. Shared conversations, channel-specific messages

Use ADR-0088's shared thread, participant and business-object link identities. CONNECT-1 is the sole writer of those rows, including the new audience kinds and membership changes. The three audience kinds are record, staff direct and staff group. Each thread belongs to one tenant, environment and company. A record thread can carry both channel kinds when CONNECT-1 resolves the same scope, eligible primary anchor and exact stored links. A channel retains its own audience, disclosure and lifecycle checks. The Discussion panel reads the in-app channel. Sharing an identity never implies access to the outbound channel's recipients, drafts or receipts. [ADR-0088 R11](ADR-0088-governed-communications-and-reminders.md#amendments-from-the-2026-11-20-fable-read)

Every shared entry point declares its channel. COMMS-1 applies channel-specific authorization before projecting thread rows, ordering or paginating lists, calculating counts, indexing or returning search results, rendering previews or resolving inbox links and copied IDs. An email participant gets only authorized email rows and email-derived metadata, including last activity and counts. Staff activity cannot move an email row or make an otherwise invisible thread appear. A staff inbox link resolves an in-app message under its current channel, company, thread and message visibility checks. Missing or unsupported channel bindings refuse by default.

COMMS-2 is the sole writer of the in-app message event table, private draft revisions and per-person thread read state. CONNECT-1 remains the sole writer of the canonical outbound message and its send machinery. In-app events carry the shared thread key and a versioned in-app channel discriminator. The separate message writer keeps free-form staff posts outside the table consumed by the protected outbound prepare and send decisions. Extending the outbound writer would put two distinct approval and delivery contracts behind the same write entry point. Duplicating threads or participants would let channel histories and membership diverge.

Every write enters a named Semantic Operation. An operation taking part in both lanes invokes their published writers within one transaction. Follow R11 across callers, workers and callbacks in order of reminder occurrence, thread, participant, message, consent, suppression and send intent. At the start of the CONNECT-1 thread step, any writer resolving or creating a record or direct thread takes the shared creation key before lookup or row locks. The key is scoped by tenant, environment and company and contains the primary record identity or the sorted direct pair, independent of channel. Take all creation keys in stable order before any thread rows. Existing-thread operations that lock by thread ID never acquire a creation key afterward. Membership changes, replies, read-state updates and draft publication take the same shared thread row lock before participant and message work. Lock multiple keys within each class in stable order, including draft, message and read-state keys within the message step. When an operation needs saved-record or company-membership fences, it takes them in stable order before R11.

The COMMS-1 worker claims a scoped outbox occurrence in a short transaction and commits the claim before acquiring any R11 locks. In a fresh transaction it takes the shared thread lock and the applicable R11 locks before the inbox row, then reconciles current state. It acknowledges the claim by lease token in another short transaction after reconciliation commits. A crash between commit and acknowledgement can replay reconciliation. No claim lock is held while waiting on the thread or inbox, and no reconciliation lock is held while acknowledging. Workers reacquire earlier locks in a fresh transaction for a new attempt.

Use the verified release fence and stored IDs, ownership and revision. Check current operation grants at admission and serialize scope changes with admission. RLS and scope-qualified keys back the gateways. All new runtime table access goes through scoped readers or narrow writers with explicit execute grants, a fixed `SECURITY DEFINER` search path of `pg_catalog, pg_temp` and qualified names. Each writer depending on READ COMMITTED checks it, including a worker or archive routine. Disjoint system and user idempotency keys keep independent worker items from blocking each other.

## 2. Record access follows every stored link

Use the released exact queries and action bindings in §8. Resolve the company from the authorized working context and stored ownership. A shared customer can have a discussion under Company A and a separate one under Company B. Links to company-owned records must all match the thread's company. Require current active company membership even when every linked record is shared. A copied thread ID or cursor confers no authority.

There is one canonical in-app discussion per company and primary record identity, independent of placement or release. The published placement selects up to seven relation bindings for that record type. Every selected binding is required and resolves from the saved record to one exact target. CONNECT-1 records the canonical anchor requirements, including the selected bindings and resolved record IDs, through governed setup for existing saved records and when new records first meet the declaration. This step runs independently of thread creation and before the panel can offer a composer. It derives the same requirements whether or not any channel already has a thread. Multiple placements for a record type must agree on the required bindings. The first poster supplies only message content and never chooses or omits the links.

Before looking up a thread or taking its creation lock, check the anchor requirements against the active declaration and saved relationships. Require current exact reads for every required record and visibility of every selected relationship. Missing, hidden, changed, archived or ineligible links give the same unavailable response whether the discussion is absent or present. A changed binding or relationship makes that anchor unavailable while it differs from the recorded requirements. V1 keeps the original links and opens no replacement discussion. The main Record page remains available under its own policy.

A person who can read only the primary record gets the same unavailable panel, with no composer, preview, count or live subscription, before, during and after another person's first post. A direct submit gets the same refusal before any thread lookup and creates no thread or message. A fully authorized reader sees an empty discussion before creation and gets a composer only with a discussion-post grant on every required record. Recheck those grants, the saved relationships and the record scope under the applicable fences at write admission. CONNECT-1 uses the scoped anchor lock to find or create the thread with exactly those links inside the first post transaction. Two authorized first posts use the same thread. Outbound preparation shares that identity only when its full link set matches. An outbound thread with different links stays separate and never produces an in-app first-post conflict.

Every thread query, pagination request, unread indicator, reply target and notification lookup re-evaluates exact record reads for **all** stored links using current policy and field disclosure. Evaluate the linked objects through the saved-record policy even if their type has no panel of its own. Render labels and eligible relations only from permitted fields. If a required binding or target cannot be read, withhold the entire thread, including existence hints, previews and counts. Participant roles or notification subscriptions confer no record access. Posting requires an independent, live discussion-post action on each linked record, even when the person can read it. It can be granted to a technician who cannot edit the underlying work order. Editing or deleting requires the corresponding write grant on all links and authorship. Reopening a stale form rechecks authority and stored targets. A record merge or archive preserves the original link for retention; ordinary record access still has to pass every stored link. An any-link rule or a participant list as an access grant would let customer-only readers see the work order's discussion.

## 3. Staff chats have explicit, company-local members

Start a direct chat with one other active staff principal in the same company. CONNECT-1 resolves a single direct thread for the unordered pair in that scope and fixes the two principal IDs for its lifetime. A group has explicit staff members, a creator who starts as manager, and an initial limit of 32 members including the creator. An active manager with the named membership-management grant adds or removes eligible staff and may appoint another active manager. A voluntary last-manager exit requires handoff. If deactivation leaves no manager, the current members can keep talking and a scoped staff-management operation can appoint a manager from those members without giving the operator access to the chat. Each read requires active company membership and current explicit thread membership. Each post also requires a current chat-post grant. Company switching changes the chat list, even for the same two people. Group names and participant labels use governed staff-directory selections. Staff threads have no business-object links in v1.

Each join records a membership interval and the last committed message sequence under the thread lock. A new or returning member sees only messages whose original creation sequence is greater than that boundary. An edit to an older message leaves its text and attachments outside their history. A reply to an older message omits the parent ID and excerpt for anyone who cannot read the parent. Removal or loss of company membership immediately ends eligibility for subsequent reads, notifications and downloads, including previously issued links. Returning to the company requires a fresh explicit group add.

A direct pair keeps the same two principal IDs when one leaves the company. The remaining active member may keep posting. Company membership reactivation opens a new interval on each existing direct pair and captures its last committed sequence in the reactivation transaction. Direct creation, posting and reactivation take the affected company-membership fences before R11, then serialize at the shared thread step. The returner sees messages created after reactivation, including messages sent before their first visit back. Earlier messages, including those posted during the absence, remain outside their visible history.

## 4. Messages, mentions, read state and retention

Append a message revision for each create, edit or delete. Assign a stable scoped message ID at creation and a unique revision/event ID and increasing sequence within that thread for each accepted event. Allocate the sequence under the shared thread lock, so a lower sequence cannot commit after a higher one. Store actor, predecessor, reply parent if any, plain text up to 4 KiB, resolved mentions, exact file references, and database evidence time. Ordinary replies target a currently visible, non-deleted message in the same thread. Authors edit or delete with the applicable write grant and expected revision. The writer serializes both operations. Deletion appends a tombstone and suppresses the text, mentions and attachments from normal reads. Database rules enforce append-only events. A bounded administrative history query requires an explicit audit grant and current thread, source and membership-window access. A retry key is bound to scope, actor, operation and canonical input digest. After a fresh authority check, a byte-equivalent committed retry returns its existing receipt. A reused key with a changed input refuses. The event, trust audit, receipt and outbox commit together. Overwriting message text would lose attribution and make a dropped response ambiguous.

The mention picker resolves up to ten distinct staff IDs from the authorized directory. For an edit, both the picker and the commit check whether each candidate can read that exact message, using its original creation sequence and the recipient's current join boundary. For a new post, check current eligibility in the conversation and recheck the resulting message visibility at commit. Refuse an ineligible selection without revealing an undiscoverable principal. Text stays escaped and literal. Typing an address or a name leaves recipient selection to the picker. For a new post, recipients are the distinct resolved mentions and the parent's author if they can still read both messages. Exclude the sender. The reply reason belongs to the original post.

COMMS-1 owns inbox rows. Its bounded, scoped worker uses the committed outbox item to find the message and recipients to reconcile, including existing rows. Under the locks in §1 it computes each recipient's reasons from the current message revision, current parent visibility and active access before writing one row per message and recipient. A delayed retry of a withdrawn mention cannot recreate its notice or increase its count. An entry uses fixed text and a governed link. List, count, preview and follow-through independently check the same current rules and suppress a row whose reasons or access ended, even before reconciliation. An inbox outage leaves the committed message visible and the occurrence retryable. Email or device notifications require a separate outward decision.

Keep a per-person read-through message creation sequence, updated only by the person's explicit **Mark read** Semantic Operation. The server issues a scope- and membership-bound mark for the authorized displayed range. Validate it against current authority and advance monotonically, so an older tab cannot reset it and a forged higher cursor cannot mark future messages. “Mark read” covers visible history through the displayed boundary. Newly visible messages above it count as unread; edits, tombstones and a member's own posts do not. Calculate unread from currently authorized messages with the COMMS-1 capped count convention. Loading a page, streaming, a prefetch or polling leaves read state alone. Automatically marking on delivery would clear unread work in background tabs.

Record a minimum retention class at first publication and retain revisions, tombstones, attribution and audit under that class. Any longer policy or legal hold wins. Where the owner has set no period, retain until a period is assigned. Retirement, loss of access, rollback and author deletion change ordinary visibility while preserving stored history. Any future disposal of retained message content requires a separate owner decision and governed retention design. Inbox archival follows COMMS-1's shorter policy and cannot remove conversation data. An automatic age-based deletion would settle retention and legal holds before the owner has ruled.

## 5. One bounded live update in the owned script

**Proposed amendment to ADR-0036 §§2 and 7.** Admit one further behaviour under §2a, with the next place in the closed list decided at merge. For an opted-in conversation region already rendered on a page, the existing CSP-hash-pinned, dependency-free script may open one authenticated, same-origin SSE stream on that page's scope and request the same server-rendered region for catch-up. The stream emits only a fixed invalidate signal after a governed check, or a fixed heartbeat. It carries no text, names, identifiers, counts, ordering numbers or permission material. The fragment is a bounded read-only same-origin GET of that named region. The composer uses ordinary forms and the existing Task presentation where needed. The same CSP keeps `connect-src 'self'` and a single script hash.

Connect, invalidation, reconnect, polling and manual refresh all use one refresh queue per conversation region. Allow one current request and one pending refresh, coalescing further triggers. Start each request from the last applied continuation. Cancel any outstanding request and invalidate its generation before changing scope or switching between push and fallback. Apply a response only if its generation and page, region and scope are still current. An authorized refresh updates the transcript and read status while preserving focus and unsent text. An unavailable response clears the transcript, cursor, counts, reply IDs and excerpts, selected mentions, file previews and other server-supplied composer data. Disable stale post, reply, download and Mark read controls. Preserve only the user's typed text as an inert local draft until a fresh authorized render supplies controls.

Native navigation supplies full access but cannot show a new message within seconds while staff are typing. SSR and ordinary forms ship in slice 1, before the enhancement. WebSockets would add a bidirectional protocol for a one-way update while the existing forms already cover writes. A streaming transaction or putting message bodies in SSE would make every connection a long-lived disclosure decision. A faster polling loop as the primary path would query during every quiet interval.

The host uses one dedicated PostgreSQL LISTEN connection per web process as a wake-up hint after commit. Use a fixed payload free of business data. The message event table is the durable source. Coalesce wakes and recheck each admitted stream's authorized view and durable progress once per second at the admitted load. The periodic check recovers missed hints and listener restarts. Emit invalidations for changes to that reader's view, including the first post on an empty authorized record anchor. Release each read transaction and pool connection between checks. At the response boundary revalidate the live session, active release fence, grant epoch and relevant audience and record eligibility. Discard results computed before an observed change. On a definitive refusal, close the stream and have the fragment endpoint return the same unavailable region for unsupported, revoked and unknown targets. Passive stream and polling reads do not extend interactive sign-in. Traffic is private and non-cacheable, rejects cross-origin subscription and is tied to the authorized page's tenant, environment, company, principal, release and thread or record anchor. [ADR-0071](ADR-0071-read-decisions-are-live-per-request-writes-per-call.md) · [ADR-0036 §2a](ADR-0036-minimum-client-capability.md#2a-what-the-set-is-closed-over--scoped-2026-08-08-after-a-doctrine-review) · [ADR-0081](ADR-0081-staff-sign-in-and-decision-authority.md)

Initial limits per web process are 64 streams across at most 32 active topics, two streams per signed-in principal and a 60-second stream lifetime. Release a slot on disconnect, deadline or a slow reader exceeding the output bound. Heartbeats keep idle paths open. One per-process budget covers stream admission and reconnect, authorization scans and all live fragments including polling. Charge each attempt before governed database work. Allow 128 starts per second and eight concurrent bounded work units, with 64 starts and four slots reserved for stream scans. Keep the live work pool within its own connection allocation so it cannot exhaust the connections reserved for ordinary Record reads and posts. Skipped scans coalesce into one check per stream and close the stream if it has gone two seconds without a successful check. When a request exceeds the budget or a stream cap, return HTTP 429 with `Retry-After: 2` before running the query. On a stream error or buffering timeout, close the stream client and start paced fragment refreshes while the page is visible. Use jittered backoff starting at two seconds for polling and reconnect, and honor retry delays from fragment responses on both paths. Use monotonic time for timers and budgets. With script off the SSR page has **Refresh discussion**, paged history, ordinary post and reply forms, a server-rendered mention picker and Mark read.

The small-server acceptance run uses one web process behind the served proxy, 64 open streams on 32 topics and two committed posts per second spread across those topics for five minutes. Measure from commit to each eligible second browser's applied transcript. Require p95 at or below two seconds and count missing updates as misses. Exercise listener restart, reconnect and proxy buffering through the same served route. Then drive reconnect and polling attempts at twice the per-second live budget. Verify bounded query starts, concurrency and 429 responses while twenty ordinary Record reads and twenty posts each complete within five seconds with the correct results.

On initial connect, reconnect and fallback poll, fetch from the last **applied** server continuation or start again with a fresh authorized snapshot. Seal an opaque continuation to recipient, scope, release fence, target, membership interval and page window. Each page orders events by thread sequence, considers up to 200 indexed candidates under a bounded provider budget, and admits up to 50 authorized changes. Fold changes by stable message ID and latest visible revision when rendering the window. Repeated hints or pages have at-least-once delivery semantics, and replacing the region is idempotent by message/revision identity and window. An edit or tombstone updates the displayed message if in the window and otherwise appears when its history page is refreshed. Advance the continuation only after its rendered response is applied. A stale continuation or a backlog beyond bounded catch-up triggers an explicit SSR snapshot reset with normal history navigation. Only show rows visible under current membership and record policies. The wire representation conceals hidden event counts and sequence gaps. This avoids skipping a late commit by timestamp or trying to recover from a transient browser event ID.

## 6. The assistant drafts privately; a person posts

The assistant summarizes through the same bounded Semantic Queries and returns the answer to the requesting person. Treat text, filenames and mentions as data, including any instructions inside them. A named Semantic Operation may save an inert private draft for that person and thread. Require current thread reads and draft-write authority. Bind the draft to the exact set of source revisions actually supplied to the drafter. The shareable draft path admits only ordinary messages from that thread, with no record-field merges or audit history. Recheck those sources before returning an answer or serving a saved draft. At publication every source must be visible to the post's audience. In either staff chat kind, compare source creation sequences against every current member's join boundary. Otherwise keep the draft private. A staff member reviews and explicitly posts the exact final draft revision through the ordinary post operation. It rechecks the thread, current posting rights, source eligibility and resolved mentions or files against the active fence. Reserve publication to an authenticated human action. COMMS-2 is a staff channel. A customer send goes through COMMS-1 and CONNECT-1's existing declared sources and exact, human-confirmed envelope, retaining consent and SIGNIN-1 proof checks. Auto-posting a summary or offering SQL, network, secrets, filesystem or provider access would bypass those authority and review boundaries. ## 7. Photos and files pin DOCS-1 versions

Use exact DOCS-1 version handles and digests via its governed link and publication operations. For an existing file, require current read and DOCS-1 attach authority on its governing source and enforce DOCS-1 scope and disclosure rules. For both existing files and composer uploads, require current destination read, the applicable post or edit authority, and an independent destination attach grant. In a record discussion the exact read and `discussion.attach` action must pass on the primary and every required linked record. In direct and group chat, require current thread membership and the conversation-scoped `staffChat.attach` grant in the active company. Check destination grants when offering the action and again at write admission. Text-post authority alone gives no attachment authority.

For a photo or file uploaded from a composer, extend ADR-0078's admitted governing-target contract to the scoped conversation message, including for a standalone chat. Stage bytes privately under the draft owner's scoped upload grant and current destination authority. DOCS-1 scans before the post transaction. At publication recheck the staged upload's owner and scope, scan result and the destination grants under the active fence. Publish the clean version and its exact conversation reference atomically with the message revision. Conversation writes take the applicable R11 locks through message before DOCS-1 publication or reference locks, in DOCS-1's own order. Standalone DOCS-1 readers and retention routines do their conversation checks as scoped reads and never take an R11 write lock while holding a DOCS-1 lock. Reference creation and purge serialize on the same DOCS-1 version/blob protection. The writer has a bounded, idempotent retry after failure. Before enabling the feature, prove the lock order against publication and purge and enforce existing quotas and download bounds.

Ordinary listing, preview and download resolve the exact reference on the message's currently visible revision and recheck current thread, message and DOCS-1 source, field and scan policy. A download URL binds scope, message ID, revision ID, reference ID and immutable version ID. Check all of them, byte-read authority and the current policy epoch before the first byte. An edit gives the new visible revision its own URLs. Replacing a photo or tombstoning a message makes its old chat URL unavailable even to someone still able to read the thread and the original document. The original document retains its own governed access. References in retained revisions, including superseded and deleted messages, still block DOCS-1 purge.
