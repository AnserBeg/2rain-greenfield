# ADR-0090. Governed record discussions and staff chat

**2026-11-21 · Proposed for the independent Fable read.** The owner approved the COMMS-2 goal. The decisions below become executable after the design read and disposition. See the [COMMS-2 packet](../execution/packets/COMMS-2.md).

A dispatcher discussing work order 418 can bring the related customer and asset into the same conversation. A technician who can see all three can read the discussion and reply if allowed to post. A clerk who can see the customer alone still sees the customer page. Separately, two staff can start a direct chat, and dispatch can start an explicit group for a shift. The rentals ERP survey (§D, **Staff messaging**) supplies the examples of starting a direct or group conversation and exchanging text and photos. The shared Communication capability supplies those jobs inside this ERP. ## 1. Shared conversations, channel-specific messages

Use ADR-0088's shared thread, participant and business-object link identities. CONNECT-1 is the sole writer of those rows, including the new audience kinds and membership changes. The three audience kinds are record, staff direct and staff group. Each thread belongs to one tenant, environment and company. A record thread can carry both channel kinds when CONNECT-1 resolves the same scope, eligible primary anchor and exact stored links. A channel retains its own audience, disclosure and lifecycle checks. The Discussion panel reads the in-app channel. Sharing an identity never implies access to the outbound channel's recipients, drafts or receipts. [ADR-0088 R11](ADR-0088-governed-communications-and-reminders.md#amendments-from-the-2026-11-20-fable-read)

COMMS-2 is the sole writer of the in-app message event table, private draft revisions and per-person thread read state. CONNECT-1 remains the sole writer of the canonical outbound message and its send machinery. In-app events carry the shared thread key and a versioned in-app channel discriminator. The separate message writer keeps free-form staff posts outside the table consumed by the protected outbound prepare and send decisions. Extending the outbound writer would put two distinct approval and delivery contracts behind the same write entry point. Duplicating threads or participants would let channel histories and membership diverge.

Every write enters a named Semantic Operation. An operation taking part in both lanes invokes their published writers within one transaction. Follow R11 across callers, workers and callbacks in order of reminder occurrence, thread, participant, message, consent, suppression and send intent. Lock multiple keys within a class in a stable order. Membership changes, replies, read-state updates and draft publication take the same shared thread lock before participant and message work. Order draft, message and read-state keys within the message step. Workers reacquire earlier locks in a fresh transaction for a new attempt. Use the verified release fence and stored IDs, ownership and revision; check current operation grants at admission. RLS and scope-qualified keys back the gateways. All new runtime table access goes through scoped readers or narrow writers with explicit execute grants, a fixed `SECURITY DEFINER` search path of `pg_catalog, pg_temp` and qualified names. Each writer depending on READ COMMITTED checks it, including a worker or archive routine. Serialize scope changes with admission. Disjoint system and user idempotency keys keep independent worker items from blocking each other.

## 2. Record access follows every stored link

For each participating record type, compile the existing saved-record exact query and explicit discussion action bindings from the release. A related binding names the target's exact query and discussion action policy, even when the target has no panel. The platform supplies these bindings for built-in and tenant-generated record types through the same Customize path. Resolve the company from the authorized working context and stored ownership. A shared customer can have a discussion under Company A and a separate one under Company B. Links to company-owned records must all match the thread's company. Require current active company membership even when every linked record is shared. A copied thread ID or cursor confers no authority.

One Discussion panel resolves one canonical in-app thread per company and primary record identity, independently of the placement ID or release. It opens empty with a composer when appropriate before a thread exists. The first authorized post can atomically create it, with the primary anchor and up to seven distinct related links selected through admitted, currently readable relation bindings. Require an exact authorized read and a discussion-post action on **each** link, and refuse a hidden relationship or archived or ineligible target. CONNECT-1 serializes first creation on the scoped anchor and checks its stored link set. A concurrent first post with different links must review the thread it actually found. Treat the link set as fixed in v1. Changing it after a message could silently change the audience of everything already said.

Every thread query, pagination request, unread indicator, reply target and notification lookup re-evaluates exact record reads for **all** stored links using current policy and field disclosure. Evaluate the linked objects through the saved-record policy even if their type has no panel of its own. Render labels and eligible relations only from permitted fields. If a required binding or target cannot be read, withhold the entire thread, including existence hints, previews and counts. Participant roles or notification subscriptions confer no record access. Posting requires an independent, live discussion-post action on each linked record, even when the person can read it. It can be granted to a technician who cannot edit the underlying work order. Editing or deleting requires the corresponding write grant on all links and authorship. Reopening a stale form rechecks authority and stored targets. A record merge or archive preserves the original link for retention; ordinary record access still has to pass every stored link. An any-link rule or a participant list as an access grant would let customer-only readers see the work order's discussion.

## 3. Staff chats have explicit, company-local members

Start a direct chat with one other active staff principal in the same company. CONNECT-1 resolves a single direct thread for the unordered pair in that scope and refuses member changes on it. A group has explicit staff members, a creator who starts as manager, and an initial limit of 32 members including the creator. An active manager with the named membership-management grant adds or removes eligible staff and may appoint another active manager. A voluntary last-manager exit requires handoff. If deactivation leaves no manager, the current members can keep talking and a scoped staff-management operation can appoint a manager from those members without giving the operator access to the chat. Each read requires active company membership and current explicit thread membership. Each post also requires a current chat-post grant. Company switching changes the chat list, even for the same two people. Group names and participant labels use governed staff-directory selections. Staff threads have no business-object links in v1.

Each group join records an immutable membership interval and the current message boundary under the thread lock. A new or returning member starts with messages created after that boundary. An edit to an older message stays outside their history, and a reply to an older message omits the parent ID and excerpt for anyone who cannot read the parent. Removal immediately ends eligibility for all subsequent reads, notifications and downloads, including previously issued links. An organization-wide directory or a chat accessible by unqualified group ID would disclose across companies. Granting earlier history on join would disclose messages addressed to a different audience.

## 4. Messages, mentions, read state and retention

Append a message revision for each create, edit or delete. Assign a stable scoped message ID at creation and a unique revision/event ID and increasing sequence within that thread for each accepted event. Allocate the sequence under the shared thread lock, so a lower sequence cannot commit after a higher one. Store actor, predecessor, reply parent if any, plain text up to 4 KiB, resolved mentions, exact file references, and database evidence time. Ordinary replies target a currently visible, non-deleted message in the same thread. Authors edit or delete with the applicable write grant and expected revision. The writer serializes both operations. Deletion appends a tombstone and suppresses the text, mentions and attachments from normal reads. Database rules enforce append-only events. A bounded administrative history query requires an explicit audit grant and current thread, source and membership-window access. A retry key is bound to scope, actor, operation and canonical input digest. After a fresh authority check, a byte-equivalent committed retry returns its existing receipt. A reused key with a changed input refuses. The event, trust audit, receipt and outbox commit together. Overwriting message text would lose attribution and make a dropped response ambiguous.

The mention picker resolves up to ten distinct staff IDs from the authorized directory against this exact conversation. At commit recheck active company membership and each recipient's read access. Refuse an ineligible selection without revealing an undiscoverable principal. Text stays escaped and literal. Typing an address or a name leaves recipient selection to the picker. For a new post, the deduplicated recipients are resolved mentions and the author of the parent if eligible, excluding the sender. An edit may add a newly mentioned recipient for a message they can see. The reply reason belongs to the original post. COMMS-1 owns inbox rows. Its bounded, scoped worker takes the committed trust outbox item, rechecks the recorded recipients and reasons, and writes or reconciles one entry per message and recipient through the COMMS-1 operation. The entry uses fixed text and a governed link. If all its reasons are withdrawn by an edit, parent deletion or message tombstone, or the recipient loses access, reads and counts suppress it. Recheck for rows, counts, previews and follow-through. An inbox outage leaves the committed message visible and the occurrence retryable. Idempotent delivery converges on the same inbox row. Email or device notifications would move data outside this governed inbox and require a separate outward decision.

Keep a per-person read-through message creation sequence, updated only by the person's explicit **Mark read** Semantic Operation. The server issues a scope- and membership-bound mark for the authorized displayed range. Validate it against current authority and advance monotonically, so an older tab cannot reset it and a forged higher cursor cannot mark future messages. “Mark read” covers visible history through the displayed boundary. Newly visible messages above it count as unread; edits, tombstones and a member's own posts do not. Calculate unread from currently authorized messages with the COMMS-1 capped count convention. Loading a page, streaming, a prefetch or polling leaves read state alone. Automatically marking on delivery would clear unread work in background tabs.

Record a minimum retention class at first publication and retain revisions, tombstones, attribution and audit under that class. Any longer policy or legal hold wins. Where the owner has set no period, retain until a period is assigned. Retirement, loss of access, rollback and author deletion change ordinary visibility while preserving stored history. Any future disposal of retained message content requires a separate owner decision and governed retention design. Inbox archival follows COMMS-1's shorter policy and cannot remove conversation data. An automatic age-based deletion would settle retention and legal holds before the owner has ruled.

## 5. One bounded live update in the owned script

**Proposed amendment to ADR-0036 §§2 and 7.** Admit one further behaviour under §2a, with the next place in the closed list decided at merge. For an opted-in conversation region already rendered on a page, the existing CSP-hash-pinned, dependency-free script may open one authenticated, same-origin SSE stream on that page's scope and request the same server-rendered region for catch-up. The stream emits only a fixed invalidate signal after a governed check, or a fixed heartbeat. It carries no text, names, identifiers, counts, ordering numbers or permission material. The fragment is a bounded read-only same-origin GET of that named region. The script applies only the server-rendered transcript and read-status region, preserves focus and any unsent composer, and drops responses for an older page generation or scope. The composer uses ordinary forms and the existing Task presentation where needed. The same CSP keeps `connect-src 'self'` and a single script hash.

Native navigation supplies full access but cannot show a new message within seconds while staff are typing. SSR and ordinary forms ship in slice 1, before the enhancement. WebSockets would add a bidirectional protocol for a one-way update while the existing forms already cover writes. A streaming transaction or putting message bodies in SSE would make every connection a long-lived disclosure decision. A faster polling loop as the primary path would query during every quiet interval.

The host uses one dedicated PostgreSQL LISTEN connection per web process as a wake-up hint after commit. Use a fixed payload free of business data. The message event table is the durable source. Coalesce wakes, and sample active topics on a bounded cadence (at least once per second at the admitted load) so missed or duplicate hints, a listener restart and a web-process restart recover. Each candidate invalidation and each refresh runs the authorized conversation query. Emit invalidations for changes to the reader's authorized view, including the first post on an empty authorized record anchor. Release each read transaction and pool connection between checks. At the response boundary revalidate the live session, active release fence, grant epoch and relevant audience/record eligibility. Discard results computed before an observed change. On a definitive refusal, close the stream and have the fragment endpoint return the same unavailable region for unsupported, revoked and unknown targets. The script clears the transcript on that response. Passive stream and polling reads do not extend interactive sign-in. Traffic is private and non-cacheable, rejects cross-origin subscription and is tied to the authorized page's tenant, environment, company, principal, release and thread or record anchor. [ADR-0071](ADR-0071-read-decisions-are-live-per-request-writes-per-call.md) · [ADR-0036 §2a](ADR-0036-minimum-client-capability.md#2a-what-the-set-is-closed-over--scoped-2026-08-08-after-a-doctrine-review) · [ADR-0081](ADR-0081-staff-sign-in-and-decision-authority.md)

Initial limits are 64 concurrent streams per web process and two per signed-in principal on that process, a 60-second stream lifetime, and bounded worker/query concurrency and writer backpressure. Release a slot on disconnect, deadline or a slow reader exceeding the output bound. Heartbeats keep idle paths open. If push is refused, cut off or buffered, retry with backoff and jitter and use paced refreshes while the page is visible, initially every two seconds with at most one in flight. Honor overload retry hints and back off when the server cannot keep up. Use monotonic time for timers and budgets. With script off the SSR page has **Refresh discussion**, paged history, ordinary post and reply forms, a server-rendered mention picker, and Mark read. The live acceptance target is p95 from commit to another open, authorized transcript updating within two seconds at the admitted load. Observe it over the actual served route including proxy buffering, rollout/restart and saturated admission.

On initial connect, reconnect and fallback poll, fetch from the last **applied** server continuation or start again with a fresh authorized snapshot. Seal an opaque continuation to recipient, scope, release fence, target, membership interval and page window. Each page orders events by thread sequence, considers up to 200 indexed candidates under a bounded provider budget, and admits up to 50 authorized changes. Fold changes by stable message ID and latest visible revision when rendering the window. Repeated hints or pages have at-least-once delivery semantics, and replacing the region is idempotent by message/revision identity and window. An edit or tombstone updates the displayed message if in the window and otherwise appears when its history page is refreshed. Advance the continuation only after its rendered response is applied. A stale continuation or a backlog beyond bounded catch-up triggers an explicit SSR snapshot reset with normal history navigation. Only show rows visible under current membership and record policies. The wire representation conceals hidden event counts and sequence gaps. This avoids skipping a late commit by timestamp or trying to recover from a transient browser event ID.

## 6. The assistant drafts privately; a person posts

The assistant summarizes through the same bounded Semantic Queries and returns the answer to the requesting person. Treat text, filenames and mentions as data, including any instructions inside them. A named Semantic Operation may save an inert private draft for that person and thread. Require current thread reads and draft-write authority. Bind the draft to the exact set of source revisions actually supplied to the drafter. The shareable draft path admits only ordinary messages from that thread, with no record-field merges or audit history. Recheck those sources before returning an answer or serving a saved draft. At publication every source must be visible to the post's audience. In a group, compare source creation sequences against every current member's join boundary. Otherwise keep the draft private. A staff member reviews and explicitly posts the exact final draft revision through the ordinary post operation. It rechecks the thread, current posting rights, source eligibility and resolved mentions or files against the active fence. Reserve publication to an authenticated human action. COMMS-2 is a staff channel. A customer send goes through COMMS-1 and CONNECT-1's existing declared sources and exact, human-confirmed envelope, retaining consent and SIGNIN-1 proof checks. Auto-posting a summary or offering SQL, network, secrets, filesystem or provider access would bypass those authority and review boundaries. ## 7. Photos and files pin DOCS-1 versions

Use exact DOCS-1 version handles and digests via its governed link and publication operations. For an existing document, require DOCS-1 attach and read authority on the governing source, permission to post in the destination, and same-scope disclosure before linking. At every listing, preview or download intersect current message/thread visibility with all DOCS-1 source, field, scan and byte-read checks. File names and thumbnails follow the same rule. A removed member, hidden source field, deleted message or quarantine makes the attachment unavailable at the respective entry points. A document independently available from its original record stays governed there.

For a photo or file uploaded from a composer, extend ADR-0078's admitted governing-target contract to the scoped conversation message, including for a standalone chat. Stage bytes privately under the draft owner's scoped upload grant. DOCS-1 scans before the post transaction and then publishes the clean version and its conversation reference atomically with the message. Conversation writes take the applicable R11 locks through message before DOCS-1 publication or reference locks, in DOCS-1's own order. Standalone DOCS-1 readers and retention routines do their conversation checks as scoped reads and never take an R11 write lock while holding a DOCS-1 lock. Reference creation and purge serialize on the same DOCS-1 version/blob protection. The writer has a bounded, idempotent retry after failure. Before enabling the feature, prove this lock order against publication and purge and enforce the existing quota and download bounds. Downloads use the exact immutable version. A replacement appends a message revision with its exact reference. References in retained revisions, including superseded and deleted messages, still block DOCS-1 purge. A temporary URL or a record picked as a surrogate for a chat would broaden the file's visibility or lose exact version and retention evidence. ## 8. Customize and the AI emit the same change set

Place **Discussion** as one grammar-owned block in the existing Record detail `sections` slot, with an isolated data failure inside the block and an ordinary compact stack. Use List, Record and Task for the staff chat list, thread and create/manage actions. Put its role-shaped entry under existing navigation grouping. Those choices preserve the page landmarks, activity rail, composer and keyboard focus, including at 390 px. Customize offers the same block for a tenant-generated or an eligible built-in saved Record. A new archetype or a renderer branch keyed to Work Order would make this capability harder to reuse.

Use four closed, versioned, add-only patch kinds in slice order. Each carries a stable logical ID, revision, predecessor and active or retired disposition. The panel and staff workspace pin the selected owning Surface and type or workspace, slot where applicable, query and operation IDs and their relevant contracts. The live and attachment members pin the specific installed panel or workspace ID and their versioned capability binding. Attachments pin the admitted DOCS-1 governing-target contract. Staff chat authoring offers live updates in the same ordered change set once available, with the choice shown in the diff. The active revision alone resolves current bindings; a successor may retire a placement and its dependent members together. A release rollback restores presentation and retained data subject to current authority. Content publishing follows current grants and the active release, independent of permission to draft a layout.

Map a removed query, relation or surface to `RETIRED_TARGET`, an incompatible contract to `INCOMPATIBLE_TYPE`, and a company-scope change to `INCOMPATIBLE_SCOPE`, naming the patch, member and affected ID. Add each kind to the independent replay allowlist with exact historical reproduction, a compatible replay and a real conflict preserving the verified source. ## After the design read

1. **Record threads.** Land after CONNECT-1's shared thread, participant and link writer contract and COMMS-1's inbox writer are available. Exercise first-party and tenant records, concurrent first posts, multi-link authorization, mentions and replies, revisions, read state, assistant drafts and Customize. Exercise the ordinary forms with scripting off. The internal path uses the staff session and established operation grants.
2. **Live delivery.** Apply the ADR-0036 amendment after the SSR path exists. Exercise missed hints, reconnects, duplicate and reordered responses, revoked grants mid-refresh, scope change, overload, polling and the actual two-second target. Keep the transcript and composer usable with and without scripting.
3. **Staff direct and group chat.** Exercise duplicate pair creation, company switching, explicit adds and removals, bounded membership, join and rejoin history, membership races and a revoked live stream. The staff entry needs the trusted staff identity contract.
4. **Photos and files.** Admit DOCS-1's conversation governing target and exact version link, then exercise a mobile photo, an attached PDF, a source grant change, replaced versions, quarantine, revocation on an open chat, loss of a submit response and purge refusal on a retained revision.

Future executable evidence uses actual runtime roles and two companies in one tenant and environment. Give the denied actor the right record owner identity or a real overlapping staff membership so company scope alone decides. For each silent-harm assertion, remove the corresponding guard independently and observe the authorized response, stored rows or external send ledger fail the claim.

## Owner questions at the design checkpoint

- **Group history on joining or rejoining.** Recommend starting from the latest message at each join. Staff can share earlier context deliberately within each recipient's access.
- **Retention defaults.** Recommend retaining message revisions and their version references until a company retention policy is approved. Keep user deletion as a tombstone and preserve legal holds.
- **Shared customers and assets.** Recommend a separate discussion per company on a shared master, with business links screened in that company. Staff who work for both companies switch context to see each discussion.
