## Goal and split boundary

Extend the accepted G3-P3 posting capability to post an Inventory transfer
without forking its transaction protocol. This packet is the transfer half of
the former G3-P4. Stock-count correction is split to G3-P4b because its
`stock_count` and `stock_count_line` evidence entities require a superseding
ADR and dependency-set v4 event.

Transfer needs neither event. The accepted definition already freezes
`transfer` as an inventory transaction type and posting role, and the v3
dependency set already authorizes the transaction, complete line set, movement,
configuration, period-lock, trust, and receipt accesses the implementation
uses.

## Shared posting protocol

`PostgresInventoryPostingService` now has two closed entry points,
`postAdjustment` and `postTransfer`, which validate their variant and enter one
private posting transaction. The shared transaction retains G3-P3's binding
order:

1. validate the command and actor before borrowing a connection;
2. `BEGIN`;
3. set the 15,000 ms transaction-local `lock_timeout` with
   `set_config(..., true)`;
4. pass every affected identity to the accepted stock serializer, before any
   business read or savepoint;
5. take the request-key lock, validate the active release/configuration, and
   row-lock the header, base-unit rows, and period-lock row with
   `FOR NO KEY UPDATE`;
6. bind the complete draft line set, evaluate serialized negative stock using
   the frozen global order, and enforce reason, approval, backdate, and period
   lock;
7. append every movement and conditionally transition the same draft under one
   post-lock savepoint; and
8. read back movements, append linked trust/outbox/receipt evidence, and commit
   all effects together.

The service continues to call `acquireStockIdentityLocks` unchanged. A transfer
line contributes its source and destination stock identities to that one call;
the serializer removes duplicates and acquires the physical keys in its ruled
total order.

## Balanced transfer representation

A persisted transfer line has one positive exact-base-unit quantity plus
distinct `fromLocationId` and `toLocationId`. The posting service derives two
immutable movements:

- source: the exact negative quantity at `fromLocationId`, source line
  `<line>:out`, posting role `transfer`; and
- destination: the exact positive quantity at `toLocationId`, source line
  `<line>:in`, posting role `transfer`.

The derived source-line suffixes keep the two natural effects distinct while
preserving the accepted database key exactly as
`(source_type, source_id, source_line, revision, posting_role)`. Both movements
name the same transaction and persisted transaction line, share one trusted
`recordedAt`, and can commit only with the draft transition and trust evidence.
Quantity must be strictly positive, locations must differ, and the complete
persisted line must match the command.

The transfer role consumes its own release-recorded configuration entries:
default `codeOnly` reason, transfer approval threshold, the legal-entity
negative-stock mode, maximum backdate, and period lock. No transfer dial is
ambient or preflight-only.

## Decisive controls

All controls extend `test/postgres/inventory-posting.test.ts`, so the accepted
CI-invoked PostgreSQL suite and executed-file reachability already own the
file.

| Control | Observed verdict |
|---|---|
| Balanced transfer and replay | A `+5` source seed followed by a quantity-2 transfer commits exactly `-2` and `+2`, both `transfer`/`EA`, leaving source `3` and destination `2`. Request and natural-effect retries return the original two movements and trust links. Same-key/different-quantity fails typed. |
| Partial-transfer rollback | A test trigger rejects the second side only after a non-transactional sequence proves the first side INSERT executed. The sequence advances once, while movement/effect/trust counts remain unchanged and the draft remains revision 1 `draft`. |
| Transfer dials | Blank code fails `INVENTORY_TRANSFER_REASON_REQUIRED`; default code-only with null narrative succeeds; quantity above the transfer threshold fails `INVENTORY_TRANSFER_APPROVAL_REQUIRED` without an approving human and succeeds with one; a closed period rejects with no movement. |
| Opposite real transfers | Two concurrent A→B and B→A transfers use opposite caller identity order. A query proxy pauses each backend after its first successful NSST acquisition. Correct production ordering exposes one granted common first key and one ungranted waiter, then both transfers commit without `40P01`. If serializer ordering is removed, both callers reach the pause holding different first keys; release constructs the real deadlock and the control fails. |
| Persisted-plus-planned order | A same-instant planned debit has `sourceId=a`; a persisted credit on the same stock identity has `sourceId=z`. Frozen sorting evaluates the debit first and rejects negative stock. Deleting `.toSorted(compareInventoryMovementOrderEntries)` at `inventory-posting-service.ts:1633` changes the verdict to commit. |
| `movementId` final branch | A pair is identical in `effectiveAt`, `recordedAt`, `sourceType`, `sourceId`, `sourceLine`, and `postingRole`, with only reversed `movementId` values. Deleting the `movementId` comparison at `inventory-posting-service.ts:1230` preserves input order and reverses the assertion. The former two duplicated comparators are consolidated into this one production function, used by both planned ordering (`:457`) and serialized negative-stock ordering (`:1633`). |

The last control is deliberately not G3-P3's
`assertSameInstantMovementIdTieBreak`. That older control pins migration 0015's
base-unit binding diagnostic order, not the frozen posting tuple.
