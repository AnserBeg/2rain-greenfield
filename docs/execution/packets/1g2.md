## Outcome

[ADR-0024](../../decisions/ADR-0024-exact-compatible-release-reversal.md) rules
rollback as an exact compatible pointer reversal. The composed application can now select
the immediate prior immutable application release only when the activation that established
the current pointer generation is the verified forward activation of that exact edge and its
persisted recovery class permits reversal.

The reverse journey uses the existing production path:

1. resolve exact B and immediate predecessor A from the validated compiled lineage;
2. load the immutable A -> B swap, verification, approval, roots, and transition receipt at
   the current pointer fence;
3. refuse before preparation unless that receipt is either no-storage or reversible;
4. persist a canonical B -> A no-storage preparation whose facts bind the forward evidence;
5. obtain a fresh human approval for the current pointer/fence and immutable A;
6. activate through `PostgresReleaseActivationService`, exact compare-and-swap, read-back,
   active verification, history, and outbox; and
7. assert `active_release_pointer_exact_swap` remains enabled around the swap and after the
   final pointer read.

The composition root, approval service, and activation service all invoke the same reverse
policy. A caller cannot bypass it by constructing a preparation outside the composition
root: approval rejects a skipped ancestor and a separately admitted release identity for A,
while activation revalidates immediacy before it can swap. Unrelated release pairs remain in
the release kernel's existing generic forward-activation domain; the reverse policy does not
grant them rollback authority.

`apps/api` exposes the explicit operator selection as
`NORTH_STAR_ROLLBACK_RELEASE_ROOT`. Absence means the existing latest-lineage behavior;
presence requests the governed rollback and is not a verification, approval, or activation
bypass.

## Storage consequence

Rollback does not unmaterialize B's storage. The reverse receipt is
`NO_STORAGE_TRANSITION` because B -> A performs no compensating DDL or DML; eligibility is
separately bound to the verified A -> B receipt. Current compiled storage transitions are
additive and record `REVERSIBLE` only after exact-pair and coexistence checks. A therefore
runs against the compatible physical superset.

The positive control makes this concrete rather than relying on the classification. It
compiles B with a new nullable Party column, executes the real v2 materializer path, and
observes that:

- the row created under A has the same `ctid` and `xmin` under B, after rollback to A, and
  after replay to B;
- every physical value present before the transition is unchanged;
- the new column remains physically present and null while A is active; and
- A still reads the row through a fresh semantic query gateway.

## Test it yourself

Prerequisite: Docker is running. From a clean checkout, run:

```bash
node --import tsx --test --test-concurrency=1 \
  --test-name-pattern='advances an existing deployment' \
  test/postgres/composed-application.test.ts
```

In about one minute, expect `1 / 1` passing. That single test compiles and verifies B,
materializes a real column, observes the forward-only refusal, activates B -> A through a
fresh approval, reads A's original row with unchanged physical identity, and replays the
same v2 A -> B edge. The disposable PostgreSQL container is removed automatically.

For the running product, `NORTH_STAR_ROLLBACK_RELEASE_ROOT=<A releaseRoot>` is the explicit
operator request when the checked-in artifact contains A followed by active B. The ready
line reports A's root after the governed activation. Omitting the variable on the next
restart replays the exact A -> B edge and reports B again.

## Known limits

- Policy v1 reverses exactly one immediate edge whose current pointer generation was
  established by that forward activation. It does not skip releases or chain reversals
  after a prior reverse activation.
- Rollback is neither schema restoration nor business-transaction reversal. Additive
  storage remains, and any future compensating storage family needs a separate canonical,
  compiler, provider, and migration decision.
- `IRREVERSIBLE` / `FORWARD_RECOVERY_ONLY` transitions remain serviceable but cannot roll
  back. Their only admitted remedy is a governed forward recovery release.
- The local composition root still provisions stable local approver/executor identities;
  this packet does not turn demo identity provisioning into a production operator service.
