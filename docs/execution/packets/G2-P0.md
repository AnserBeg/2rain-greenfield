# G2-P0 — G2 stage cut and parallelization map

Status: active
Tier: Mechanical

## Goal and scope

Cut G2 into tracked, user-selectable packets that together deliver Party,
Catalog, and Location as the first complete master-data walking slices. Route
every G2 doctrine obligation to an executable packet, establish the Party
slice as the reusable template, and permit Catalog and Location to fan out
only after their shared contracts and UI behavior are frozen.

Owned paths:

- `docs/execution/packets/G2-P0.md`
- `docs/execution/ledger.md`
- `docs/execution/doctrine-coverage.md`

Out of scope: product code, migrations, canonical/compiler/runtime changes,
trust-substrate implementation, domain modules, UI components, durable jobs,
new ADR decisions, or any claim that a G2 packet or the G2 stage has passed.
No G2 implementation packet is started or status-advanced by this cut.

Runnable exit: documentation-only changes leave the accepted G1 runtime and
all repository gates unchanged. The packet ends with a selectable G2 graph,
not a business-module implementation or stage-completion claim.

## Planning authorities

- Plan sections 5.8-5.10 define the one-definition/all-projections module
  contract and Q0/O0/storage algebras. Sections 6 and 11.5 define Party,
  Catalog, Location, shared table behavior, durable import, and Gate G2.
- Plan sections 8.5-8.6 and the pinned `ux-grammar` skill define the closed
  surface vocabulary, desktop/compact transformations, accessibility checks,
  and the conformance suite that begins gating stages at G2.
- Plan section 13 requires `T-01` before `D-01` and requires consolidated
  module projections (`R-07`) before a walking slice can count as complete.
- ADR-0004 owns trusted tenant/request identity; ADR-0008 owns the Semantic
  Query and Operation gateways; ADR-0010 owns invocation evidence,
  transactional change documents, lifecycle archive/restore, and outbox
  coupling. Modules consume these authorities and may not create peers.
- The doctrine-coverage maintenance rule requires concrete G2 owners for
  storage validity/transition safety, full surface conformance, trust/audit,
  no hard delete, resolver outcomes, same-DTO channel parity, and cross-tenant
  relation rejection.

## Parallelization map

```text
Accepted G1
  -> G2-P1 Freeze E: trust transaction substrate
      -> [bounded storage-topology debate]
      -> G2-P2 Freeze F: projections + transition safety + conformance
          -> G2-P3 Freeze G: Party, first complete walking-slice template
              -> G2-P4 Freeze H: surface conformance
                  -> G2-P5 Freeze I: shared table behavior
                      ├── lane C: G2-P6 Catalog ──┐
                      └── lane L: G2-P7 Location ┤
                                                  v
                              G2-P8 durable import (serial convergence)
                                  -> G2-P9 consolidated G2 evidence
```

Lane C and lane L may author module-local definitions, generated artifacts,
bindings, fixtures, and focused tests concurrently in isolated worktrees.
Their path leases are disjoint. PostgreSQL migration application and provider
tests run in reserved serial windows, never at the same time. Reviews are also
serial even when writers ran concurrently; each frozen SHA receives its own
fresh naive chartered review.

The P2 storage decision must preserve this property. The intended contract is
that module-owned canonical definitions lower to compiler-owned additive
migration artifacts without hand-editing a central registry. If P2 instead
requires either lane to edit a root SQL migration, `db/schema.snapshot.json`,
a shared registry, a root manifest/lockfile, or a frozen E-I contract, the
fan-out is no longer parallel-safe: stop and create a serial bridge/amend this
cut before launching both writers.

## Serialized resources and lane ownership

| Resource | Serial owner/rule |
|---|---|
| Shared canonical/compiler/runtime/query/operation/surface/report/agent contracts | Frozen by G2-P1 through G2-P5; later changes require one serial bridge |
| Generated/shared registries and application package composition | Orchestrator-serialized; lanes contribute module-local definitions only |
| Root `package.json`, `pnpm-lock.yaml`, workspace/export manifests | Orchestrator-serialized setup or bridge before fan-out |
| Root database migrations and `db/schema.snapshot.json` | One packet/substep at a time; no concurrent writes or migration runs |
| PostgreSQL provider tests, browser/dev servers, worker tests, and full/heavy suites | One scheduled runner at a time |
| Reviews, evidence documents, ledger/doctrine updates, and integration to `main` | One frozen SHA and one integration checkpoint at a time |

## Debate assessment

G2-P0 itself does not warrant debate: it is a mechanical routing cut reviewed
against the decisive charter below.

G2-P2 does warrant one bounded pre-build debate. The plan fixes the required
semantics but leaves a genuine storage-topology choice: how dedicated
first-party typed tables and/or generated typed storage are represented in a
compiled transition; how additive migrations, data-validity/backfill truth,
and old/new active releases coexist in a shared database; and how preparation
evidence binds activation without forcing Catalog and Location to edit shared
schema paths. The debate is limited to that topology and must end in one
versioned contract/ADR or a stop. It may not reopen PostgreSQL as sole launch
provider, one release authority, additive-only launch evolution, no EAV/JSON
escape hatch, tenant isolation, or human-controlled activation.

No other G2 packet needs pre-build debate. G2-P1 implements ratified
ADR-0010; Party, Catalog, and Location compose the ratified G1 contracts;
surface grammar is fixed by plan §8.5-8.6; table behavior and import semantics
are explicit in §11.5. Their uncertainty is implementation risk handled by
targeted charters and deterministic gates, not an open design space.
