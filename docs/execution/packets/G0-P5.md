## Goal and scope

Establish the first runnable observability slice: structured JSON logs,
deterministic request correlation and W3C trace propagation, bounded request
and dependency metrics, error evidence, real `/healthz` liveness, and `/readyz`
readiness that reflects PostgreSQL availability. Capture the focused test,
metrics, health, and error/log evidence as a retained CI artifact.

Out of scope: production observability-vendor wiring, SLO dashboards and alert

or dependency scanning implementation. The last concern remains a separately
tracked Mechanical G0-P5c packet rather than being silently absorbed here.

## Threat model and review charter

- Gates must be green at the frozen candidate.
- Threat model: accidental missing or incorrect correlation/trace propagation
  and readiness that does not reflect real PostgreSQL dependency state,
  introduced by honest developers or AI writers. Adversarial input is not in
  scope.
- In scope: `/healthz` remains live independently of PostgreSQL; `/readyz`
  returns ready with reachable PostgreSQL and HTTP 503 after that dependency is
  stopped; structured logs carry the same correlation and trace identity as
  response headers throughout one request; metrics and redacted error evidence
  cover both readiness outcomes; CI retains deterministic focused evidence.
- Out of scope: vendor agents/exporters, dashboards/SLOs, hostile identifiers,
  high-cardinality product labels, and future tenant/release/query/operation
  fields that do not exist yet.
- Decisive questions: can readiness remain green after PostgreSQL is killed;
  can an ordinary request completion or readiness failure lose or change its
  correlation/trace identity; and can CI pass without producing readable
  health, metrics, and redacted error/log evidence?

## Runnable exit

The dedicated web observability server can be started with a PostgreSQL URL;
an operator can call `/healthz`, `/readyz`, and `/metrics`, stop PostgreSQL,
observe readiness turn red while liveness stays green, and correlate response
headers with structured logs and deterministic metric/error evidence.

## Outcome

The new `@north-star/observability` package provides one immutable request
observation context, structured JSON logging with sorted fields and redacted
error evidence, and bounded Prometheus request/readiness/error counters. An
incoming correlation ID and W3C `traceparent` are created once or propagated
unchanged through response headers, readiness errors, and completion logs.

The PostgreSQL provider owns a private `SELECT 1` readiness probe. The dedicated
Node HTTP host under `apps/web/observability/` exposes `/healthz`, `/readyz`, and
`/metrics`: liveness is dependency-independent, while readiness returns HTTP
503 with redacted evidence when PostgreSQL is unavailable. No framework or
external observability dependency was added.

CI runs the focused evidence suite only after the existing PostgreSQL and
browser jobs, then retains TAP output, health status JSON, Prometheus metrics,
and structured error/request logs for seven days. G0-P5c now explicitly tracks
the still-deferred dependency and secret scan rather than widening this packet.

## Test it yourself

This focused command starts real PostgreSQL and the HTTP host, calls `/healthz`
and `/readyz`, stops PostgreSQL, calls both endpoints again, and writes the
correlated evidence:

```bash
cd /tmp/2rain-greenfield-g0-p5
g0p5_evidence_dir=$(mktemp -d /tmp/g0-p5-evidence-XXXXXX)
OBSERVABILITY_EVIDENCE_DIR="$g0p5_evidence_dir" \
  node --import tsx --test test/postgres/observability-health.test.ts
sed -n '1,120p' "$g0p5_evidence_dir/health-evidence.json"
sed -n '1,160p' "$g0p5_evidence_dir/metrics.prom"
sed -n '1,12p' "$g0p5_evidence_dir/structured-logs.ndjson"
```

Expect the test to pass. `health-evidence.json` shows health 200 before and
after the database stop, readiness 200 then 503, plus fixed correlation/trace
IDs. Metrics show one ready, one not-ready, and one redacted error count. Every
log line carries those same IDs; the readiness error has only the stable code
and error type, never the provider message or a payload.
