# G1-P0 — G1 stage cut and parallelization map

Status: accepted
Tier: Mechanical
Frozen candidate: `69b6ff87c28ca3638ac7958efce7acfa011b43a0`

## Goal and scope

Cut G1 into tracked, user-selectable packets that together prove the release
kernel and empty compiled application shell. Assign every G1 doctrine
obligation to an executable packet, freeze the shared contracts before
parallel work, and identify which paths and integration steps remain serial.

Owned paths:

- `docs/execution/packets/G1-P0.md`
- `docs/execution/ledger.md`
- `docs/execution/doctrine-coverage.md`
- `learnings.md`

Out of scope: implementation of canonical schemas, compiler, release storage,
activation, request pinning, gateways, SurfaceRuntime, UI components, CI,
observability, or any claim that G1 or G0 as a whole has passed. G0-P1b and
G0-P5 are external parallel work owned by another agent and are not started,
edited, or status-advanced here.

Runnable exit: documentation-only changes leave the accepted P4b runtime and
all repository gates unchanged; the packet ends with a selectable ledger graph,
not an implementation or stage-completion claim.

## Planning authorities

- Plan sections 5.3-5.10, 8.5-8.6, 11.4, and 13 define the G1 outcome and
  executable work sequence.
- ADR-0001 owns `AppPackageRevision`, `TenantRelease`, and
  `ActiveReleasePointer`; ADR-0006 owns `ReleaseApproval`; ADR-0004 owns trusted
  request context and `RequestRuntimeView`; ADR-0008 owns the two semantic
  gateways.
- The runtime authority map remains the one-owner check. Compiler artifacts,
  views, gateways, and surfaces consume authorities; none becomes a peer
  source of truth.
- The doctrine-coverage maintenance rule requires tracked G1 enforcement for
  compiler determinism, human-controlled activation, trusted request pinning,
  gateway ownership, and the UX grammar skill-pin/surface seam.

## Shared-contract freeze sequence

| Freeze | Owning packet | Must be immutable for downstream lanes |
|---|---|---|
| A — Canonical language | G1-P1 | Branded canonical IDs; object-kind discriminants and schema versions; package/module/entity/field/state/surface/query/operation/permission/assertion/storage/capability schemas; closed `SurfaceDefinition` archetype/slot/status vocabulary; Query/Operation definition envelopes |
| B — Compiler output | G1-P2 | Canonical serialization and hash input; deterministic diagnostic shape/order; `CompiledArtifactSet` projection keys; bootstrap package fixture; release-diff and capability-report envelopes |
| C — Release records and ports | G1-P3 | Immutable revision/release shapes; tenant/environment composite keys; release repository ports; pointer/approval/activation-attempt contract shapes consumed by P4 and P5 |
| D — Request consumer envelope | G1-P5 | Immutable `RequestRuntimeView`; pinned catalog/query/operation/surface/agent projection interfaces; runtime package exports consumed without modification by P6 and P7 |

After a freeze is accepted, a downstream packet consumes it. Changing a
frozen shared contract is a serial bridge packet or explicit upstream reopen,
never an uncoordinated edit from a parallel lane.

## Packet breakdown

### G1-P1 — Canonical schemas

- Outcome: stable canonical IDs and versioned minimal schemas for every object
  family named by G1, including the closed surface vocabulary and typed
  query/operation contracts.
- Planned implementation lease: `packages/canonical-model/**`, canonical
  portions of `packages/test-contracts/**`, `test/unit/canonical-model/**`, and
  its salvage admission record. Package manifest/lockfile changes serialize.
- Gates: schema/property and round-trip tests, invalid kind/version/reference
  negatives, typecheck, boundary checks, and full canonical-model tests.
- Checkpoint: inspect a minimal valid package and copy-paste negative fixtures;
  unknown kinds, versions, references, slots, and status roles must fail.

### G1-P2 — Deterministic compiler

- Outcome: parse, normalize, order, resolve, typecheck, hash, compile, diff, and
  emit the bootstrap package's complete artifact set byte-stably.
- Planned implementation lease: `packages/compiler/**`, `test/compiler/**`,
  `test/fixtures/g1/**`, golden snapshots, and its REFERENCE/RE-EXPRESS salvage
  records. It consumes Freeze A and creates Freeze B.
- Gates: double compile byte equality, golden/hash tests, deterministic
  diagnostics, isolated candidate compile, release diff, unknown target/
  component/capability negatives, typecheck, and boundaries.
- Checkpoint: compile twice and compare hashes/artifacts; then run the bounded
  negative fixture set and inspect the bootstrap capability report.

### G1-P3 — Immutable release persistence

- Outcome: tenant-qualified immutable `AppPackageRevision` and
  `TenantRelease` records persist one complete desired state and one complete
  compiler artifact set without overlay or content-hash identity shortcuts.
- Planned implementation lease: the next ordered release-record migration,
  `db/schema.snapshot.json`, release repository/provider files, release-record
  contracts, `test/postgres/releases.test.ts`, and its salvage record.
- Gates: schema drift, empty/upgrade migrations, immutability, tenant and
  environment collision tests, content-hash-versus-minted-ID tests, typecheck,
  boundaries, and PostgreSQL suite.
- Checkpoint: persist identical content for two tenants and observe distinct
  revision/release identities with immutable artifacts.

### G1-P4a — activation contracts and approval substrate

- Outcome: precreated tenant/environment pointer rows, a real versioned
  approver-authority substrate, immutable exact approval/attempt/preparation/
  outcome contracts, and a trusted server-side approval service.
- Planned implementation lease: migration 0004, `db/schema.snapshot.json`,
  release-activation contracts/provider files, focused PostgreSQL and
  architecture tests, and packet/doctrine records.
- Gates: pointer backfill/creation, exact `+1` fence trigger, trusted-context
  `UPDATE` RLS, append-only grants/rules, decisive-outcome uniqueness,
  authority-version bumps, server-recomputed binding, maker-checker, expiry,
  first activation, typecheck, boundaries, and the full PostgreSQL suite.
- Checkpoint: create a real approval from canonical records for a null pointer,
  exercise constraint negatives, and prove no callable activation exists.

### G1-P4b — CAS activation and rollback

- Outcome: exact human `ReleaseApproval`, single activation-attempt claim,
  policy recheck, stale-pointer CAS refusal, read-back, history, active
  verification, retry/resume, replay refusal, and compatible rollback to a
  prior immutable release.
- Planned implementation lease: the next ordered activation-kernel migration,
  `db/schema.snapshot.json`, release activation runtime/provider files,
  activation/rollback PostgreSQL tests, and PORT/RE-EXPRESS salvage records.
- Gates: approval binding, maker-checker/current-policy hook, competing CAS,
  attempt uniqueness/resumption, failed-approval replay refusal, read-back,
  history, compatible rollback, recovery, no ambient pointer, typecheck,
  boundaries, and PostgreSQL suite.
- Checkpoint: race two expected-pointer updates, prove one loses, rollback with
  a new approval, and inspect unchanged immutable release history.

### G1-P5 — RequestRuntimeView and pinning

- Outcome: authenticated entry reads one tenant/environment pointer once,
  loads one immutable release, and constructs one frozen `RequestRuntimeView`
  passed explicitly to consumers without default tenant, release, or global
  fallback.
- Planned implementation lease: `packages/runtime/src/request-runtime-view.ts`,
  the API request-entry adapter, request-pinning integration tests, and the
  serialized runtime export manifest. It consumes Freeze C and creates Freeze
  D without changing P4b trusted identity ownership.
- Gates: one-request/one-release tests, activation-during-request stability,
  stale-plan result, two tenants on different releases, absent-pointer and
  ambient-fallback negatives, pool-context suite, typecheck, and boundaries.
- Checkpoint: hold a request open while another activation succeeds; the open
  request keeps its first release and the next request sees the new release.

### G1-P6 — Empty semantic gateways

- Outcome: empty `SemanticQueryGateway` and `SemanticOperationGateway`
  skeletons resolve only definitions from the pinned view, invoke current
  auth/policy hooks, preserve plan/execute and idempotency seams, and return
  typed unsupported/error envelopes without table, handler, or tool bypasses.
- Planned implementation lease: dedicated semantic gateway runtime files, API
  adapters, and `test/integration/semantic-gateways.test.ts`; it must not edit
  Freeze D or add business-domain handlers.
- Gates: missing/unknown definition, wrong release, unauthorized, stale,
  unconfirmed, idempotency-hook, typed-error, direct-access, boundary, and
  typecheck tests.
- Checkpoint: call empty Q/O definitions through the public adapters and see
  typed fail-closed results; direct table/physical-handler inputs must fail.

### G1-P7 — SurfaceRuntime shell

- Outcome: the signed-in shell, navigation, home/setup surface, component
  registry, error boundary, and unsupported-capability diagnostic render only
  from the pinned compiled `SurfaceDefinition`; no hardcoded navigation,
  compatibility manifest, overlay, or bespoke ordinary screen exists.
- Planned implementation lease: `apps/web/**`, the dedicated SurfaceRuntime
  runtime file, component-registry files, browser shell tests, and referenced
  surface salvage records. Web manifest/lockfile setup is serialized before
  parallel implementation starts.
- Gates: build, browser shell journey, compiled-navigation assertion,
  unsupported diagnostic, error boundary, accessibility smoke, no-overlay/
  no-bespoke seam, typecheck, and boundaries.
- Checkpoint: open the empty signed-in shell, navigate the compiled home
  surface, and trigger the unsupported-capability/error paths.

### G1-P8 — UX grammar pin and SurfaceRuntime seam

- Outcome: formally adopt the portable `ux-grammar` draft with valid
  top-level skill frontmatter, pin it to plan sections 8.5-8.6 and the closed
  surface vocabulary, and make the G1 compiled-SurfaceRuntime-only seam fail
  CI. Full five-archetype/mobile conformance remains a tracked G2 obligation.
- Planned implementation lease: `.agents/skills/ux-grammar/SKILL.md`, a
  skill-guidance contract test, a G1 surface-seam architecture test, and any
  dedicated developer-tooling scanner file; no product surface code.
- Gates: skill loader/shape test, plan/skill/code pin test, compiled-runtime
  seam negatives, architecture suite, format, and typecheck.
- Checkpoint: read the adopted skill, then mutate a temporary fixture with a
  bespoke screen or vocabulary drift and observe a stable failing rule.

### G1-P9 — Consolidated G1 gate

- Outcome: run the accepted combined G1 state from a clean checkout and record
  the exact plan §11.4 evidence without adding product logic.
- Planned implementation lease: one G1 gate evidence document and its packet
  record; ledger/doctrine updates remain serialized orchestration paths.
- Gates: clean frozen install, schema drift, boundaries, compiler goldens,
  release/activation/pinning/gateway tests, browser shell, skill/seam tests,
  full build/test, and the complete plan §11.4 gate checklist.
- Checkpoint: follow one under-ten-minute smoke that compiles, activates,
  pins, renders, rolls back, and confirms another tenant remains unchanged.

```text
External G0 lanes (other agent; no G1-P0 edits)
  G0-P1b CI/hygiene ───────────────┐
  G0-P5 observability/evidence ────┴─ integrate only at serialized checkpoints

G1 serial spine
  G1-P1 Freeze A
      -> G1-P2 Freeze B
          -> G1-P3 Freeze C + release DB schema
              -> G1-P4a approval contracts/substrate (no activation)
                  -> G1-P4b activation DB/CAS + crash reconciler
                      -> G1-P5 Freeze D
                      ├── lane Q: G1-P6 empty semantic gateways ─────┐
                      └── lane S: G1-P7 SurfaceRuntime shell         │
                                      -> lane G: G1-P8 skill/seam ───┤
                                                                    v

```

Lane Q and lane S may run concurrently in isolated worktrees after Freeze D.
Lane G begins after P7 exposes the SurfaceRuntime seam and may overlap the tail
of lane Q. Reviewers and heavy suites remain serial even for parallel-safe
writers.
