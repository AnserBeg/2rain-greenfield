# G3-P2b-4 — Runtime storage-payload-family admission

Status: evidence ready

Tier: Critical

Base: `301d8e67a1e29dd4600fdbc4fe21d09fc4115b4c`

Branch: `packet/g3-p2b-4`

## Scope and defect

The generic module interpreter previously admitted only
`northstar.storage-target-payload/v1` by comparing every persisted version stamp
to one compile-time constant. The compiler had already emitted v2 for
entity-owned targets, and G3-P2b-1 adds v3 for partitioned inventory facts. A
valid non-v1 release therefore failed with
`MODULE_STORAGE_PROJECTION_MISSING` before any semantic operation reached
PostgreSQL.

This is the version-from-artifact defect at a fifth production layer. The fix
does not replace one local constant with a local list. The compiler protocol owns
one frozen `SUPPORTED_STORAGE_TARGET_PAYLOAD_VERSIONS` family, exported through
the compiler package. The interpreter consumes that family and additionally
requires the release reference, projection manifest, and projection payload to
declare the same admitted version. An unknown version still fails closed.

The packet also carries the period-lock privilege correction found by
G3-P2b-1: a generic update changes both `closedThrough` and the optimistic
`revision`, so granting UPDATE on only the first column causes PostgreSQL
`42501`. The correction grants exactly those two columns and does not widen
period-lock mutation authority beyond them.

## Evidence split

Evidence is intentionally split across the integration boundary:

1. **Layer 1, accepted-base independent:** synthetic artifact chains exercise
   the production admission function. Every compiler-owned version is admitted;
   an unknown version and each inconsistent stamp fail with typed diagnostics.
2. **Layer 2, after accepted G3-P2b-1 integration:** Party, Catalog, Location,
   and Inventory are compiled together from their production definitions. The
   resulting v3 Inventory target is persisted, its fourteen managed relations
   are materialized, and `advance_period_lock` executes through the real
   Semantic Operation gateway under the runtime database role. A separate
   administrator read observes the persisted value and revision.

No unreviewed FIX work is merged merely to make Layer 2 available.

## Executed reds

### The former single-version check rejects v2

With the production validator deliberately left on its former v1 equality, the
synthetic v2 chain reached the validator and printed:

```text
G3-P2b-4 pre-fix red: version=northstar.storage-target-payload/v2 code=MODULE_STORAGE_PROJECTION_MISSING message=pinned release has no supported storage target
```

The unchanged test then failed at `assert.doesNotThrow` for v2. Switching only
the validator to the compiler-owned family made the same test pass, while the
unknown `northstar.storage-target-payload/v999` control continued to require
`MODULE_STORAGE_PROJECTION_MISSING`.

### The former period-lock grant reaches PostgreSQL and fails

With family admission already active but the accepted G3-P2b-1 grant unchanged,
the real gateway operation reached the provider. A temporary diagnostic at the
existing provider-error translation boundary recorded the underlying SQLSTATE;
the diagnostic was removed before commit. The retained output is:

```text
# G3-P2b-4 period-lock pre-grant provider red: sqlstate=42501
# Subtest: a real v3 inventory period lock executes through the generic operation gateway
not ok 1 - a real v3 inventory period lock executes through the generic operation gateway
  failureType: 'testCodeFailure'
  error: 'module provider rejected the operation'
  code: 'MODULE_PROVIDER_FAILURE'
1..1
# pass 0
# fail 1
```

This observes both sides of the provider boundary: PostgreSQL denied the
multi-column UPDATE with `42501`, while the public interpreter correctly kept
the physical SQLSTATE behind its typed `MODULE_PROVIDER_FAILURE` error.

The final materializer grants UPDATE on exactly the compiled
`closedThroughColumn` and `optimisticRevision.column`. Its drift model expects
the same two columns. The real operation then returned revision 2 and
`2026-07-28T23:59:59.999Z`; a separate query observed both values in
PostgreSQL. `information_schema.column_privileges` returned exactly those two
UPDATE columns. The existing transition control now proves revision can change
while an unrelated `archived_at` UPDATE still receives `42501`.

### The unknown-version rejection remains load-bearing

The permanent family test submits
`northstar.storage-target-payload/v999` consistently at all three artifact
levels and still requires `MODULE_STORAGE_PROJECTION_MISSING`. Separate controls
make the projection manifest disagree with its release reference and the
payload disagree with both; they require
`MODULE_STORAGE_PROJECTION_MALFORMED` and
`MODULE_STORAGE_TARGET_MALFORMED`, respectively. Family admission therefore is
not a wildcard or a no-op.

## Recorded limits

- The operation uses the same candidate-view shape as release semantic
  verification: persisted candidate artifacts, production runtime projections,
  an issued trusted request view, the real gateway, and the real provider. It
  does not claim approval or active-pointer activation. Full semantic candidate
  verification currently collides with Inventory's already-provisioned default
  legal entity while synthesizing another fixture; that unrelated verification
  behavior is not repaired or presented as evidence here.
- G3-P2b-1 owns the v3 schema and Inventory physical contract. This packet
  merged only its accepted integration and changed no v3 storage semantics.
- The family remains closed. A future payload version is admitted by extending
  the compiler-owned family once; the interpreter does not change.
- The gateway intentionally translates physical SQLSTATE values to its stable
  typed provider error. The temporary negative-control diagnostic observed
  `42501` without widening that product error surface.
