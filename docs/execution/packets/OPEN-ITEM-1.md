CI tier: pending

**Claims.**
1. Declarations: an open item may name `void {operationId, transitionId}` (the machine's open -> void transition); an application type may name `unapplyOperationId`. Both refuse unless person-confirmed core operations of their capability (`open_item_void`, `open_item_unapply`) reading back the item or application type.
2. Ledgers: every apply, void and unapply binding carries, for each end, the item type's ledger: every application type naming that type at that end. An item's applied is the live sum across ALL of them, so a credit note and a receipt settle one fee note under one balance; s1's single-type gate refused that (`appliedDiverged`).
3. Void: grant, policy epoch, counterparty lock, item row (apply's order); refused unless the revision holds and the item is open with stored applied 0 and a live ledger sum 0. Writes state void and balance 0 (nothing owed; total and number kept). A void racing an apply: exactly one succeeds.
4. Unapply: input recordId is the SOURCE, arguments name application IDs. Targets and company come from the STORED lines (prepare and again under the locks); counterparty, items sorted by record ID, then the lines FOR NO KEY UPDATE (after the items, as apply's inserts are). Refused for a line not live, of another source, or of another company. Lines are archived (kept); amounts return to source and targets; state from figures (applied 0 -> open, balance 0 -> settled, else partially settled); the ledger gate re-reads every touched item.
5. Owed notes: (a) a required link on an application type other than its two ends refuses at compile; (c) named reds for currencyMissing, policyChanged, isolationUnsupported and directionMismatch, and compile refusals asserted by reason; (d) a policy version the live policy did not issue refuses `openItem.policyUnverifiable` (fail closed, not the interpreter's skip). Direction is now checked in prepare, on the binding, before any read.

**Rule 17.** (a) Withdrawing a document nothing is applied to, and withdrawing an amount moved between two documents: general to any open item. (b) Unchanged users: rental and clinic invoices voided before payment, a bounced payment unapplied, a supplier credit note applied to bills, a refund against a credit. (c) Narrower: void only from open (a zero-total item issued straight to settled cannot be voided); unapply takes whole lines (no partial unapply of one line).

**Decisions.**
- Unapply archives the application line instead of writing a reversing line (note §4). A reversing line needs a negative amount (amendment 5 forbids it) or a new declared role; s1's sums already count only live lines. The reversal fact is the line's archived_at and revision, the source's change document and the invocation (metadata lists the unapplied lines).
- Credit notes are the existing role on a separate credit-side type with its own series (owner: credits are separate documents), applied through their own application type; no new role.
- STOP (rule 16) on per-target change documents: `trust_business_change_documents` is UNIQUE on (tenant, environment, invocation_id), the invocation row holds one `change_document_id`, and `AcceptedMutationCommand` carries one `change`. A change document per target is a trust-substrate change (Critical, needs a design read) or a core-owned per-target evidence table. Not built; targets still ride the source's change in metadata.
- Not built (remains): note (b), a Customize member declaring the role (rule 12: drafting support and eval cases), which also makes an application type's name optional; the event consumer.

**Controls** (`test/evidence/OPEN-ITEM-1-s2.expected-red.json`, 6 silent-harm entries): void balance, unapply state, policy changed, isolation, currency missing, direction. Void-only-from-open, unapply's own-source and live-once checks each have a second layer (state plus applied; prepare plus the locked re-read; the ledger gate), so they have reds but no single-layer control.

**Test it yourself.** Read the s2 subtests in `test/postgres/open-items.test.ts`: a 15.00 fee note voided keeps FN-number and owes 0.00; a 100.00 note part-paid 30.00 by a receipt takes a 50.00 credit note CN-000001 (applied 80.00, balance 20.00), and a second 30.00 credit note is refused; unapplying the credit note brings it back to 30.00 / 70.00.

## Slice 1 · Draft -> issue (numbered per company) -> one payment applied, two companies — record

**Claims.**
1. Two optional v6 keys (`openItems`, `openItemApplications`; emitted only when declared, first-party and demo releases byte-identical). An open item names `direction` (receivable/payable), `side` (debit/credit), counterparty relation, create-only currency, number, optional document and due dates, subtotal, total, applied, balance, either a parent-scoped line relation with its amount or an entered amount, a five-state map over its own machine, and its issue operation and transition.
2. `FieldNumbering` gains `assignOn {transitionId}` and `scope` (`legalEntity` only with `assignOn`): the field is then optional, carries no business key, leaves every input and every create's `assignedFields`.
3. Compile refusals (`bindOpenItems`, canonical-model): a role field missing or of the wrong type; amounts of different scales; a core-written figure that is required, a rollup or derived (amendment 2); a currency not create-only; a counterparty that is not a required many-to-one link; both or neither of lines and amount; a line relation that is not `parentScopedChild` (amendment 3); a state map not on the item's own machine or not starting in draft; an issue transition not draft -> open; ANY `transitionStateEffect` on the item's machine (amendment 7); a generic update, archive or restore that is not exactly draft-only, or a line-bearing item with no update (amendments 1, 3); a number not assigned on this issue per company (amendment 6); an issue or apply operation that is not person-confirmed, of the open-item capability, reading back its type; an application across directions (amendment 4), across counterparty master types, at another scale, or whose type has any generic operation; an open-item operation no declaration names.
4. Projections: core-written figures (number, subtotal, total, applied, balance) leave every create and update input (amendment 1); issue and apply operations carry a compiled `openItem` binding (field and relation IDs, states, number series, scale), parsed by the gateway, which refuses a binding on any other operation and an open-item operation without one.
5. Issue (`northstar.openitem:capability.open_item_issue`): grant consumed first; header `FOR NO KEY UPDATE`; live lines summed (no line locked after the header); refused when not draft, the revision moved, no lines, an absent or negative amount, the line-set digest (`openItemLineSetDigest`: live line IDs and revisions) or the previewed total differs (amendment 3); number drawn LAST from the per-company counter; total = subtotal = balance, applied 0, state open (settled at zero).
6. Apply (`...open_item_apply`): input recordId is the SOURCE; lines name caller-minted application IDs, targets and amounts. Company from the STORED source and every target (refused `companyMismatch` before policy, amendment 9); counterparty advisory lock in the core's namespace, then every item sorted by record ID; refused unless source and targets are open or partially settled (amendment 5), same counterparty and currency, amounts positive at the item scale, within each target's and the source's balance. Application rows inserted (append-only, `recordCreations`); applied/balance/state written with the revision CAS; then each touched item's applied is re-read against the sum of its live application lines under the held locks (`appliedDiverged`).
7. Migration 0076 (provisional 0075): `open_item_approval_grants` (0074's shape plus the consuming transaction), attest (approval issuer only), consume (runtime; stale fence, spent, expired, mismatch refused), the deferred receipt check; `open_item_number_counters` (forward-only) and `open_item_issued_numbers` (unique per company and series, one number per record); `open_item_allocate_number` refuses unless an issue grant for THIS record was consumed in THIS transaction, so no runtime-role caller can burn a number and open a gap. RLS forced, PUBLIC revoked.
8. Release verification plans no create probe for core-written figures or for an application type (no create exists: the materialized-state-field precedent).

**Rule 17.** (a) A document a counterparty owes or is owed, issued from a draft, numbered per company and series, settled by amounts moved between opposite sides of one direction. (b) Unchanged users: rental and subscription invoices, clinic visit charges, contractor and supplier bills, credit notes, customer payments and refunds, hotel folios. (c) Narrower on purpose (thin slice): issue and apply only (void, unapply, credit notes, tax, posting, supersede are s2-s9); one application type per item; exact decimals with a stored currency (no fixed-currency money); no Customize member (the fixture declares the role as data); the grant table is a third copy (HARDENING-PASS debt).

**Decisions.**
- Refusals live in the canonical-model binder (the line-totals pattern) rather than conformance.ts; the compiler calls it once.
- The binding rides an operation-level key (the `booking` precedent), not the input-contract parser the note pointed at.
- Owed, not built: void (so R3's void-racing-apply has no test), unapply, a change document per target of an N-row apply (the source's change carries the targets in metadata), the "no human" refusal red, the event consumer. The preceding-binary proof (rule 21c) is listed in FIRST-TENANT-OWED.md.

**Controls** (`test/evidence/OPEN-ITEM-1-s1.expected-red.json`, 8 silent-harm entries, all killed in evidence run 46151671258): protected figures, number per company, line set, target balance under a race, source open, currency, counterparty, grant per request. A ninth (a create assigning the issue number) was dropped: that mutation fails loudly, because the gateway's assignedFields parser refuses the issue-only keys and the release does not install, so it guards no silent harm. Company isolation is held by two layers (prepare and the locked re-check), so it has a red but no single-layer control.

**Fix round (Mythos pre-merge review FIX, findings 1-6; first execution of the rung).** (1) A number assigned at a transition with no open-item declaration now refuses (the check ran after the no-declaration return). (2) The currency role must be required, and apply refuses a source with no stored currency. (3) After the grant, the transaction holds the policy epoch FOR SHARE and refuses `openItem.policyChanged` unless it equals the gateway's decision. (4) `open_item_consume_grant` refuses any isolation but READ COMMITTED (the line freeze depends on it). (5) Apply re-checks direction and sides at run time. (6) The view service's rule-consumption flag excludes open items. The rung's first execution (local, under the lock) found every successful apply refused at the application insert: Customize makes a record type's name required, and the core writes only company, ends and amount; the binder now refuses any other required field on an application type, and the fixture declares the name optional. Compile refusals are asserted as "not compiled" (a refused compile reports `failed`). A targeted Mythos check of these changes follows (rule 24.2).
