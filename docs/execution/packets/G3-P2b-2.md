## Goal and boundary

This packet supplies the concurrency mechanism that every future posting
transaction must acquire before it evaluates stock state. It implements the
already-ruled explicit lock point; it does not choose between locking and SSI.

The boundary is deliberately narrow:

- the serializer accepts an already-open dedicated PostgreSQL transaction and
  neither starts nor completes it;
- it reads and writes no movement, transaction, configuration, period-lock,
  reservation, balance-cache, or idempotency row;
- it exposes no posting service or movement insert path;
- it performs no negative-stock preflight and no locked-row re-read; and
- G3-P3 remains the sole owner of the posting transaction and all business
  evaluation performed inside it. G5-P1 remains the reservation owner.

## Ruled mechanism

`acquireStockIdentityLocks` uses only the blocking transaction-scoped overload:

```sql
SELECT pg_advisory_xact_lock($1::integer, $2::integer)
```

It never uses a session-scoped advisory lock, `pg_try_*`, `hashtext`, or a
retry loop. Transaction completion is the only release path. A savepoint at
entry is a transaction-contract assertion: PostgreSQL rejects autocommit use
with `25P01`, preventing a transaction-scoped lock from becoming a
statement-scoped silent no-op. The savepoint reads no business state and is not
a negative-stock preflight.

### Reserved namespace

The first integer is the reserved constant `0x4e535354`, the ASCII tag `NSST`
(North Star stock). PostgreSQL's two-integer advisory-lock family is disjoint
from the one-bigint family. The migration and materializer paths named in the
mechanism ruling use the one-bigint family, so they cannot collide with this
namespace even if all underlying bits match. No other two-integer advisory-lock
caller exists in the repository; `NSST` is reserved here exclusively for stock
identities.

The second integer is the signed first word of SHA-256 over the versioned,
unambiguous scoped identity. A 32-bit collision can conservatively serialize
unrelated stock identities; it cannot let equal identities bypass each other.
The physical lock key, rather than an SQL `hashtext` result, is stable across
PostgreSQL installations and process versions.

Tenant and environment qualify the ratified v1 tuple
`(legalEntityId, itemId, locationId)` for locking. They do not become stock
dimensions. They prevent two unrelated database scopes with coincident UUID
values from contending on the database-global advisory key.

### Deterministic total order

Every call validates canonical lowercase UUIDs, removes exact duplicate scoped
identities, derives every physical int4 key, and acquires locks in this single
order:

1. ascending signed physical identity key; then
2. ascending canonical tuple `(tenantId, environmentId, legalEntityId, itemId,
   locationId)` as the collision tie-breaker.

Physical-key order is primary deliberately. Ordering only the semantic tuples
would permit two rare hash-collision pairs to map to opposite physical orders
and recreate a deadlock. With the physical order first, every transaction that
shares advisory keys acquires those keys in the same total order. Distinct
identities that collide merely take the same transaction lock more than once.

### Partition independence

Business period, effective time, physical table, and physical partition are
intentionally absent from the lock identity. Partitioning is the placement of
an immutable movement fact; it is not a stock dimension and does not split the
authority whose state the posting transaction evaluates. The lock therefore
serializes the scoped stock-identity value across every tenant-business-period
partition.

If a command is ever allowed to carry facts for one stock identity into more
than one business-period partition, the protocol does not change: duplicate
scoped identities collapse to one advisory key, so that command acquires the
identity once. A command carrying several identities across any number of
partitions still orders only the physical identity keys by the total rule
above. The pure control proves that changing incidental `businessPeriod`
metadata leaves the same identity plan byte-for-byte unchanged.

Adding business period to the advisory key would be a correctness defect, not
an optimization. Two postings for the same scoped stock identity but different
periods could then run their serialized-state decisions concurrently. Partition
pruning may change the cost of G3-P3's eventual aggregate read; it cannot change
which lock guards that read.

## Authored proof controls

`test/postgres/stock-serializer.test.ts` contains four direct controls. The
PostgreSQL cases require G3-P2b-1's real movement relation; they do not
manufacture a substitute table.

| Control | Observed fact when executed |
|---|---|
| Same stock identity | Transaction A owns the granted advisory lock while transaction B exposes the same `pg_locks` row with `granted = false`. Only A can read the movement aggregate; after A commits, B acquires, reads, and commits. This observes waiting rather than inferring it from interleaving or elapsed wall time. |
| Unordered transfer red | Two transactions directly acquire A then B and B then A after each owns its first lock. PostgreSQL must reject exactly one second acquisition with `40P01 deadlock_detected`. This is the ordering-removed executed red. |
| Ordered transfer restoration | The production serializer receives the same transfer pair in opposite caller orders. Both plans expose the same physical-key order; one transaction visibly waits on the common first key, then proceeds after the winner commits, with no `40P01`. |
| Real, scoped lock | `pg_locks` observes the stock lock with `objsubid = 2` while a bit-identical one-bigint lock is simultaneously granted with `objsubid = 1`. Autocommit is rejected, and the stock row disappears on commit. This proves the lock is held, transaction-scoped, and disjoint from the shared bigint key space. |

The executed control harness composes the real inventory definition into the
real application definition exactly because standalone inventory is specified
to fail closed without its Item and Location targets. It follows the emitted
release-manifest → storage-target-manifest → storage-target-chunk chain, selects
the sole emitted fact-storage entity, and resolves its generated schema, table,
and field columns. It then persists and materializes that release through the
generic provider before any aggregate probe. No `nsm_t_*` or movement table
name is hardcoded, inferred from a catalog pattern, or copied from compiler
output.

Every transactional path queries that real compiled movement relation by the
emitted tenant and environment scope columns, compiler-derived legal-entity
column, and emitted item and location columns. The tests append no facts and
create no posting path. Synchronization is by observed `pg_locks` state and
PostgreSQL deadlock detection, never sleep-and-measure wall-clock assertions.
