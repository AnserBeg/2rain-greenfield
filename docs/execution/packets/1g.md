## Outcome

The composed application is no longer a one-time bootstrapper. Its compiled
artifact now carries an ordered immutable lineage:

1. the existing v1 artifact is read as `bootstrap -> application A`;
2. a rebuild first recompiles and verifies every existing edge from its own
   normalized bytes;
3. if the authored definition changed, the compiler emits application B with
   `expectedActiveReleaseFrom(A)` and appends B under the v2 lineage envelope;
4. startup resolves the active pointer to one exact lineage member and advances
   only through subsequent exact source -> target edges; and
5. every edge registers the immutable release, persists preparation evidence,
   obtains a real approval, and activates through
   `PostgresReleaseActivationService`.

A transition with storage elements continues through
`PostgresModuleStorageMaterializer`. A definition-only transition with zero
storage elements uses the release kernel's existing
`NO_STORAGE_TRANSITION` preparation receipt instead of inventing a fake
materialization. Both paths bind the active source release, source root,
candidate release and candidate root.

The checked-in v1 artifact is intentionally unchanged. The first changed
definition upgrades it to v2 and preserves A before appending B. A fresh
database can therefore replay `bootstrap -> A -> B`, while a persistent
database already on A selects only `A -> B`.

## Exact selection and activation

Before opening a database connection, startup validates every compiled edge
against:

- the previous release root and normalized-definition digest;
- the previous storage-target artifact root and semantic digest; and
- the candidate normalized-definition digest plus storage-target artifact root
  and semantic digest.

After persistence, the active release ID must equal one member of that validated
lineage. Startup never guesses from a package version, definition shape, or
latest timestamp. A pointer outside the lineage fails closed. A pointer on a
lineage member runs only the following edge(s).

`active_release_pointer_exact_swap` is read directly from `pg_trigger` and must
have `tgenabled = 'O'` before transition preparation, immediately before every
activation call, in a `finally` block after every activation call, and after
the final pointer is read. No code disables the trigger or writes the pointer
directly.

| Vacuity vector | Executed control | Observed result |

| advancement is not real | Before the runtime fix, compile B with the real compiler against A, close A, then reconstruct the same tenant from B | red in 11.7s with `the active pointer names a release outside this composed application` at the reported old branch; this is the defect reproduction |
| persisted data could be recreated or changed | Create Party `P-UPGRADE-001` through `SemanticOperationGateway` under A; snapshot the complete physical PostgreSQL row with `to_jsonb`; close all A pools; activate B; snapshot again and query through a fresh `SemanticQueryGateway` | the physical row is deep-equal before/after and the B query returns the same record ID |
| the exact-swap trigger assertion could be vacuous | Set only `active_release_pointer_exact_swap` to disabled, call the real B startup, and restore it in `finally` | startup rejects with `active_release_pointer_exact_swap is not enabled`; A remains active; the permanent control then reads `tgenabled = 'O'` after restoration |
| a mismatched previous could activate | Compile a decoy successor from A, compile a second candidate from that decoy, but declare the second candidate immediately after A | startup rejects before database writes with `compiled application transition does not match its declared previous release`; A remains active |
| approval could be bypassed | Bind a persisted preparation, approval and activation attempt to the real B candidate registered by startup; revoke that approver's live eligibility; invoke the activation service | decisive result is `APPROVER_REVOCATION` / `NO_SWAP_TERMINAL`, not a missing-record error; A remains active and the trigger remains `O` |
| the positive path could use a different candidate | Restore the same approver, then run the composition root against the same B artifact | one joined approval/attempt/outcome for exact A -> B records `SWAPPED`; B becomes active |
| rebuild support could be test-only synthesis | Run `compile-app-release.ts` against temporary copies of the real v1 artifact and an authored v1.0.1 definition, then run its `--check` mode | the script emits a parseable v2 lineage with exactly one appended immutable release and its freshness check passes |

## Rollback boundary

Rollback to prior immutable release A does **not** fall out of this machinery.
A's compiled storage transition is immutably bound to `bootstrap -> A`, not
`B -> A`. Recompiling A's old definition against B would produce a new release
identity, not activate the prior immutable A, and storage-changing reversals
need an explicit reverse-transition policy. This packet therefore stops at the
requested boundary: forward advancement is now reachable and exact; composition
root rollback remains work for the G2-P9 journey rather than being guessed or
silently broadened here.

## Test it yourself

Prerequisite: Docker is running. Use one shell from a clean checkout. First
back up the two generated inputs, start release A, and keep the same named
database volume:

```bash
packet_1g_backup="$(mktemp -d)"
cp apps/web/release/app.authored.json "$packet_1g_backup/app.authored.json"
cp apps/web/release/app.compiled.json "$packet_1g_backup/app.compiled.json"
corepack pnpm --filter @north-star/api dev
```

Wait for `COMPOSED_APPLICATION_READY` and note its `releaseRoot`. Open
<http://127.0.0.1:4174>, click **Party form**, create a uniquely named Party,
then confirm it appears under **Party list**. Press `Ctrl+C`.

Change the authored package definition, rebuild, and restart without removing
the container or volume:

```bash
node --input-type=module -e "import {readFile,writeFile} from 'node:fs/promises'; const path='apps/web/release/app.authored.json'; const definition=JSON.parse(await readFile(path,'utf8')); definition.package.version='1.0.1'; await writeFile(path, JSON.stringify(definition,null,2)+'\n');"
corepack pnpm --filter @north-star/web build:app-release
corepack pnpm --filter @north-star/api dev
```

The new `COMPOSED_APPLICATION_READY` line has a different `releaseRoot`. Open
**Party list** and observe the Party created under A unchanged under B. No
database volume was dropped. Press `Ctrl+C`, then restore the checked-in
artifacts:

```bash
cp "$packet_1g_backup/app.authored.json" apps/web/release/app.authored.json
cp "$packet_1g_backup/app.compiled.json" apps/web/release/app.compiled.json
rmdir "$packet_1g_backup"
```

## Known limits

- Verification evidence remains the asserted UUID contract inherited from
  G2-P5e; current-plan row 1b owns durable content-bound verification.
- The local composition root still installs its stable local approver and
  executor identities. The approval and attempt are real persisted kernel
  records, but this is not production identity provisioning.
- Lineage growth is intentionally append-only. Retention/compaction is not
  introduced because deleting prior immutable releases would break fresh replay
  and the no-hard-delete doctrine.
- Rollback is not implemented for the reason recorded above.
