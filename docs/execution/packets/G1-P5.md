## Goal and Freeze D semantics

Build the request-entry composition that consumes the one authoritative
tenant/environment `ActiveReleasePointer`, resolves exactly one immutable
`TenantRelease` and its compiled projections, and exposes one immutable
`RequestRuntimeView` to every consumer in that unit of work. Freeze D is the
last SERIAL-SPINE contract: G1-P6, G1-P7, and G1-P8 consume it without
introducing another release or request authority.

The view pins application definition only. Current authorization remains live,
deny-capable, and owned by the Identity/Policy gateway seam. Invalidation is a
cache-coherence hint; correctness always validates the authoritative pointer.

## Binding design

1. Request entry starts with the accepted authenticated trusted context. The
   PostgreSQL loader reads the tenant/environment pointer and the selected
   release/artifacts in one authoritative snapshot, then constructs one deeply
   immutable view containing tenant/environment, principal, policy version,
   pointer identity and fence, release identity/content hash, and pinned
   catalog/query/operation/surface/agent projections.
2. A unit of work receives exactly one view. It cannot reload or substitute a
   release through an ambient tenant, environment, global release, process
   default, or caller-supplied identity. A null pointer or invisible/missing
   release fails closed.
3. The view's application definitions remain stable for its lifetime. Live
   authorization is invoked with explicit trusted/pinned context at every
   decision and may deny after a policy change or revocation; the entry-time
   policy version is evidence, not frozen authority.
4. The P4b invalidation envelope and maximum-fence consumer are consumed
   directly. Each cached view is tagged with the pointer fence read in the same
   snapshot as its artifacts. Entries below the highest invalidated fence are
   dropped. A slow fill may not publish after a newer invalidation. Duplicate
   or reordered events are rejected, and a gap or doubt causes an authoritative
   reread.
5. Pin validation compares the explicit view with the authoritative pointer.
   A release change returns a versioned recoverable stale-release/replan result,
   never a partially updated view or silent divergence.
6. Jobs, workers, agent runs, operation plans, caches, and report snapshots use
   a serialized explicit pinned-context envelope equivalent to the view's
   trusted/release generation identity. No consumer can reconstruct it from
   ambient process state.

## Review charter

Gates must be green on one frozen candidate. In scope: single-release request
pinning, trusted request-entry composition, same-snapshot release/artifact
resolution, fail-closed absence, live deny-capable authorization, monotonic
invalidation and slow-fill races, recoverable stale-release detection, and
explicit deferred context.

Threat model: stale reads, cache races, ambient fallback, and accidental
authorization freezing by honest code; not hostile input.

Out of scope: gateway semantics (G1-P6), surface rendering (G1-P7), agent
runtime, rich application verification, migration execution, compiler changes,
and unrelated hardening. Valid out-of-scope observations become future-work
rows and are not chased.

Decisive questions:

- During activation racing an in-flight request, does the old request retain
  exactly its pinned release while the next request receives the new one?
- Can two tenants concurrently hold different pinned views without any global
  or default fallback?
- Do missing/null pointers and missing/invisible releases fail closed?
- Can a live policy change or revocation deny work inside a valid pinned view?
- Is a fence-N cache entry discarded after advancement, including when a slow
  reader tries to publish after the newer invalidation?
- Does release change return a recoverable replan result, and is deferred
  execution context always explicit?

Critical tier requires a fresh naive Codex `gpt-5.6-sol` xhigh review to PASS,
then Fable max on the identical unchanged SHA. Any code fix creates a new SHA
and a fresh review. At most two `REVISE` rounds are permitted before stopping
and surfacing the result.

## Evidence

### Preliminary writer implementation notes

- `@north-star/runtime/request-runtime-view` is the sole Freeze D authority.
  The authenticated composition reuses the accepted trusted-context issuer,
  asks an injected loader and the explicit current-policy port for entry
  evidence, constructs exactly one view, and passes that view to one unit of
  work. Projection payloads are decoded immutable JSON, recursively cloned and
  frozen; neither the view nor its nested definitions exposes `Uint8Array`.
- The PostgreSQL loader accepts only an issued `TrustedRequestContext`. Each
  fill reads the scoped pointer, selected immutable release, root artifact,
  projection manifests, chunk links, and chunks with one SQL statement. It
  verifies the release envelope and the semantic-model, query-catalog,
  operation-catalog, surface-manifest, and agent-discovery family/manifest/
  chunk structures before returning Freeze D data.
- Every cache lookup first reads the authoritative pointer. Cache keys include
  explicit tenant, environment, and stable pointer identity; entries carry the
  same-statement fence. Publication rechecks the pointer and the imported P4b
  maximum invalidation fence without an intervening await, closing the slow
  fill race. The service consumes the accepted P4b invalidation event/fence
  state directly; gap and doubt paths perform an authoritative reread.
- The narrow current-policy port is explicitly marked as the future T-01/G2
  seam. Entry policy version is evidence only. Every authorization helper call
  passes explicit view identity to the live gateway, and no decision is stored
  in the view. The stateful focused adapter proves entry-time ALLOW followed by
  DENY after revocation while the complete pinned view remains byte-for-byte
  unchanged.
- The versioned deferred envelope contains explicit tenant, environment,
  principal, policy evidence, pointer identity/fence, and release identity/
  content hash. Exact authority returns `CURRENT`; a generation change returns
  recoverable `STALE_RELEASE_REPLAN`; missing authority throws a stable typed
  fail-closed error. A child-process fixture receives and parses only the
  serialized envelope and proves an absent explicit envelope cannot be
  reconstructed.
