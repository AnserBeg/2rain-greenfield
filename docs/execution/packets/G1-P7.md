# G1-P7 — Compiled SurfaceRuntime shell and component registry

Status: accepted
Tier: Behavioral
Base: `6a31b17886e3e8ccdef7a72291261519c4bf79e7`

## Goal

Render the first signed-in browser pixels from one compiled tenant release.
Navigation, active surface selection, slots, status roles, and component
references come from the surface projection in one issued Freeze D
`RequestRuntimeView`. The shell has no pointer/release loader, ambient context,
hardcoded screen list, or component-registration escape hatch.

This is an empty application shell, not a business module. The checked-in demo
release exists so a human can exercise the browser checkpoint before G2 data
screens exist; it is deterministically regenerated by the accepted compiler
and enters the renderer only through the accepted authenticated request-entry
adapter.

## Binding design

1. `createSurfaceRuntimeServer` receives an
   `AuthenticatedRequestRuntimeEntryAdapter`. Each browser read invokes that
   adapter and passes its one issued view directly to `renderSurfaceRuntime`.
   The server and renderer expose no loader, pointer, release repository,
   tenant selector, or process-global application state.
2. `renderSurfaceRuntime` and `readCompiledSurfaceManifest` both assert the P5
   WeakSet-gated view. The only application-definition input is
   `view.projections.surface`; the view's release ID, content hash, pointer
   identity/fence, trusted tenant/environment, and principal remain pinned for
   the rendered response.
3. Active navigation is the ordered active-surface array from the compiled
   manifest. A missing route is a typed rendered diagnostic. No screen label or
   navigation entry is declared in renderer or registry source.
4. The surface projection is runtime-checked for its frozen payload version,
   closed archetype/status/slot vocabulary, required identities, duplicate
   surfaces, and duplicate/invalid slots. Missing, malformed, empty, or
   unsupported projection states fail as browser diagnostics rather than
   becoming a fallback surface.
5. The component registry is immutable and has no registration API. A compiled
   reference either resolves to one closed renderer, produces
   `UNSUPPORTED_COMPONENT`, or is caught by the component boundary as
   `COMPONENT_RENDER_FAILED`; one failed slot never replaces the pinned view or
   crashes the shell.
6. The demo release is compiled from `shell.authored.json` into
   `shell.compiled.json` by the production compiler. The focused contract gate
   recompiles and compares its complete semantic JSON before browser tests.
   The running demo reads that explicit artifact through a test/demo P5 loader;
   serving runtime code never invokes the compiler.

## Decisive review charter

Gates are green on one frozen candidate. In scope:

- navigation and the home/setup experience are driven by the compiled release,
  including an assertion that compiled labels/order are absent from renderer
  and registry source;
- the shell reads application definition only through the issued pinned
  `RequestRuntimeView`, with no ambient release path;
- unsupported projection/component, unknown surface, and component-failure
  paths render usable diagnostics rather than crashing;
- every slot renderer comes only from the closed component registry.

Threat model: accidental hardcoding and ambient release access by honest code.
Out of scope: G1-P6 gateway semantics, real G2 business modules, agent runtime,
hostile-input hardening, full responsive/accessibility conformance, and any
finding unrelated to this packet.

Decisive questions:

- If compiled surface labels/order change, does navigation change without a
  renderer edit?
- Can any shell path load, choose, substitute, or globally cache a release
  outside the issued view?
- Do unsupported and thrown component paths remain inside stable rendered
  diagnostics?
- Can an unregistered component execute, or can runtime code extend the
  registry?

Behavioral tier requires one fresh naive Codex `gpt-5.6-sol` xhigh review
against this charter, then the user-requested Fable max confirmation on the
identical unchanged SHA. Any product fix creates a new candidate and fresh
reviews. At most two REVISE rounds are permitted.
