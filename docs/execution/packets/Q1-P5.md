# Q1-P5 — The legal-entity query operand, canonical v4

Lane: CANON · Tier: Critical · Branch: `packet/q1-p5-gateway` · Base: `8385e13`, merged with `main` at `d7b932f` (Q1-P4 integrated)

## Outcome

Canonical language **v4** is cut, carrying one new member: `legalEntityScope` on both v4
query branches, with a `queryParameterReference` operand and
`"exactlyOne" | "nonEmptySet"` cardinality. Nothing adopts v4, so every checked-in root,
golden and release artifact is byte-identical.

The design decision and its reasoning are [ADR-0031](../../decisions/ADR-0031-legal-entity-query-operand.md).
The short form: the family map derives compile-time storage metadata, the read scope
selects a runtime business value that changes the answer, and query operands belong in
the query shape. The operand is an **ordinary declared query parameter**, which is what
makes it reachable — the caller puts a UUID in `envelope.arguments` and the existing
two-argument adapter carries it unchanged.

**The gateway half is not in this packet.** See "Deferred by ruling" below.

## v4 was cut as `4a`+`4b`, not `4c`

Row `4a` cut v3 as dispatch-only with the success condition "canonical bytes, goldens and
release roots do not move"; `4b` added shapes; `4c` migrated packages and absorbed the
artifact event. This packet is `4a`+`4b` for v4. Adoption — and therefore the artifact
event — belongs to the packet that authors `onHand`.

That required splitting one constant into two:

| Constant | Before | After | Meaning |
|---|---|---|---|
| `LATEST_LANGUAGE_VERSION` | `v3` | **`v4`** | newest readable |
| `ADOPTED_LANGUAGE_VERSION` | — | **`v3`** | what `DEFAULT_COMPILER_PROFILE` selects |

`4a` did not make this split: it moved `LATEST` to v3, which moved
`DEFAULT_COMPILER_PROFILE` with it and cost a class grant across eight files to
re-derive profiles per artifact. Splitting the constant avoids that entirely here.

## Review round 2 — REVISE, one finding: my round-1 fix was incomplete

Fresh naive Codex xhigh against `4ab9e38`, same charter, plus an instruction to verify
the three round-1 fixes rather than assume them settled. Findings 2 and 3 were confirmed
closed. Finding 1 was **not**.

The round-1 fix guarded `parseAuthoredValue`, but
`VersionedAuthoredApplicationPackageSchema` and
`VersionedNormalizedApplicationPackageSchema` are themselves **public exports**
(`index.ts`), so a caller using the schema directly still parsed a v3 package carrying a
v4 node. The reviewer reproduced it on both schemas.

**The root cause was the shape of my fix, not its placement.** Guarding one entry point
left the next entry point as the next hole. Purity now lives on the exported schemas
via `withNodeVersionPurity`, so every consumer — the two function parsers and any direct
caller — inherits one rule from one authority. The imperative duplicate in
`parseAuthoredValue` was deleted rather than kept alongside it.

## Recorded conditions of this packet — two items owed, neither a blocker

Stated here rather than left in a report, because a condition that lives only in a
message is invisible to the next lane.

### 1. Five v3-pinned comparisons reject v4 aggregate catalog nodes

`packages/runtime/src/semantic-query-gateway.ts:1045`, `:1077`, `:1093`, `:1338`, `:1361`
each compare an aggregate catalog node's `schemaVersion` against the literal `'v3'`. A v4
package's *aggregate* query catalog entry would therefore be refused as a malformed
pinned catalog.

- **Not reachable today, and not a blocker.** No package is authored at v4 — this packet
  deliberately adopts nothing — so no v4 aggregate node exists in any compiled release.
  The failure mode is a typed refusal, not a wrong answer: it fails closed.
- **What makes it reachable:** the first packet that migrates a package carrying an
  aggregate query to v4. Concretely, the `onHand` packet (`G3-P5`), which is the whole
  reason v4 exists. It cannot ship without touching these five lines.
- **Owner: the `onHand` packet**, as part of its v4 migration. This is the eighth
  appearance of the version-from-artifact rule and these five are the same disease: they
  should ask the node's declared version, not compare against one literal.
- The row-query path this packet exercises does not reach them, which is why the
  reachability control passes while they stand.

**If a reviewer finds any of the five reachable from a v3 or unadopted-v4 path, that is a
stop-and-report, not a widening.** Relaxing a comparison to admit v4 without a package at
v4 would loosen the pinned-catalog contract for no observable gain.

### 2. Release verification does not yet run the probe

ADR-0031 §5 rules the mechanism and the gateway implements the refusal, controlled by
`omission is refused with a typed error and no business entity`. The call site is not
wired: `packages/postgres-provider/src/release-verification-service.ts:691-700` declares
`VerificationQueryContract` over `get | list | resolve | search` only, and
`#invokeQueryById` supplies no arguments for a plain `list`.

- **Not reachable today**, for the same reason: verification probes queries in a compiled
  release, and no released query declares the operand.
- **What makes it reachable:** the same v4 migration. The moment a released Q0 query
  declares `legalEntityScope`, verification's existing `#invokeQuery(query, {})` call hits
  the typed refusal and fails the release — correctly, but as an unhandled error rather
  than as the probe's expected outcome.
- **Owner: the `onHand` packet**, which must teach verification to expect the refusal
  rather than to treat it as a failure. The file is outside this packet's lease.

## Findings recorded, not chased

- **A v3 row query may reference an undeclared query parameter.**
  `v3PredicateExpressionSchema` admits `queryParameterReference` in any query's filter,
  but `deriveAggregateContracts` validated references for aggregates only, and row
  queries have no `parameters` collection. v4 row queries close this (they get
  `parameters` and the shared derivation). **v3 is deliberately left alone** — narrowing
  a released version retroactively is the mirror image of widening it.
- `QUERY_PARAMETER_LIMIT_V3` is reused as v4's bound. The value is right; the name now
  reads oddly. Renaming it is a mechanical follow-on, not this packet's business.
