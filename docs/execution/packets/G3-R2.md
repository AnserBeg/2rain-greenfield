# G3-R2 — dimension-set replay reproduces prior balances

Status: authoring candidate; Critical review and full-matrix evidence pending

## Packet contract

- **Goal:** execute plan §11.6 gate criterion 11 and ADR-0016 step 2 with a
  test-owned stock-dimension set: replay one immutable v1 movement history
  under an activated v2 set, then prove every balance served for the old key is
  byte-identical.
- **Tier:** Critical. A false green would bless a one-way change to inventory
  identity.
- **Owned paths:** `test/postgres/inventory-dimension-set-replay.test.ts`,
  `test/fixtures/g3/dimension-set-replay.ts`, this record, and the add-only
  test inventory entry in
  `test/architecture/repository-hygiene.test.ts`.
- **Out of scope:** a product dimension-set v2; ADR-0016's re-baseline
  operation and activation blocker; any change to the frozen Inventory
  contract, conformance ratchet, posting path, or existing on-hand test.
- **Runnable exit:** the fixture compiles two independently pinned query
  catalogs, persists and replays the movement history in ephemeral PostgreSQL,
  and serves balances through `SemanticQueryGateway`.

## Fixture and observed property

The v1 fixture set is `(legalEntityId, itemId, locationId)`. The v2 fixture set
adds `batchId` and declares the canonical enum member
`northstar.g3r2fixture:member.batch_unspecified`. The member is a stored,
filterable domain value. It is neither `NULL`, the empty string, nor an
executor-only sentinel.

The two compiled subjects are observably different:

- v1 release root:
  `c835756160a37e287258fe80e4aae31f711330ff83036a97f6990e6cb81e585e`
- v2 release root:
  `43ade940305d378a9ee66e96b49832afdea45ddee8396abff7a716f29c809c75`
- the v2 storage projection contains the added enum field and its compiled
  query catalog contains the filterable added-dimension aggregate;
- a persisted activation row binds the v2 projection table, exact four-member
  dimension list, set version `2`, and v2 release root before any answer is
  measured.

Five immutable v1 events are inserted into the v1 projection. The same five
event IDs and payloads are replayed into the v2 projection; only the derived
new member is added, resolving to the declared `unspecified` member. Five
bitemporal probes are then served through the real semantic gateway for each
activated catalog:

| Prior balance probe | v1 bytes | v2 bytes | independent history reducer |
|---|---:|---:|---:|
| same stock, before the backdated event was recorded | `10.5` | `10.5` | `10.5` |
| same stock, after the backdated event was recorded | `7.25` | `7.25` | `7.25` |
| same stock, complete prior history | `8.375` | `8.375` | `8.375` |
| other location | `4` | `4` | `4` |
| other item | `2.5` | `2.5` | `2.5` |

The assertions compare the UTF-8 byte arrays, not parsed numbers. Each served
set is checked against a separate BigInt fixed-scale reducer over the immutable
event fixture before the two served sets are compared. The reducer does not
read the projection tables, query SQL, or gateway result.

After those observations, one v2-stamped event carries the real member
`northstar.g3r2fixture:member.batch_red`. Re-running all five prior probes is
still byte-identical. At a later horizon, the gateway observes:

- `unspecified` filtered aggregate: `8.375`;
- real-member filtered aggregate: `2.125`; and
- total: `10.5`.

A direct persisted-effect query groups the same rows into exactly those two
non-null, non-empty members. This separately observes grouping; the gateway
queries observe filtering and aggregation.

## What the gate observes

- two different compiler-produced query/storage subjects, including the added
  v2 field and query;
- activation evidence read from PostgreSQL before gateway execution;
- the exact event IDs persisted by both replays;
- every prior balance returned by the production semantic gateway;
- independently re-derived balance bytes from the immutable event fixture;
- persisted concrete `unspecified` values on every pre-extension movement;
- grouping in PostgreSQL, filter/aggregate behavior through the gateway, and
  the concrete member plus its display value in gateway-served output;
- a real v2 member on a post-extension movement without movement of any prior
  answer.

The activation verifier only reads compiled and persisted evidence. It does
not call the replay resolver, so the code that heals a missing dimension is not
the code that claims v2 was active or that `unspecified` was persisted.

## What the gate cannot see

This is deliberately fixture scope. It does **not** claim that the product
ships dimension-set v2, an unspecified-member lowering, a re-baseline
operation, or a tenant activation blocker. The product contract continues to
admit only v1. Because no product v2 interpreter exists, the compiled catalogs
execute through a test-owned PostgreSQL aggregate executor behind the real
`SemanticQueryGateway`; the packet does not claim coverage of
`PostgresModuleRuntimeInterpreter` for a nonexistent product shape. ADR-0016
steps 3 and 4 remain separate work and may not cite this packet as their
evidence.

The independent reducer proves the declared event fixture and served balances
agree. It is not a property generator over arbitrary histories, does not prove
concurrent posting, and does not prove production migration or release
activation mechanics. Those claims are outside this packet.

## Executed negative controls

The focused PostgreSQL run executed and caught these exact failures:

1. No served balances (empty-comparison vacuity):
   `G3_R2_ZERO_BALANCES_OBSERVED: replay comparison requires at least one served prior balance from each activated set`
2. No movement history (absent subject):
   `G3_R2_REPLAY_HISTORY_EMPTY: the replay subject must contain at least one prior movement`
3. Both served sets carry the same corrupt value, so comparing them only to
   each other would pass:
   `G3_R2_INDEPENDENT_ORACLE_MISMATCH: v1 same-stock-before-backdated-recording expected 10.5, observed 999`
4. Pre-extension movements resolve the added dimension to an ignored value.
   Before the member check runs, the ordinary replay equality assertion is
   executed and passes, proving that equality alone would miss this defect:
   `G3_R2_UNSPECIFIED_RESOLUTION_MISMATCH: event 61a00000-0000-4000-8000-000000000001 expected northstar.g3r2fixture:member.batch_unspecified, observed ignored`
5. Pre-extension movements resolve the added dimension to `NULL`. Before the
   member check runs, the ordinary replay equality assertion is executed and
   passes, proving that equality alone would miss this defect:
   `G3_R2_UNSPECIFIED_RESOLUTION_MISMATCH: event 61a00000-0000-4000-8000-000000000001 expected northstar.g3r2fixture:member.batch_unspecified, observed NULL`
6. The replay is run against the v1 compiled subject a second time:
   `G3_R2_V2_NOT_ACTIVATED: expected release 43ade940305d378a9ee66e96b49832afdea45ddee8396abff7a716f29c809c75, observed c835756160a37e287258fe80e4aae31f711330ff83036a97f6990e6cb81e585e`

## Review charter

- **Gates already green:** focused PostgreSQL 1/1, repository hygiene 11/11,
  and typecheck.
- **In scope:** whether P1-P5 are actually observed; whether byte identity is
  judged independently; whether the concrete member groups, filters, and
  aggregates; whether all stated vacuity vectors execute red; whether v2
  activation is measured independently of resolution.
- **Out of scope:** shipping product v2, ADR-0016 steps 3-4, redesigning the
  frozen Inventory contract, unrelated query/compiler concerns, and active
  adversarial obfuscation.
- **Threat model:** an honest future author accidentally omits the history,
  shares an oracle with execution, maps the new dimension to null/ignored,
  or runs v1 twice and receives a false green.
- **Decisive questions:** do both served sides independently equal the event
  history bytes; does a v1-stamped row persist the declared member; can that
  member be grouped and selected in an aggregate; did the activated subject
  provably gain the new dimension; and does each named false-green construction
  produce its recorded red?
