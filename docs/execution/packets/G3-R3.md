# G3-R3 — restore, rebuild, and the same balances

Lane: BUILD · Base: `fc536d07` · Tier: Critical · Reviewed SHA: `6646f5da`.

Closes gate criterion 16 ("restoring a backup and rebuilding read models
reproduces the same balances") and the criterion 7 `PARTIAL` ("backdated
behavior is explicit and tested") from the `g3-completion` ruling.

Test-only. No product code changed.

## What already existed and was not rebuilt

On-hand is a `sum` over `inventory_movement.quantity_delta`; no stored balance
exists (criterion 1, criterion 17). The only derived store is the aggregate
anchor set from migration `0020`, written **lazily on read** by
`insertAggregateAnchor` (`module-runtime-interpreter.ts:1336`). So "rebuild the
read models" means: clear the three derived tables, read again, let them
regenerate. Nothing about the anchor machinery is altered here.

There was no dump/restore machinery anywhere in the harness. This packet adds
it, for tests only.

## R3-a — `test/postgres/inventory-backup-restore.test.ts`

One test, ~20 s, one ephemeral cluster.

1. Migrate, provision one legal entity (`negative_stock=reject`,
   `maximum_backdate_days=30`), stage the empty and composed releases,
   materialize, seed items and locations.
2. **Back up (1)** — before any posting exists.
3. Post real history through `PostgresInventoryPostingService`: three
   adjustments (`+10.5`, `+7`, `+4.25`), one transfer (3 units, two movement
   legs), one **initial** stock count (`expected 14.75 / counted 15 /
   variance 0.25`, posting role `count`). Seven movements total.
4. **Back up (2)** — with the correction still unposted, so restoring it is a
   restore that lost exactly one movement.
5. Post the stock-count **correction** (`expected 15 / counted 14 /
   variance -1`, posting role `correction`).
6. Read all seven balance probes through the **real** gateway
   (`SemanticQueryGateway` over `PostgresModuleRuntimeInterpreter` over a
   `north_star_runtime` pool, view issued by
   `PostgresRequestRuntimeViewService`). Assert them against an independent
   oracle: `10.5, 14.75, 15, 14, 4, 3, 0`.
7. **Back up (3)** — the complete subject, taken after those reads, so the
   backup carries both the ledger and the anchors they wrote. Census the source.
8. Restore each backup into a fresh `CREATE DATABASE … TEMPLATE template0`, one
   at a time, dropping each when done.
9. On the complete restore: census → clear the derived stores → **assert the row
   counts are 0** → read again through the same gateway → assert byte-identical.

### How measurement was separated from regeneration

This is the subtle part, and an external reviewer cannot observe it by reading
the assertion alone.

**Reading is what recreates the anchor.** The post-restore comparison read
regenerates exactly the thing whose absence it is meant to prove. So the
comparison's own result can never be the evidence that the rebuild happened.

Two independent observations carry it instead, and neither is produced by the
comparison:

- **Persisted state, before and after.** `assertDerivedStoresEmpty` reads actual
  `count(*)` from all three tables in the window between the clear and the first
  read, and requires exactly `0`. The row counts are read out of the catalogue,
  not assumed from the `DELETE` returning. After the reads, the anchors are
  observed populated again. Empty-then-populated is a durable fact about the
  database, independent of what any balance said.
- **Provenance of each served value.** The interpreter reports, per aggregate
  read, whether a surviving anchor answered (`cache-hit`) or the movements were
  summed (`ledger-recomputation`). Every post-clear read must report
  `ledger-recomputation`; a single `cache-hit` fails
  `assertRebuiltFromLedger`. This is a fact about the code path taken, not about
  the number returned, so a rebuild that quietly did nothing cannot satisfy it
  by producing the right answer.

The **same restored database** is read once before the clear, where it reports
`cache-hit` for every probe. That is the positive demonstration that the backup
really carried the read models and that the clear is what turns the second read
into a rebuild.

### Counting anchors is not checking them

A row count cannot tell a restored anchor from a decoy, and cannot tell a full
rebuild from a partial one. Both are now **set** comparisons, and the two
vacuity vectors each have an executed red.

**Restore and rebuild need different identities, and the reason is not
cosmetic.**

- A **restore** must reproduce the **cache key** exactly. The key folds in
  release, principal, query, operands and movement generation, so a set that
  matches key for key cannot be decoys with the right cardinality.
- A **rebuild** cannot be held to the cache key. Clearing
  `semantic_aggregate_generations` resets the movement generation the key folds
  in, so every rebuilt key **legitimately** differs. What must be reproduced
  exactly is the query, the operands it was asked with, and the balance it
  anchors.

The expected set is derived, not written down: the anchor catalogue is
snapshotted either side of the source probe reads and the difference is the
expectation, asserted to be exactly one anchor per probe.

**The decoy control runs on its own restored copy, which never opens a read
seat.** "It fails before any gateway read" is therefore a structural fact about
that block, not a claim about statement order — the control cannot fail after a
read has already regenerated what it checks.

### The comparison set is not hand-maintained

The G3-R1 lesson applies directly: no field list, no classification table.

- **Balances** are compared **wholesale as bytes**, not field by field.
- **The relation census** is a `count(*)` over **every base table in every
  non-system schema**, derived from `information_schema.tables` via
  `query_to_xml`. Nothing in the test decides which relations matter, so a
  relation the restore silently dropped or truncated cannot go unnoticed. It is
  **cardinality only** and is named that way (`G3_R3_RESTORE_ROW_COUNT_DIVERGED`)
  — equal counts are not equal content, and content equality is proven only
  where it is separately observed.
- **The anchor set** is compared by identity, not by cardinality (below).
- **The query and its five parameter identifiers** are read out of the release
  the database under test actually serves (`onHandBinding`), not written down.
- **The derived-store roster** carries a construction-time ratchet:
  `assertDerivedStoreRosterIsComplete` deep-equals the roster against every
  `semantic_aggregate%` base table in `north_star_internal`. A fourth derived
  store fails the test instead of being silently under-cleared.

### Two restore hazards found by building this

Both are recorded, neither is fixed here.

1. **The business-period CHECK constraint reads another table.** The movement
   fact table carries
   `business_period = north_star_internal.inventory_business_period(tenant_id, effective_at)`
   (`module-storage-materializer.ts:1798`), and that function reads
   `platform.inventory_tenant_calendars`. A CHECK is re-validated on every
   `COPY` row, so a **single-pass `pg_restore` of this database fails** with
   `INVENTORY_TENANT_CALENDAR_UNDECLARED` whenever the calendar has not happened
   to load first. Observed, not theorised. The test restores in three passes and
   detaches the constraint around the data pass, re-attaching it afterwards —
   which **validates** every restored business period against the derivation
   rather than leaving it unchecked. A production restore runbook would need the
   same handling, and does not exist.
2. **The canonical decimal pattern rejects `-0.5`** — filed and escalated to
   canonical as `dec-negfrac`; this fixture uses `-1` for the correction
   variance to route around it.

## R3-b — `test/postgres/inventory-backdate-policy.test.ts`

Criterion 7 asked for the **policy** to be asserted, not for one sample
rejection. `enforceBackdate` (`inventory-posting-service.ts:1953-1967`) refuses
when `recordedPeriod - effectivePeriod > maximumBackdateDays`.

Two legal entities differing **only** in that dial (7 days and 0 days), recorded
time injected at `2026-08-04T13:00Z`:

| Case | Scope | Effective period | Outcome |
|---|---|---|---|
| exactly at the window | 7-day | `2026-07-28` (7 back) | **admitted**, movement written at that period |
| one day beyond | 7-day | `2026-07-27` (8 back) | **refused** `INVENTORY_BACKDATE_LIMIT_EXCEEDED` |
| forward-dated | 7-day | `2026-08-11` | **admitted** — the dial bounds backdating only |
| the admitted command, narrower scope | 0-day | `2026-07-28` | **refused**, naming the 0-day window |
| same day | 0-day | `2026-08-04` | **admitted** |

The fourth row is the decisive one: the identical effective period flips from
admitted to refused when nothing changes but the configured window, so the
**dial** is the cause and not the date.

Each refusal asserts the typed error class, the code, the exact message
including the enforced window, and the `effectivePeriod` / `recordedPeriod`
details — not merely that something threw. Six other checks run before
`enforceBackdate`, and asserting only "it rejected" would accept any of them.
Each refusal also asserts **no movement was written** for that source and that
the source transaction is still `draft`, so the refusal is inside the
transaction.

**Correction to the charter's premise.** The charter said "only config-shape
tests touch it today". That is not accurate: `inventory-posting.test.ts:489-510`
has asserted `INVENTORY_BACKDATE_LIMIT_EXCEEDED` since `867a738`
(2026-07-29). What that case does **not** do — and what left criterion 7
`PARTIAL` — is exercise a non-zero window, an accepted boundary, or the dial as
the cause: every legal entity in that file is provisioned with
`maximum_backdate_days = 0`, so the only fact observed is that one day back is
too far when zero days are allowed. R3-b adds the boundary and the dial.

Nine in R3-a, two typed refusals in R3-b. Seven of the nine are produced by real

## What this does NOT prove

Stated plainly, because an external reviewer cannot discover it by running
things.

- **The restore is database-scoped, not cluster-scoped.** `pg_dump` /
  `pg_restore` of one database into a fresh database in the **same** cluster.
  Cluster globals — the `north_star_runtime`, `north_star_module_runtime` and
  `north_star_module_materializer` roles — are not part of the backup and are
  not exercised by the restore. A real disaster-recovery drill onto a new
  cluster would need `pg_dumpall --globals-only` first, and nothing here tests
  that.
- **No production backup or restore procedure exists.** This is test-only
  machinery. In particular the CHECK-constraint hazard above means the obvious
  production restore command does not work, and no runbook records that.
- **Only the on-hand aggregate is compared.** It is the only balance the
  platform serves, so the set is complete today — but the comparison is over
  the seven authored probes, not over every key a tenant might read.
- **The relation census is cardinality, not content.** Equal row counts per
  relation prove nothing about the bytes in those rows. Content is separately
  observed for exactly three things: the served balances (byte for byte), the
  anchor set (by identity), and every business period (re-validated by the
  re-attached CHECK). Every other restored column is uncompared.
- **The anchor comparison covers only the anchors the seven probes produce.**
  Anchors for keys nobody reads are outside it, which is the same read-path
  limitation the `g3-completion` ruling already records for the discrepancy
  guard.
- **Rebuilt anchors are matched on query, operands and balance — not on
  `anchor_digest`.** The digest cannot be compared across the rebuild for the
  same reason the cache key cannot, and this packet does not re-verify it. The
  standing `anchor_digest` integrity gap the ruling names as "the only remaining
  genuine reachable false-consistent" is untouched here.
- **The decoy control proves cache-key set equality, not payload equality.** A
  restored anchor carrying the right key with a corrupted `balance_value` would
  pass the set check; what catches that case is the separate byte comparison of
  the served balances, and only for the seven probe keys.
- **The rebuild is a `DELETE` plus a read**, not a rebuild job. There is no
  scheduler and none is claimed; durable job machinery stays deferred to G4.
- **`--disable-triggers` on the data pass is not load-bearing.** It was kept for
  safety, but a victim run showed the test stays green without it, because the
  fact table's effect trigger is created in `post-data` and does not yet exist
  while the data loads. The comment says so rather than implying protection it
  does not provide.
- **Criteria 11 and 14 are untouched.** Criterion 11 is `G3-R2`; criterion 14's
  agent and export arms are the explicit G4 inheritance.
