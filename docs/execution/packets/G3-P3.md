## Goal and scope

Post the first immutable Inventory movement through the declared
`northstar.inventory:capability.posting` v1 capability. This packet supports an
existing adjustment draft only. Transfer, count correction, reversal, `onHand`,
UI mounting, reservations, valuation, and public transport wiring remain out of
scope.

Owned implementation is one closed provider capability, its real PostgreSQL
control, ADR-0026, and this record. No migration was needed: accepted migration
0015 already contains the partitioned append-only movement, effect companion,
configuration, calendar, period-lock, base-unit binding, grants, and RLS
contracts.

## Ratified capability boundary

[ADR-0026](../../decisions/ADR-0026-inventory-posting-capability.md) admits the
posting capability because the generic press deliberately has no movement
create/update/archive operation. It is therefore not an alternate executor for
a Tier-A O0 operation. The compiler, generic runtime interpreter, materializer,
and fallback routing gain no Inventory branch.

The provider exact-matches the capability ID and version against the frozen
contract constants and exact-matches dependency-set v2/root. It also proves the
caller-supplied v3 storage payload is byte-for-byte the named projection chunk
of the active release. Event and record IDs derive from the accepted capability
namespace. The identity constant is compiled into this capability-local adapter
without adding a module-ID branch to generic press machinery; the press-law
ratchet remains at its exact three pre-existing routed entries.

Release-persisted capability admission is **not claimed**. No current release
artifact declares `capability.posting`: Inventory is not mounted in the composed
release, so an admission table would become a second desired-state authority
rather than evidence of release state. G3-P6a plus its routed projection
follow-on owns emitting that declaration. Until then this packet delivers the
achievable fail-closed boundary: exact compiled contract identity/root plus
exact active storage artifact, and records the missing release binding plainly.

The posting dependency set intentionally evolves before the first fact from v1
(30 entries, root `7ef50e86732818a0ec4ec2a03a001066ac59408ea260c65bf018646e4377a63d`)
to v2 (31 entries, root
`2eb1de635331ee5781fe928a37d3664e3d4f8ccfe56ca44e231a652a806eca05`).
The added read is `northstar.inventory:transaction_line`; without it the
capability cannot prove the command equals the complete persisted draft line
set. This is the protocol-version event anticipated by G3-P0 item 7, not a
history rewrite.

The accepted generic trust service cannot wrap this mutation: it performs
runtime-role, context, release, and idempotency reads before its mutation
callback. G3-P2b-2 requires stock-lock acquisition to immediately follow
`BEGIN`. ADR-0026 therefore admits private capability-local writers for the
existing invocation/change/event/outbox/receipt rows. They expose no standalone
successful-evidence API and commit or roll back only with the movement.

## Posting transaction

`PostgresInventoryPostingService` owns this sequence:

1. validate the closed command and issued actor envelope before acquiring a
   connection;
2. `BEGIN`, then call `acquireStockIdentityLocks` as the first operation;
3. validate the active release and its release-recorded legal-entity dials;
4. assume the compiled module role, bind the complete persisted draft line set
   and optimistic revision to the command, validate active legal entity,
   item/base unit and location, read all serialized movements for each affected
   stock identity, and apply the global same-instant order;
5. evaluate `negativeStock` against that serialized history, then enforce
   reason, approval, backdate, and the per-entity period lock;
6. create a savepoint only after the stock locks, append movements (whose
   compiled trigger claims the natural effects), and transition the matching
   adjustment draft by state/revision only;
7. read back the immutable movements, restore the trusted runtime role, append
   linked quantity-only trust evidence plus the semantic receipt, and commit.

Any failure rolls back the movement, effect companion, draft transition, trust
facts, and receipt. The capability never accepts `recordedAt` in command input;
one platform-owned authority is sampled once and supplies every movement and
linked trust fact.

## Atomicity and non-vacuity

- An `AFTER INSERT` trigger advances a non-transactional sequence, and a later
  transaction-transition trigger injects SQLSTATE `P0001`. The sequence proves
  the movement INSERT executed before failure; afterward the movement and
  companion counts and accepted-trust count are unchanged. This distinguishes
  real rollback from an implementation that checks state before writing.
- Foreign draft-B line IDs, mutated quantities, and an omitted member of a
  two-line draft all reject `INVENTORY_TRANSACTION_STATE_CONFLICT`. A stale
  draft revision rejects; the corrected revision posts, and the change document
  records the revision returned by the conditional transition (`3`), not a
  hard-coded `2`. Final focused diagnostics were:
  `transaction line e9ca1298-131e-48a4-9d92-f066ce4c79f8 differs from the posting command`;
  `transaction line 372128dc-7c0a-49a4-8178-fa807d2f9fb7 differs from the posting command`;
  `transaction 9d348e77-19d1-4798-9928-ffc29cf4676d line set differs from the posting command`;
  and `transaction 3b243aa0-5549-43db-a861-29997b21941c does not exactly match the active draft`.
- `northstar.fake:capability.posting`, the v1 dependency root, and a tampered
  storage payload each reject before any movement. The active storage control
  observes exact persisted artifact bytes, not only the caller's digest.
- All queried quantity-only subjects assert presence before key inspection.
- The money-key parser is independently observed rejecting `unitCost`.
- The repository inventory registers the new PostgreSQL test, so executed-file
  reachability cannot silently omit it.
