## Goal and boundary

This packet creates the physical inventory persistence required before any
movement insert path exists. It stores the legal-entity master, tenant business
calendar, per-entity period lock and posting configuration, transaction headers
and lines, immutable quantity-only movements, and the global natural-effect
identity. It also completes provider support for G3-P1b's entity-owned storage
target and upgrades already-materialized Item tables with the base-unit binding
constraint.

The split boundary is preserved:

- no per-stock-identity serializer mechanism is selected or prepared;
- no public or application movement insert/posting path exists;
- period-lock, configuration, and negative-stock enforcement remain inside the
  future posting transaction owned by G3-P3;
- no reservation table, column, configuration, or behavior exists; and
- no lot, serial, bin, monetary amount, cost, value, price, or currency column
  is reserved on a movement.

G3-P2b-2 remains responsible for deciding and proving either a lock point every
posting acquires or serializable execution with a declared bounded retry
contract. The schema in this packet does not decide between them.

## Physical shape and provider behavior

Migration `0015_inventory_storage_foundation.sql` adds sixteen tenant-scoped
relations: eight logical inventory tables and eight movement partition leaves.
All sixteen carry a required UUID `tenant_id`; the tenant-completeness ratchet
therefore moves from **49 / 42 / 7** to **65 / 58 / 7** for total,
tenant-scoped, and tenant-independent tables. The closed seven-table
tenant-independent authority is unchanged.

The movement primary key includes the partition key, while the separate effect
registry closes PostgreSQL's cross-partition uniqueness limitation. The natural
effect tuple is never weakened by `business_period`: the deliberate control
that added the period to the registry key allowed the same effect in two
periods and turned the gate red.

G3-P1b payload v2 is accepted only when at least one entity-owned target is
present; a tenant-shared-only target must still advertise v1. Entity-owned
managed tables receive the legal-entity column and FK. Runtime UPDATE is
column-granted only for mutable business columns, excluding tenant,
environment, record identity, and legal entity. The provider's drift model
expects those columns, constraints, table grants, and column grants exactly.

The base-unit migration scans persisted storage-target projection chunks and
attaches the same deterministic constraint to any already-materialized Item
table. It does not share a healing path with catalog verification: the upgrade
is migration DDL, and provider drift verification only measures the resulting
shape.

## Temporal and authority notes

`effective_at` and `recorded_at` are separate required movement columns.
`recorded_at` has no update path and is included in the stock-horizon index.
This schema does not source either timestamp: G3-P3 must source `recordedAt`
from trusted request context and enforce the per-entity `closed_through` and
backdate rule inside the posting transaction, as ADR-0018 requires.

The tenant calendar has no UTC fallback. Business period is derived by the
declared IANA zone and local boundary, never server locale, process timezone,
or session setting. Legal entity remains an ordinary business dimension rather
than an RLS axis; RLS continues to isolate tenant and environment, allowing
future authorized cross-entity reads inside that trust scope.
