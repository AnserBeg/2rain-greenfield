## Outcome

A tenant release can no longer enter the admitted release set merely by naming
a well-formed UUID. Registration now requires an immutable, durable result set
whose executed plan, compiled artifact closure and release root exactly match
the staged candidate.

The release path is now explicit:

1. persist and verify the immutable package revision;
2. stage the compiled candidate and its content-derived evidence identity;
3. execute every scenario in the compiled verification plan against real
   PostgreSQL gateways;
4. persist the content-bound result set and individual scenario results;
5. register one admission only after reloading and validating that durable
   evidence; and
6. allow activation to load only an admitted target.

The composed application follows that path for bootstrap, initial activation
and forward advancement. Its preparation writer loads the durable evidence
version and result-set digest that `createApproval` consumes. It no longer
mints a random evidence identity or substitutes a digest made from an ID.

## Durable result-set contract

`executeVerificationPlan` now returns a serializable
`northstar.verification-result-set/v1` value instead of relying on process
identity in a `WeakSet`. It binds:

- the candidate release root;
- a digest of the complete release artifact closure;
- the verification-plan artifact root and semantic digest;
- a digest of the canonical plan;
- a provider-generated PostgreSQL run identity that no caller supplies; and
- the exact ordered scenario IDs, fingerprints, positive/negative probe
  digests and aggregate result-set digest.

Admission reloads the stored header and scenario rows, recomputes conformance,
and requires an exact match to the candidate's compiled binding. The execution
commands are closed objects. Unknown fields are rejected, with explicit
controls for a skip flag, sampling parameter and time-box parameter.

Migration `0013_release_verification_evidence.sql` adds append-only, forced-RLS
tables for durable evidence, scenario results and release admissions. Foreign
keys bind results to evidence, admissions to both the exact staged candidate
and its evidence, and federated evidence to a real executed source result set.
The database constrains execution to `FULL`, an empty skipped-scenario set, the
real PostgreSQL provider and no impact-analysis derivation. The checked-in
schema snapshot records the new tables, policies, rules, grants, indexes and
constraints.

## Production execution and preparation

The provider's semantic verifier loads the candidate's compiled runtime
projections while leaving the active pointer unchanged. It invokes the real
Semantic Operation and Query gateways against the PostgreSQL module runtime,
executes positive and required negative probes, and archives the immutable
probe records afterward. Its values derive from compiled field contracts, so
maximum lengths, canonical decimals, enums and temporal shapes are exercised
without fixture-specific semantics.

Party, Catalog and Location harnesses now execute one real candidate plan in an
isolated verification environment and federate only that durable result set to
the exact target scopes. No fixture flag, environment bypass, sampled plan or
invented identity exists.

The only persistence-capable scenario callback is a JavaScript private method
inside `PostgresReleaseVerificationService`. The public production method owns
the PostgreSQL interpreter and generates the run identity itself. An injected
executor can execute and return a transient result set for the saved-filter
refusal control, but that method cannot persist evidence or create admission.

The composed production path executes its own plan, persists and admits the
candidate, then writes preparation evidence from the stored result set before
approval and activation. A PostgreSQL join in the product test observes that
the active release's admission references a durable evidence header, that its
stored result count equals its scenario-row count, and that its execution
source is the same genuine run.

## Saved-filter refusal boundary

The platform saved-filter package remains a Tier-A declaration with all four
required queries. Its bespoke executor still implements only `get` and `list`.
The harness now stages the real compiled package and executes its real plan
through `PostgresSavedFilterExecutor`; verification reaches the positive
resolver probe and fails with `VERIFICATION_RESOLVER_POSITIVE_FAILED`. The
database then contains zero evidence headers and zero admissions, and a direct
registration attempt fails with `VERIFICATION_EVIDENCE_NOT_FOUND`.

Saved filters are therefore non-releasable until current-plan row 1c resolves
the module's tier. This is an executable blocker, not a bypass. The composed
application contains only Party, Catalog and Location, so no product startup
or advancement path depends on the refused package. Because the declaration
was restored, authored/compiled app artifacts and release roots did not move:

## Known boundary

The canonical preparation writer delivered here is the composed production
path: it writes exactly what `createApproval` consumes and binds the stored
result-set digest. Extracting a general preparation service for every future
release producer is deferred; admission integrity does not depend on that
extraction, and the packet does not broaden into a release-orchestration API.

Verification probes are archived, not hard-deleted, in accordance with the
repository doctrine. Storage-transition tests therefore measure any existing
null rows before seeding their own backfill corpus and separately prove every
seeded record was processed.
