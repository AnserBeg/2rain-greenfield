## Outcome and boundary

Inventory now adopts **canonical language v4** and registers one Q1 scalar
aggregate, `inventory_movement_on_hand`. This is distinct from the **Inventory
dependency-set v4** posting contract. The query computes exactly:

```text
SUM(posted inventory_movement.quantity_delta)
  scoped by tenant, environment,
  exactly one legalEntityId, itemId, locationId,
  effectiveAt <= atTime,
  recordedAt <= recordedAtHorizon,
  archive and policy predicates
```

The operand is the ordinary declared
`parameter.on_hand_legal_entity_id`. Its `legalEntityScope` has cardinality
`exactlyOne`; the gateway issues the capability from the caller's argument.
Neither Inventory nor the provider calls `issueLegalEntityReadScope`.

This packet intentionally declares no scoped list query. Consequently the
Q1-P5 inherited shared-list exact-key limitation is unreachable here and
`parseSharedListArguments` is unchanged. Filtered movement history is not
hand-authored around that boundary. Composed availability is also absent:
`reserved` remains a structurally separate future G5-P1 concern, and no
reservation contract or mutable balance field is introduced.

## One registered path

The query follows the existing registered sequence:

1. canonical-language-v4 Inventory authors the aggregate, five declared
   parameters, exactly-one legal-entity operand, and both pre-aggregate temporal
   comparisons;
2. generic compiler aggregate/predicate lowering emits the registered sum and
   parameterized filter plan;
3. `SemanticQueryGateway.invokeAggregate` validates the pinned catalog,
   authorizes the query, binds the UUID operand, and issues the read scope;
4. `PostgresModuleRuntimeInterpreter` verifies the issued scope against the
   compiled entity-owned storage descriptor and visible legal-entity master;
5. the existing generic aggregate executor conjuncts tenant/environment RLS,
   archive exclusion, the verified legal-entity predicate, authored filters,
   and contributed policy filters before `COALESCE(SUM(...), 0)`.

There is no Inventory-specific SQL branch. The only hand-written recomputation
SQL is in the negative/control test and deliberately does not share the cache
writer or registered executor code; it is the independent oracle required by
G3-P0 item 10.

## Derived, immutable, load-bearing anchor

Migration 0019 adds three tenant/environment-RLS relations:

- `semantic_aggregate_generations`, a tenant/environment movement generation
  advanced by the movement table's existing `AFTER INSERT` trigger;
- `semantic_aggregate_anchors`, an immutable derived scalar keyed by that
  movement generation plus release, principal, query, issued legal-entity set,
  all bound parameters, policy/filter plan digest, tenant, and environment; and
- `semantic_aggregate_anchor_discrepancies`, an append-only record of a stored
  anchor disagreeing with its integrity digest and ledger recomputation.

The anchor stamps both temporal horizons by persisting every declared
date-time parameter separately in `temporal_horizons`; the onHand control
requires exactly `atTime` and `recordedAtHorizon` with their supplied values.
The complete parameter map is also part of the cache key and integrity digest.

The cache is load-bearing. A second identical read observes a `cache-hit` and
zero ledger-recomputation observations; equality of the returned number is not
used as the evidence. The victim is the consistent-anchor `return cached;` in
`executeAggregateQuery`: deleting it makes the control observe a recomputation.

The posting-linked generation closes `5g3-stale`. Migration 0019 replaces the
existing `reserve_inventory_movement_effect` trigger function so its same
`AFTER INSERT` invocation both reserves the immutable companion effect and
advances the generation. PostgreSQL executes the trigger inside the movement
statement and posting transaction: failure rolls the append back, and rollback
of the append rolls the generation back. This is not a follow-up invalidation
write. The generation is stable between appends, is inside anchor-key v2 and
anchor-integrity v2, and advances conservatively for every movement in the
tenant/environment. No timestamp, nonce, request counter, or other per-request
input was added.

The interpreter takes a transaction-scoped shared generation guard before it
reads the generation and retains it through cache acceptance or ledger
recomputation. The trigger takes the matching exclusive guard before advancing
the generation. Therefore an append either commits before the read selects its
generation, or waits until that read's transaction finishes; there is no window
after a validation sample in which posting can make a cached answer stale. A
conditional insert additionally refuses to mint an anchor unless its generation
is still current.

The same-key append-after-anchor control reuses one unchanged argument object
for every read. It observes `5` and a real cache hit, commits `+2` inside both
unchanged horizons, then requires a recomputed `7` and a genuine hit on the
refreshed anchor. The concurrency leg holds that refreshed cache key, observes
an identical read waiting after it established the shared generation guard,
then observes an in-horizon `+1` append waiting on that read. Releasing the
cache key lets the earlier read hit `7`; only then can the append commit, after
which the next identical request recomputes `8` and the following request hits
the refreshed anchor. Its rollback leg sees the generation advance inside the
movement transaction, rolls the transaction back, and proves both movement and
generation stayed invisible.

With only the first reaching control added to `be8071b`, the focused PostgreSQL
run failed exactly `actual '5' !== expected '7'`. Fresh Critical review of
`4599ccb` then found that a request could sample a generation before waiting on
its cache-key lock. That correction led to the stricter shared/exclusive guard,
which also closes the later interval between a validation sample and cached
return. Removing only the reader's shared generation guard makes the
concurrency control fail because the append is not observed waiting. Restored,
the command passes 3, fails 0, and skips the one unchanged `BLOCKED(ver-agg)`
case.

The independent proof directly sums the physical movement facts with the full
stock identity, both horizons, and archive predicate. The control then disables
the immutable-update rule only long enough to perturb the anchor balance as an
administrative fault injection. The registered read observes the mismatch,
recomputes through the registered ledger path, appends a discrepancy, preserves
the corrupt `999` anchor, and returns the independent ledger value. The exact
no-stale-answer victim is `return recomputed;`; deleting it falls through to
`return cached;` and exposes `999`.

Sum remains unordered because it is commutative. No diagnostic enumerates
movements, so this packet introduces no competing same-instant ordering. Any
future enumeration remains bound to
`(effectiveAt, recordedAt, sourceType, sourceId, sourceLine, postingRole,
movementId)`.
