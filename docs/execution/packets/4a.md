## Outcome

Canonical language v3 and normalization profile `northstar.normalization/v3` are now selectable
readers. No package adopts either one: `LANGUAGE_VERSION` and `NORMALIZATION_PROFILE_VERSION`
remain compatibility authorities for v2, every checked-in package remains v2, and every existing
canonical byte, golden digest, release root, and compiled web release remains byte-identical.

The former rolling three-name window is replaced by append-only `LANGUAGE_VERSIONS` and
`NORMALIZATION_PROFILE_VERSIONS` catalogs. The v0/v1/v2 compatibility names remain stable rather
than being renamed when a reader is added. `SUPPORTED_*` lists all four stable entries, while
`LATEST_*` is convenience metadata and is not used as a dispatch key. This distinction is
load-bearing: a future v4 entry can be appended without silently dropping v3 from a switch or
tuple.

`CANONICAL_LANGUAGE_PROFILES` is the strict language-to-normalization-profile dispatch. Its v3 row
has feature level v2 because 4a adds no family or node shape. Normalization, authored projection,
the strict predicate-kernel entry point, and compilation accept v3. The compiler emits the same
nine-family projection topology as v2 and labels the v3 release manifest with v3. Existing v0/v1
compiler behavior and all v2 module behavior remain unchanged.

## Scope and implementation

The packet changes only the KERNEL lease:

- canonical version constants, schemas through their supported tuples, normalization/profile
  dispatch, public exports, and predicate-kernel version dispatch;
- compiler profile admission and the temporary v3-to-v2 projection-shape dispatch in
  `compiler.ts`;
- existing canonical-model and compiler test files; and
- this packet record.

`packages/compiler/src/projections.ts` remains untouched because FIX holds it. `compiler.ts`
passes a shallow dispatch view whose envelope version is v2 only to the existing projection and
module-conformance selectors. Nested canonical nodes remain v3, the real normalized definition is
the value hashed, and the release manifest records v3. This is an explicit compatibility adapter,
not a second canonical representation; 4b removes the need to treat v3 as empty when it defines
v3-only content.

No family, aggregate branch, typed query parameter, formula/rule node, capability-disclosure
object, D2 shape, signed-decimal change, domain definition, provider, migration, or app changed.

## Executed evidence

### v3 was not already selectable

Before the implementation, the production normalizer was invoked with a complete ordinary module
whose envelope and all nested nodes were changed from v2 to v3:

```text
PRE_FIX_V3_RED codes=CANON_VERSION_UNSUPPORTED count=190
```

After the change, the same definition normalizes and compiles through the production compiler:

```text
V3_SELECT status=compiled language=v3 profile=northstar.normalization/v3 families=9
```

The compiler test also compares every emitted projection payload's recursive key topology and
array cardinality against the v2 compile, verifies the same nine family IDs, and proves that v3
still receives module conformance by rejecting an empty resolve-match authority.

### Legacy readers are byte-identical

The same pre-change representative authored definition was normalized through all three retained
readers. The post-change digests and byte counts equal the captured base values:

```text
LEGACY_BYTES version=v0-experimental digest=00444e2e40aedea745ea23cc89ac5f2f01f9234dcae2473481b39134f3f036ba bytes=12552
LEGACY_BYTES version=v1 digest=7126210813d43a1b8097f8500c8d3ece3ef5966dfdbe27bbfe988f035bcd0231 bytes=11486
LEGACY_BYTES version=v2 digest=538ed9deca0fed3f2c2340ce05ce65213fbacb02f153544b1d58cc9844d5048a bytes=11508
```

The v3 canonical-authored projection also renormalizes byte-identically to its v3 normalized input.

### Mixed versions still fail closed

A normalized v3 package with exactly one field node changed back to v2 reaches semantic validation
and produces the required diagnostic:

```text
MIXED_VERSION code=CANON_VERSION_MIXED
```

The strict predicate-kernel tests independently execute literal and structural evaluation for
v0-experimental, v1, v2, and v3.

### The set is structurally open-ended

The test extends both catalogs in memory with hypothetical v4 entries and verifies that every
existing binding remains equal without a rename. The observed language-catalog receipt is:

```text
OPEN_ENDED existing=experimentalV0,v1,v2,v3 hypothetical=experimentalV0,v1,v2,v3,v4 renamed=0
```

This is intentionally a structural proxy. It proves the code shape accepts append-only extension;
it cannot prove a future author remembers to add the new supported-tuple, profile-dispatch,
predicate, and compiler rows. The compiler and canonical tests make omissions in those rows red
once a future version is exercised.

## What 4b builds on

Packet 4b starts from an existing v3 reader/profile pair and adds content only to the v3 schema. It
must define, still without adoption:

1. capability-disclosure and formula/rule families, including bounded collections and the boolean
   reason channel;
2. Q1's aggregate branch, typed query parameters/references, normalization checks, catalog metadata,
   `greaterThanOrEqual`, `lessThanOrEqual`, and signed sub-unit decimals; and
3. D2's reserved family shape.

4b must update the v3 profile feature level and replace the empty-v3 projection compatibility
adapter with actual v3 dispatch while leaving every checked-in v2 artifact unchanged. 4c alone
adopts v3 and absorbs the artifact event.

## Known limits and what the gates cannot prove

- No checked-in package uses v3, by design. Provider and browser gates therefore prove that v2
  consumers remain intact; they do not execute persisted v3 releases.
- v3 has no new canonical content. Its schemas are intentionally identical to v2 until 4b.
- The compiler topology comparison ignores scalar values and array order. Separate assertions bind
  the v3 manifest version/profile, family IDs, cardinalities, and module conformance; it does not
  claim v2 and v3 hashes are equal.
- The open-ended test is a structural proxy, not an observation of a real v4 reader.
- The private exact v3 compiler profile is selected by overriding the public v2 module profile's
  language/profile pair. 4c owns changing the ordinary module profile and package definitions when
  adoption occurs.
- No family, node, aggregate, parameter, decimal, projection payload, runtime provider, or storage
  behavior is added here.
