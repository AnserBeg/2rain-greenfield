Status: implementation evidence ready; frozen-candidate matrix and Critical review pending

Integrated base: `2d29f43` (1b, G3-P1a, 1d, and packet 9 plus their accepted execution records).
The product-code advance from 1d voided the earlier documentation-only exception, so generated

## Outcome

The repository's current package authors, canonical/G1/G2 fixtures, compiler defaults, persisted
release round-trips, and composed application now adopt language/profile v3. This is the artifact
event isolated by 4a and 4b: the inventory-blocking aggregate branch, typed query parameters,
`greaterThanOrEqual`/`lessThanOrEqual`, signed sub-unit decimals, derived query-catalog metadata,
normalization checks, and reserved empty `impactAnalyses` family are now the current language.

V0/v1/v2 readers remain supported. The diagnostic shell deliberately remains
`v0-experimental`, byte-for-byte, because it is the end-to-end legacy-reader fixture and carries
four browser negative controls. The composed application moves from v2 to v3. Persisted application
lineage therefore contains historical v2 and current v3 entries at the same time, and each entry is
verified with the compiler profile declared by its own normalized definition.

No capability-disclosure or formula/rule family was added. The orchestrator's sequencing ruling
retired 4b-2: capability disclosure rides the future N1 consumer language event, and formula/rule
rides the G6/N2 tenant-customization language event. The only deadline-sensitive shape, D2's
top-level `impactAnalyses` collection, was already reserved by 4b.

## Adoption boundary

Current authors now use `v3` / `northstar.normalization/v3` and include the required empty
`impactAnalyses: []` root collection. The narrow production definition migration covers Party,
Catalog, Location, Platform, and the composed application builder without changing fields,
surfaces, operations, or storage declarations.

The conditional inventory lease did not fire. At the integrated product base,
`packages/domain/src/inventory/` contains only `contracts.ts` and `index.ts`; no package definition
exists to migrate. A v2 inventory package beside v3 application packages would be legal in any
case, because the one-version rule is per package. `CANON_VERSION_MIXED` still rejects mixed nodes
inside one package.

The historical G1 filenames `vertical-v1` and `vertical-v2` describe the transition scenario, not
the canonical language version. Their authored packages now use v3. Because the current module
conformance floor applies at v3, the fixtures were expanded to the ordinary minimum module shape
rather than weakening the compiler: get/list/search/resolve queries, create/update/archive/restore
operations, list/record/form surfaces, an executable assertion, and a dedicated-table mapping.

## Persisted artifacts own their versions

Adoption exposed one systemic rule across production, scripts, and fixtures:

1. `compile-app-release.ts` had applied one current profile to historical and current lineage.
2. `release-repository.ts` had required the v2 constants on every revision envelope.
3. `composed-application-runtime.ts` and four G2 runtime harnesses had stamped v2 constants on
   every stored revision.
4. `compile-demo-release.ts` still described the v0 shell with a current compiler constant.
5. A repository-wide sweep for the exact persisted-envelope assignments
   `languageVersion: LANGUAGE_VERSION`,
   `normalizationProfileVersion: NORMALIZATION_PROFILE_VERSION`, and
   `schemaVersion: LANGUAGE_VERSION` found six PostgreSQL test writers persisting newly-v3 fixture
   bytes with v2 envelope stamps.
6. The synthetic surface-grammar compiler copied the deliberately-v0 diagnostic shell but invoked
   the current default v3 compiler profile. The exact-SHA architecture run exposed this last
   reader with seven `COMPILER_PROFILE_UNSUPPORTED` failures after the fixture's accidental v3
   node stamp was restored to v0.
7. A transition fixture extended a now-v3 package with nested default/backfill nodes stamped from
   `LANGUAGE_VERSION`, which remains the deliberate v2 compatibility authority. The PostgreSQL
   suite exposed the resulting mixed package as `CANON_VERSION_UNSUPPORTED`; the extension now
   takes its node version from the authored package it mutates.

All now read the normalized artifact, select its declared language/profile, and keep strict
envelope equality. No validator was relaxed and `LANGUAGE_VERSION` was not repointed: 4a
deliberately retained that name as the v2 compatibility authority for legacy projections.

This yielded an adopted learning that supersedes the earlier G2-P2a wording: any component reading
or writing persisted artifacts across a version boundary takes language/profile versions from the
artifact, never from a compile-time constant. The still-correct half of the earlier rule remains:
when compiler roots or persisted metadata move, downstream PostgreSQL registration suites are
required before acceptance.

The six test helpers were not treated as disposable mocks: they exercise the same strict release
repository boundary as production and now parse each normalized `desiredState` before constructing
its envelope. A spot-fix of the three initially reported production sites would therefore have
left six provider gates red at the moment strict validation became active. The reusable method for
the next version event is the assignment sweep above, followed by classification of the remaining
hits as artifact writers or deliberate version-specific fixtures.

The second sweep inventoried every `compileApplication` call that spread a fixed
`DEFAULT_COMPILER_PROFILE` or `MODULE_COMPILER_PROFILE`, then traced its
`normalizedDefinitionBytes` producer back to the authored artifact. Comparing those two declared
versions found the deliberately-v0 surface-grammar artifact behind the fixture compiler, browser
journey, and architecture diagnostic helper. Party already derived its profile; Surface data
binding, Catalog, Location, and the determinism subprocess consume only current v3 artifacts and
were deliberately left unchanged. This trace-from-consumer-to-artifact method found the class;
searching only for hard-coded version fields did not.

## Discovered version-only storage transition

The first composed-release regeneration failed before artifact generation:

```text
COMPILER_STORAGE_RETYPE_UNSUPPORTED
path: $.fields.fieldType
subject: northstar.app:field.item_sku
```

The v3-to-v2 compatibility view used by unchanged projection families retained the v3
`fieldType.schemaVersion`. Storage fingerprinting therefore interpreted a language-marker-only
change as a physical column retype. The compiler's bounded compatibility projection now maps field
type and enum-option version markers to v2 before legacy physical fingerprints are calculated;
the original v3 normalized definition remains the hashed authority, and v3 metadata is decorated
after the legacy projections are built.

A permanent transition test compiles semantically identical v2 and v3 packages against an
expected-active transition and observes `storageTransition.elements` as exactly `[]`. This is
stronger than merely making the app artifact regenerate: it proves a language-only adoption cannot
silently request data-affecting DDL.

## Plan §5.1 versus §5.5 disposition

Plan §5.1 says the launch language owns every launch object family, while §5.5 says a capability is
`Supported` only when its authoring, compiler, runtime, storage, policy, sinks, migration,
read-back, recovery, and evidence all exist. The packet resolves the tension in favor of explicit
support truth rather than unused schema claims:

- v3 adopts only the shapes with a live inventory consumer and the already-deadlined D2 family key;
- `capabilityRequirements` remains fail-closed runtime authority and is not repurposed as product
  disclosure;
- capability disclosure and formula/rule become language events with their actual N1 and G6/N2
  consumers, when §5.5 can be satisfied rather than implied.

This is an explicit staged departure from §5.1's literal “first schema version” wording, not an
accidental omission. The closed-set artifact cost is paid when a family becomes real, not stages
early merely to populate a launch-family checklist.

## Known limits and what the gates cannot prove

- Q1-P3b still owns aggregate SQL lowering, policy/archive/tenant conjunctions, result overflow,
  and the execution-observed cost-class probe. V3 makes those shapes serializable; it does not run
  them.
- D2 reserves only an empty top-level collection and its structural bound. Row 4d owns impact
  content and reference-graph semantics.
- Capability disclosure and formula/rule are deliberately absent until their consumer language
  events. This packet proves neither family's future shape.
- The legacy projection compatibility view is an internal bridge for existing projection
  families. It proves a version-only transition has no storage DDL, but does not assert that all
  future v3-only physical concepts can reuse v2 projections.
- No inventory package definition existed at integration, so 4c proves no inventory-domain
  migration. The canonical aggregate shapes and composed application are v3; BUILD must author the
  eventual inventory package at the then-current language.
- The diagnostic shell remains v0 by design. It proves the v0 reader and negative controls, not
  that v0 modules satisfy v3's current module-conformance floor.
