### Materializer policy-boundary correction

The final correction removes every materializer `SELECT` policy on `platform`
tables and every direct platform-table `SELECT` grant. Materializer runtime SQL
now reaches kernel state only through five narrow
`north_star_internal.module_storage_read_*` `SECURITY DEFINER` readers. Each
reader uses schema-qualified objects with fixed `search_path = pg_catalog`,
requires non-null tenant/environment arguments equal to the trusted
transaction-local settings, and returns only the pointer, artifact, authority,
approved-attempt, or live-root facts needed by the caller.

`PUBLIC` execution is revoked and only `north_star_module_materializer` receives
`EXECUTE`; `north_star_runtime` (the Query/Operation gateway runtime) and
`north_star_module_runtime` cannot execute the readers. The PostgreSQL proof
also queries the catalogs to require zero materializer policies and zero direct
platform relations with `SELECT`, validates the definer/search-path/execute
facts for all five readers, and proves that every cross-tenant invocation
returns zero rows. This keeps the DDL principal from becoming a second broad
platform reader while preserving the minimum trusted facts required to
materialize an exact persisted release pair.

The DML-only role receives one additional fixed-search-path scoped
`SECURITY DEFINER` mutation gate. It returns only whether the exact approved
attempt remains valid and serializes each batch against attempt cancellation
and current authority changes; it does not expose any kernel row. The
materializer and Query/Operation runtime cannot invoke it.

  live boundary and registered permission checks, and dispatch only active Q0
  or O0 registrations. Nontrivial predicates that the launch interpreter does
  not implement return the stable `unsupported` envelope instead of being
  ignored.
- One `PostgresModuleRuntimeInterpreter` loads the exact pinned release's
  content-hash-verified storage-target artifacts and interprets the physical
  mapping. Registration remains data. No module name, generated handler, or
  fixture-specific branch exists in production source.
- Q0 get/list/search/resolve use selected visible fields, stable record-ID
  ordering and paging, archive-hidden defaults, and exact/ambiguous/not-found/
  unsupported results. DTOs contain canonical entity/field IDs and logical
  values only; physical names and storage class never cross the provider
  boundary.
- O0 supports only create/update/archive/restore. It enforces optimistic
  revision checks, read-back through the registered pinned get-query shape,
  parent-scoped child relations, and the P2b composite tenant/environment
  foreign key. There is no delete operation or raw domain-table ingress.
- Every O0 write runs inside `PostgresTrustService.executeAcceptedMutation`.
  Module mutation, ActionInvocation, BusinessChangeDocument, event, and outbox
  therefore commit or roll back as one transaction. Canonical field and
  relation values are conservatively classified `SENSITIVE`; the journal
  preserves absent/value/cleared state while values are redacted. Actor
  identity comes only from the issued trusted context and actor gateway.
- The original trusted context is bound privately to the issued
  `RequestRuntimeView` and supplied to the executor port; request input cannot
  substitute tenant, environment, principal, request, or release identity.

### Named O0 role-assumption bridge

Migration `0008_module_runtime_role_assumption.sql` grants
`north_star_runtime` only `SET` membership in `north_star_module_runtime` with
`ADMIN FALSE` and `INHERIT FALSE`. The login therefore has no ambient module
DML. The generic interpreter starts a trusted request transaction as
`north_star_runtime`, verifies the session role, uses `SET LOCAL ROLE` only
around module DML, verifies the assumed role is neither superuser nor
`BYPASSRLS`, and executes `RESET ROLE` before returning to the trust callback.
Trust evidence is consequently written as `north_star_runtime`, never as the
module role.

The grant is one-directional. Catalog evidence proves
`north_star_module_runtime` cannot assume `north_star_runtime`, cannot insert
trust facts, and cannot reach the materializer role. Neither runtime role is
superuser or `BYPASSRLS`; the DDL-only materializer remains disjoint and
unreachable. Failed DML aborts the single transaction, whose rollback and
connection cleanup reset the local role before reuse, and writes no trust
fact. Successful DML followed by linked trust facts proves the reset occurred
before evidence insertion.

The bridge required no schema-snapshot byte change. The migration-list/count
assertions consciously advance the stream to 0008 without weakening any
behavioral assertion.
