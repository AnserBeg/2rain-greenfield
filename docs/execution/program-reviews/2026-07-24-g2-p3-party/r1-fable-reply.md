**2. [MATERIAL] Declared `humanRequired` confirmation is enforced nowhere real — the gateway ignores it, and the UI's own forms auto-supply the confirmation as a hidden field.**
Evidence: Party archive declares `confirmation: 'humanRequired'` (packages/domain/src/party/definition.ts:348). SemanticOperationGateway never reads `definition.confirmation`; its request envelope has no confirmation field at all (semantic-operation-gateway.ts:31-35, 147-227) — any direct gateway caller (the future agent channel per ADR-0009 enters here) executes archive with zero confirmation. The only check is apps/web/src/surface-runtime.ts:167-172 (`submission.confirmed !== 'yes'`), and the server-rendered forms defeat it by emitting `<input type="hidden" name="confirmed" value="yes">` (component-registry.ts:214, 222). The integration test enshrines the bypass: `assert.match(initial.html, /name="confirmed" value="yes"/)` (test/integration/surface-data-binding.test.ts:307).
Why it matters: violates ADR-0008 twice ("validates exact confirmation/approval grants"; "confirmation... cannot vary by channel") and plan 8.5 ("consequential effects always preview predicted effects and confirm"). The declared confirmation level has zero behavioral difference from 'none' on every channel; the fan-out template and later the agent lane inherit confirmation-free consequential operations.
Smallest fix: add a typed confirmation grant to the operation request envelope, enforce `definition.confirmation !== 'none'` at the gateway (fail closed), render a real two-step confirm in the surface runtime, delete the hidden field, and invert the test.
Disposition: fix-before-fan-out.

**3. [MATERIAL] The conformance gate's per-entity "verification evidence" dimension is self-attesting — a module satisfies it by declaring a JSON array of evidence kinds.**
Evidence: compiler/src/conformance.ts:134-159, 221-227 credits an entity with structure/provider/userInterface/agent/migration/recovery evidence if ANY active AssertionDefinition lists those strings in `evidenceKinds`; Party declares exactly that constant array (domain/src/party/definition.ts:439-447), including 'recovery' — and no Party recovery test exists anywhere in test/**. Nothing binds a declared evidence kind to an executed proof.
Why it matters: ADR-0011 requires "verification coverage including per-entity recovery evidence" as a conformance dimension; today that dimension is satisfiable by a copy-pasted literal, and the fan-out template (Catalog, Location) will copy exactly that literal. This is the structural-vs-semantic gap embedded in the gate that is supposed to close it.
Smallest fix: have the compiler emit the declared kinds into the verification-plan projection and add a gate that fails when a declared evidence kind has no executed, recorded proof for that entity (even a per-kind test-ID ledger checked in CI); until then, rename the diagnostic so packets cannot cite it as proof of verification.
Disposition: fix-in-named-later-packet (G2-P4 or the G2-P9 stage gate) — but stop crediting it in packet evidence immediately.

**4. [MATERIAL] Search ignores the declared `searchable: false` and matches against a confidential field; the declared search normalization is also not what search executes.**
Evidence: the interpreter's search column filter is `selected && (searchMapping === 'normalizedTextIndex' || /^(?:text|character varying|varchar)/.test(postgresqlType))` (module-runtime-interpreter.ts:637-644) — the type-based fallback disjunct searches ANY selected text column. Party's `contactSummary` is declared `searchable: false` AND `classification: 'confidential'` (definition.ts:92-101) but is selected by party_search (definition.ts:38,147), so a `%text%` substring search matches on the confidential column even though the compiler correctly emitted `searchMapping: 'none'` for it (storage.ts:1188-1190). No test in the repository exercises searchable-exclusion (grep 'searchable' under test/ hits only fixture declarations). Additionally search matches with `lower() LIKE` while resolve/uniqueness use the pinned `nsm_unicode_case_fold_v1` — two different fold semantics for the same declared normalization profile — and the emitted 'search' index is a plain btree a `%text%` LIKE can never use, so the declared search mapping is decorative.
Why it matters: a declared privacy-relevant contract (searchable:false on a confidential field) is silently violated by the generic press, i.e., every future module inherits it; it is a textbook instance of the charter's hypothesis.
Smallest fix: restrict search columns strictly to `searchMapping === 'normalizedTextIndex'`; add a metamorphic-fixture probe (searchable:false field must not match, searchable field must match case-insensitively per the profile).
Disposition: fix-before-fan-out.

**5. [MATERIAL] Denied and failed attempts leave no trust evidence — `recordNonAcceptedInvocation` has zero production callers.**
Evidence: the API exists and is tested (postgres-trust-service.ts:167-205; test/postgres/trust-substrate.test.ts:201,237,395-405) but grep shows no call site outside tests; the gateway throws `SemanticOperationPolicyDeniedError` (semantic-operation-gateway.ts:165-166,185-186) and interpreter failures (revision conflict, relation-target-not-found, unique violation) propagate with no DENIED/FAILED ActionInvocation row.
Why it matters: ADR-0010 declares ActionInvocation "the sole cross-channel invocation-evidence authority for allowed, denied, failed, timed-out, and successful attempts"; today only SUCCEEDED is recorded on the live path. Denial/failure evidence is precisely what the audit story and the future agent lane need.
Smallest fix: wire gateway deny paths and executor failure paths to `recordNonAcceptedInvocation` with typed failure codes (the plumbing and validation already exist).
Disposition: fix-before-fan-out (low cost, ADR-visible).

**9. [MINOR] Write/read normalization asymmetry: resolve/search input is NFKC-normalized but stored values and uniqueness are case-fold-only.**

## DIAL B VERDICT — B1 (goal): KEEP

## NEW CONCERNS (not asked)

1. **Per-request cryptographic re-verification will not scale past toy releases.** Every query/operation re-reads ALL release artifacts and re-hashes each (module-runtime-interpreter.ts:874-886 loops verifyArtifact over the whole set), and an update does this THREE times (storage load, prior-record load, mutation transaction). Correctness-gold, but cost is O(release size) SHA-256 per request and will be felt abruptly when Catalog/Location/G3 multiply artifact count and row traffic. Needs a verified-once, content-hash-keyed immutable cache (the loader service already has one; the interpreter bypasses it) before G3 — as a deliberate packet, not an emergency patch.
2. **O0 has no idempotency story, and the outbox dedup key can never dedupe.** Create-retry with the same recordId surfaces as a raw unique violation (no idempotent-success contract), and `deduplicationKey` embeds the per-attempt random invocationId (interpreter:293), so retried deliveries are distinct by construction. Harmless for master data; fatal if the pattern is copied into G3 postings, where ADR-0007's "one source effect cannot post twice" is the core invariant. Decide the idempotency spine (gateway-level idempotency keys + outbox dedup semantics) before O1 is designed, not inside it.
3. **The trust substrate has no read surface.** Change documents/events are written but unreadable through any semantic contract (no Q0 query, no read model) — yet plan 8.5's activity rail and ADR-0008's "no direct table reads that drive business behavior" jointly require a governed trust read model. Left unplanned, the first activity-rail packet will be tempted into raw SQL against platform.trust_* from the app; name the packet now (it also forces Finding 7's classification fix, since a rail over all-REDACTED changes is useless).
